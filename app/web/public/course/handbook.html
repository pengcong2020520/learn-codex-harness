单轮：打通执行引擎

控制台发问后，谁真正调用了模型？从 stdio 到 turn/completed，逐层拆解一次请求的完整生命周期。

全景：一次请求怎样走完

先分清用户、我们的程序、Codex 和模型四个角色，再沿五步流程检查一轮问答。

📌

关键认知

Node.js 不直接调用模型 HTTP 接口。它是编排客户端，Codex 才是真正与远端模型通信的执行引擎。两者通过 stdio 连接。

邮局比喻：initialize → initialized

把这套通信想象成一个邮局系统：Node 是寄件人，Codex 是邮局，模型服务是收件目的地。寄信前必须先"在柜台登记开户"——这就是协议握手。

1
spawn 启动子进程
Node 调用 child_process.spawn，把 Codex App Server 作为子进程拉起。此刻"邮局开门"，但还没有任何账户。
2
发送 initialize 请求
Node 通过 JSON-RPC 2.0 发送 initialize 方法。Codex 返回初始化响应，客户端等待这一步成功。
3
发送 initialized 通知
Node 再发一条单向通知 initialized（无需回复），告知 Codex"我已收到你的初始化响应，正式开始"。握手完成。
为什么要两步握手？
initialize 返回初始化结果；initialized 是客户端的确认回执。两步保证双方同步进入"就绪"状态，避免客户端在服务端还未准备好时就发业务请求。
为什么本地不需要 HTTP 端口
Node 与本机 Codex 通过进程管道通信；握手完成后，thread/turn 请求沿用同一连接。远端模型调用仍然需要网络。

Thread 与 Turn：往来档案与一次寄送

Thread 是一个往来档案，Turn 是其中一次寄送。单轮 Demo 只新建一个档案、完成一次寄送，但架构已经为多轮做好了准备。

⚠️

事件先到缓存——关键时序细节

turn/start 触发的事件通知可能在 RPC 响应（含 turnId）返回之前就到达 stdio。代码先建立监听缓冲区，收到 turnId 后再回放已缓存的匹配事件，防止漏掉早到的通知。

turnId 不是递增数字
Turn 标识符由 Codex 服务端生成，是唯一字符串而非 1、2、3 这样的计数器。匹配时必须用完整 ID 对比，不能用序号推算。
finally 的责任
无论成功还是异常，finally 块都必须关闭子进程。否则 Codex 进程会在后台残留，占用资源并可能干扰下次启动。

FIFO 是排队，不是推理

FIFO 输入缓冲是用户侧的节奏控制机制，不负责模型内部的推理循环。

容易混淆的两个概念
外
FIFO 缓冲 · Node 侧

用户消息入队、出队；决定何时发出下一个 turn/start，不决定模型如何推理。

内
ReAct / 内部 Loop · Codex 侧

处理一个 Turn 内的模型推理与工具调用往返；不管理下一条用户输入的排队。

关键区分

FIFO 决定的是"你的第三条消息要等第二条处理完才能发出"，而不是模型"思考"的步骤数。

从执行机制看，一个 Turn 可包含多次推理与工具往返，由 Codex 的内部循环控制。本阶段的工具能力受限，不能把这种机制理解为已开放外部工具。

结论：FIFO 是外部排队，ReAct 是内部循环，两者分工不同。

为什么需要 FIFO？
如果同时推进多个用户输入，客户端必须处理更复杂的会话状态。本阶段按顺序等待每个 Turn 完成，使输入与结果的对应关系清晰。
超时后恢复原会话
s02 超时后停止连接，提示重启并使用 /resume。任务状态持久化、unconfirmed 与 /continue 队列恢复属于 s04 的服务能力。

resume 恢复会话 vs 记忆注入：两件不同的事

这是最容易被混淆的概念对。用笔记本比喻：resume 是"重新翻开一本旧笔记本继续写"，记忆是"把多本笔记的精华摘录写到新本子的扉页"。

/resume 做了什么
1. 按关键词检索本地会话元数据（名称 / 开场预览）
2. 显示编号列表，用户输入数字选择
3. 发送 thread/resume RPC，Codex 恢复该 Thread 的原生历史
4. 后续 Turn 在此 Thread 上继续，上下文连贯
记忆（Memory）是什么
长期记忆可将有用信息跨会话保留并在后续会话召回；它与重新打开某一个历史会话是不同机制。
s02 不开启跨会话记忆（features.memories=false），/resume 恢复的是历史上下文，不是记忆注入。

服务：让 Agent 常驻

这个云端 Agent 还缺一个独立运行的服务端。亲手接通 HTTP 入口，追踪一轮的执行归属，验证客户端离线后的结果与资源收尾。

这个云端 Agent 还缺什么？一个能一直工作的服务端

我们已经能在一个 Thread 里连续对话，也能用 /resume 找回历史。现在请它写一份长回答，回答到一半关掉终端：如果终端程序持有 Codex 子进程，这次执行就会跟着结束。要亲手做一个云端 Agent，先让执行拥有独立于用户窗口的生命周期。

本章要完成的体验很具体：在一个终端启动服务，在另一个终端聊天；关掉聊天窗口，服务继续工作；重新连接同一个 Thread，查看这一轮的结果。先在本机验证这条链路，服务默认只监听 127.0.0.1:4313，本章不提供公网部署或多用户授权。

服务端持有什么
读取 .env 中的模型配置，启动 Codex App Server，持有会话与执行中的 Turn。服务端接收 Codex 通知，即使此刻没有客户端查看，也会更新状态。
客户端持有什么
读取 .data/connection.json 中的地址与连接令牌，保存当前选中的 Thread id，通过 HTTP 提交和查看。客户端不读取 .env，不启动 Codex，不需要模型 API Key。

Thread 是会话，Turn 是其中的一轮。服务端进程、客户端进程、Codex 子进程则是运行边界。把这三种概念分清，就能回答“关掉哪一个进程会停止哪一部分工作”。

📌

先定验收条件

客户端退出只停止提交与查看，已交给服务端的一轮继续执行。停止服务端会结束 Codex 子进程；原生历史保留，但 s03 没有持久任务记录来核对中途执行。

接好入口：HTTP 请求先过连接校验

给 Agent 一个入口，并不意味着把模型密钥交给每个客户端。服务启动时生成随机连接令牌，写入权限为 0600 的连接文件。客户端每次发送 Authorization: Bearer <令牌>；这个令牌只用于访问 Agent 服务，与远端模型的 API Key 分别管理。

HTTP 负责外层请求；服务端通过 JSON-RPC 调用 Codex。读源码时先看谁在和谁说话，再看同样名为“请求”的操作实际跨过了哪条边界。

发起一轮：为什么要同时检查 activeTurnId 和 starting

试想两个客户端几乎同时向同一个 Thread 提交。只检查 activeTurnId 不够：第一条请求可能已发出 turn/start，却还没拿到 turn id，第二条就趁这个空隙进来了。因此需要一个“正在发起”的标记。

  async startTurn(threadId, text) {
    requireText(text);
    await this.ensure(threadId);
    const session = this.sessions.get(threadId);
    if (session.activeTurnId || this.starting.has(threadId)) throw new AppError("上一轮还在执行，请等它结束再发送。", 409, "TURN_IN_PROGRESS");
    this.starting.add(threadId);
    try {
      const result = await this.rpc.request("turn/start", { threadId, input: [{ type: "text", text: text.trim(), text_elements: [] }] });
      const turn = this.recordTurn(threadId, result.turn);
      return { threadId, turnId: turn.id, status: turn.status };
    } finally { this.starting.delete(threadId); }
  }

POST /turns 会等待 startTurn 返回，然后响应 202。它省去了等待完整模型回答的时间，但不是“收到 HTTP 就直接返回”，也没有把输入写入持久队列。

查看一轮：停止轮询为什么不会取消执行

      const { session } = await this.request(`/state?threadId=${encodeURIComponent(threadId)}`);
      onSession(session);
      const turn = session.turns.find(item => item.id === turnId);

断线不等于未提交

如果 POST /turns 的响应在网络中丢失，客户端可能不知道服务端是否已经发起执行。s03 没有 clientMessageId 去重记录，不要把“没收到响应”当成“肯定没执行”而直接重复发送。下一章会为每条输入建立任务记录。

事件与消息：让任务有序执行

这个云端 Agent 还缺可靠的连续提交与状态同步。亲手串起任务记录、按会话调度和 SSE，遇到不确定执行时保留证据、暂停核对。

这个云端 Agent 还缺什么？能保存每条输入的任务记录

现在服务端能独立完成一轮了。试着在回答过程中再输入两条，然后关闭客户端：已经发出的那一轮可以继续，仍等在客户端的输入却没有服务端记录。一个能长期工作的云端 Agent，还要接住用户连续交来的事情，并告诉用户每一条走到了哪里。

本章的验收场景是：连续提交三条普通消息，三条都被服务端接收；关闭客户端后，服务端依次完成它们；回来时能看到队列和会话状态。如果执行结果拿不准，就停下来让用户核对，避免把同一件事做两遍。

messages：决定执行节奏
接收消息、按 Thread 排队、发 turn/start，处理追加、超时、暂停与继续。它决定哪条输入现在可以执行，不代替 Codex 内部的推理与工具循环。
data：保存任务事实
将消息和暂停状态写入 .data/messages.json，每次更新整体原子替换文件。进程退出后记录还在，重启时可据此判断哪些任务需要核对。
events：把变化交给订阅者
事件中心分发会话与队列状态，经 HTTP 的 SSE 连接交给对应 Thread 的客户端。它不负责启动下一轮，也不调用模型。

区分三个 ID：threadId 标识会话，clientMessageId 标识用户这次提交，turnId 标识 Codex 执行轮次。任务可以在还没有 turnId 时就处于 queued；追加也可能与已有任务关联到同一轮，三个 ID 不能相互替代。

实现边界

服务默认监听 127.0.0.1:4319，仍是本机单用户、单进程队列。同目录只运行一个服务；每个会话最多 100 条 queued 消息。本章验证可靠提交与状态同步，不提供多机器调度。

提交先落盘：同一个消息 ID 为什么不会做两遍

客户端为每条输入生成 clientMessageId，再调用 POST /messages。服务端先校验文本、模式和会话，进入同一 Thread 的串行操作区间，然后检查这个 ID 是否已有记录。幂等 在这里解决的是“同一提交的重复请求”，不是“所有意思相同的文本都只执行一次”。

调度一次：普通消息 FIFO，显式追加另有去向

FIFO 的范围是同一个 Thread。调度器先看会话是否暂停，再看有没有正在执行的 Turn；不同 Thread 的任务互不阻塞，同一 Thread 的普通输入一次只启动一轮。

让状态主动到达：SSE 先快照，后事件

客户端订阅 GET /events?threadId=…，建立 SSE 长连接。服务端有变化时发送数据，不需要客户端每 200 ms 询问一次。消息提交仍走 POST /messages；订阅只负责查看。

snapshot / session / queue
snapshot 是每次连接的首条完整状态，含会话与队列；session 表示会话变化，queue 表示任务状态、暂停或继续。客户端用这些内容更新显示。
fatal / shutdown
fatal 提示执行连接失效、服务停止调度；shutdown 表示服务正常关闭。看到这类事件要核对服务与任务状态，不能据此认定所有任务已完成。

客户端断线后约一秒再尝试连接，每次都先获取快照。事件序号用于排查问题，本章不按 Last-Event-ID 重放历史事件。快照帮助客户端重新看到当前状态，不承诺补齐离线期间每一条事件；订阅过程也不会替用户再提交一次消息。

普通事件写入积压超过 1 MiB 时连接会被断开，再由客户端重连取快照。快照之后的事件仍是状态更新，渲染时应以事件内容更新视图，不能把事件到达次数当作执行次数。

Registry 从 config/tools/*.json 装配：配置声明工具规格和实现模块，加载器编译参数校验规则、加载工厂函数，再把名称绑定到实际执行函数。重名、缺实现、无效 schema 或越界模块路径会使装配失败。

本阶段的四个默认工具
list_files 列出授权范围内的资料，read_file 读取文本，write_file 新建文件，read_webpage 读取公开网页。没有网页搜索工具；读取网页不等于搜索互联网。
模型提出调用，服务端执行
Codex 通过 MCP 发现和调用工具。注册表检查工具名与参数，文件服务继续检查路径与权限。Skills 描述方法，但不会自动增加 tools.allow 中的授权。

不可变 Blob：内容寻址与来源追踪

单机单 owner、单 Agent 配置，支持多 Thread；并非多 Agent 编排。s08 使用数据库 agent_s08（schema v1），s09 使用 agent_s09（schema v2），PG 与 Redis 均必需。两套 Compose 绑定相同的 5432/6379 端口，不可同时启动；可共享一组依赖并使用不同数据库。

sha256 是内容指纹，正文按指纹命名保存。内容改动会生成新 blob，已登记版本不被覆盖；这不等于承诺永久保留。 这让系统能追踪“摘要声明引用的是 report.md 哪个版本”；读取或校验发现原文变化后，依赖链会传播失效。

🔒
create-only，不覆盖
write_file 只创建新路径，已有路径会被拒绝，即使内容相同。底层 blob 可按内容指纹复用；这是不同层次的规则。
📂
路径格式
.data/files/objects/<sha256>.txt——无子目录，所有版本平铺在同一目录。.data/codex/ 是 Codex 原生存储，由 Codex 管理，主进程不读写。
🔗
来源声明 vs 语义证明
dependencies 表记录版本依赖，source_versions 声明来源。这是声明，不证明模型语义引用完全——AI 可能引用了未声明的内容。
⚠️
跨存储非原子
blob 文件写入与 PG 写 resource_versions 之间没有跨存储事务保证。PG 内部操作是原子的；跨文件系统与数据库则不是。

RAG 索引：从 Wiki 到向量检索的切换路径

RAG 是可选层，Chroma 是可选依赖；未启用 RAG 时可使用 wiki 模式。切换到 RAG 必须走完以下路径——不能热切换，不能在运行时自动生效。

①
配置并重启

②
发 index 任务

③
两边就绪后切指针

④
Agent 配置改 rag + 重启

上一章，云端 Agent 已能通过 Wiki / RAG 查依据，文件和知识操作也经过同一道门禁。这个云端 Agent 还缺什么？用户说“写一篇文章”，可能希望先看大纲再决定；用户说“整理这些新资料”，可能还需要一次受限的知识库更新。能调用工具，还不足以表达哪里等人确认、这一次能写到哪里、做到什么才算交付。

上一章 s10 用 Skill 教方法，用 Workflow 管步骤、权限与确认。写作任务可以先产出大纲，等用户确认后再继续成稿。这个云端 Agent 还缺什么？大纲和成稿未必适合用同一个模型；知识检索需要向量模型，生成图片又是另一种用途。模型越来越多之后，谁负责挑选，谁持有密钥，花费达到上限时谁来停止派发，都需要明确的执行位置。

交付一个部署单元，明确进程与数据的归属

已有的 Agent 可以组织任务、使用工具和知识、执行 Workflow，并通过模型网关选择模型。让它在服务器上持续工作，还需要回答几件具体的事：运行环境怎样复现，服务什么时候能接任务，退出后由谁重新启动，数据库和原生历史放在哪里，升级失败以后能恢复到什么状态。本章把这些责任收进一套独立部署，不改变 Codex 的推理与工具执行循环。

部署单元 包含 postgres、redis、gateway、agent 四个服务。PostgreSQL 保存业务事实，Redis 承担队列唤醒，Bifrost 承接模型请求，agent 运行既有服务。只有 agent 发布宿主回环端口；客户端使用 SSH 隧道进入。它不加入 app 的共享 stages 容器，也不登记为工作台默认实时目标。

边界本章负责什么仍需保留的依据
Codex管理 Thread、Turn、上下文与工具执行。原生 SQLite / JSONL 历史与固定路径。
Agent 服务判断就绪，限制排队、执行和连接，关闭时保存不确定状态。PostgreSQL 任务记录、执行器与队列状态。
Compose / Docker固定服务版本、依赖健康、挂载与退出重启。镜像、锁文件、卷与宿主目录。
宿主 Bash / systemd开机启动、远程部署、停服备份和恢复。部署版本、成功备份、权限与操作结果。

镜像固定 Node 版本和 digest，按 npm 锁文件安装依赖，使用非 root 的 node 用户。Agent 镜像额外安装 lsof 和 bubblewrap；数据库转储使用正在运行的 postgres 容器，不要求在 Agent 镜像里安装 PostgreSQL 客户端。构建可以配置 NPM_REGISTRY 与 APT_MIRROR，配置改变镜像下载来源，不改变服务的责任。

PostgreSQL 和 Redis 使用命名卷；.data、.runs、workspace 和 backups 使用宿主目录挂载。代码和镜像可以替换，持久状态需要保留。正文、产物与原生历史都不应该因为容器重建而消失。部署脚本不会把镜像当成数据备份，也不会把删除数据卷作为日常停止方式。

固定路径 是恢复契约。CONTAINER_APP_DIR 必须等于宿主部署目录，容器内工作位置保持一致。使用带时间戳的新目录运行下一版代码，看起来便于保留版本，却会改变历史引用的位置。本章在固定位置替换代码与镜像；要转移原生历史，需要连同原路径保持一致，没有实现跨路径历史改写。

接多少、做多少、连多少：四个容量边界

服务长期运行后，一次请求所占的资源并不一样。普通 HTTP 请求可能很快结束；SSE 可以保持连接；数据库中的 queued 任务等待执行；一个运行中的模型轮次可能持续较久。只限制请求频率不能限制活动轮次数，只限制轮次又挡不住连接耗尽。因此部署配置分别给出四个上限。

SSE 使用独立名额：在异步读取会话数据前先 acquireSse，连接 close 时释放。释放函数带有 released 标记，即使清理路径重复调用，也只减一次计数。满额错误与请求超频错误都使用 429，但错误码和等待时间不同。健康接口绕过限流，让运维仍然能检查进程和依赖。

关闭先停止派发，重启保留不确定事实

一次轮次可能已经执行了外部操作，但尚未来得及把最终结果完整持久化。进程此时收到停止信号，不能把未收到终态等同于“模型完全没做事”，也不能把残留任务直接再发一次。部署的关闭逻辑要先阻止新增工作，再保存已经确定的状态，并给未确认的执行留下人工核对入口。

pending 让多次关闭请求共享一次流程，避免重复关闭资源。

stopDispatch 同步执行，收到信号后先停止继续派发。

正常清理结束后取消截止定时器；无法在截止前落库的残留执行状态，交给启动恢复再次处理。

SIGTERM 到达后，关闭入口按这个顺序组织服务：同步停止派发，把执行中的不确定状态持久化为 unconfirmed，然后关闭连接和资源。queued 任务仍保留。重启时沿用已有 recover 处理残余 starting、running、steering，不会自动重发需要核对的任务。这个设计保留了事实的不确定程度。

停止前状态停止或恢复后的含义下一步动作
queued尚未派发的持久任务仍在。服务恢复后按队列机制处理。
starting / running / steering可能已发生执行，结果需要核对。恢复为 unconfirmed，先查看任务结果与产物。
完成且已落库保留已有完成事实。根据已保存结果继续业务流程。
资源关闭卡住30 秒截止后强制退出。启动恢复检查残留状态，不能推断外部操作未发生。

优雅关闭并不是跨模型、数据库和文件系统的原子事务。执行器依赖 PostgreSQL 独占锁，服务停止后重建连接与锁仍需验证；模型工具内部的行为也不是部署模块重新实现的。真实 SIGTERM 验收应观察派发停止、任务状态、进程退出时间和重启后的恢复结果。离线断言能验证调用顺序，不能取代服务器上的完整故障过程。

代码回滚同样要区分事实。remote.sh 保留上一版目录和 previous 镜像标签，回滚替换代码与镜像，数据目录维持原路径。它不恢复 .env 的历史版本，也不会自动倒转数据库和 workspace。如果升级包含破坏性 schema 变化，需要兼容代码或升级前的完整备份，不能只切换镜像就宣称业务数据已恢复。

部署失败会留下 pending 标记，下一次部署前需要先处理回滚。首次部署没有上一版，排除故障并确认没有部署进程后，才能清除 pending 再重试。这个标记记录的是未完成的交付事实；它和 flock 锁文件不是同一概念。flock 在进程退出后释放，不需要通过删除锁文件来解锁。
