关键认知

Node.js 不直接调用模型 HTTP 接口。它是编排客户端，Codex 才是真正与远端模型通信的执行引擎。两者通过 stdio 连接。

邮局比喻：initialize → initialized

把这套通信想象成一个邮局系统：Node 是寄件人，Codex 是邮局，模型服务是收件目的地。寄信前必须先"在柜台登记开户"——这就是协议握手。

1
spawn 启动子进程
Node 调用 child_process.spawn，把 Codex App Server 作为子进程拉起。此刻"邮局开门"，但还没有任何账户。
2
发送 initialize 请求
Node 通过 JSON-RPC 2.0 发送 initialize 方法。Codex 返回初始化响应，客户端等待这一步成功。
3
发送 initialized 通知
Node 再发一条单向通知 initialized（无需回复），告知 Codex"我已收到你的初始化响应，正式开始"。握手完成。
为什么要两步握手？
initialize 返回初始化结果；initialized 是客户端的确认回执。两步保证双方同步进入"就绪"状态，避免客户端在服务端还未准备好时就发业务请求。
为什么本地不需要 HTTP 端口
Node 与本机 Codex 通过进程管道通信；握手完成后，thread/turn 请求沿用同一连接。远端模型调用仍然需要网络。

Thread 与 Turn：往来档案与一次寄送

Thread 是一个往来档案，Turn 是其中一次寄送。单轮 Demo 只新建一个档案、完成一次寄送，但架构已经为多轮做好了准备。

A
thread/start → 拿到 threadId，注入基础指令
↓
B
先注册事件监听（暂存本 Thread 的通知），再发 turn/start
↓
C
RPC 返回 turnId，把缓存里匹配该 turnId 的通知重放
↓
D
等待 turn/completed，提取回答文本
↓
E
finally 块负责释放连接与子进程，失败也要清理
⚠️

事件先到缓存——关键时序细节

turn/start 触发的事件通知可能在 RPC 响应（含 turnId）返回之前就到达 stdio。代码先建立监听缓冲区，收到 turnId 后再回放已缓存的匹配事件，防止漏掉早到的通知。

turnId 不是递增数字
Turn 标识符由 Codex 服务端生成，是唯一字符串而非 1、2、3 这样的计数器。匹配时必须用完整 ID 对比，不能用序号推算。
finally 的责任
无论成功还是异常，finally 块都必须关闭子进程。否则 Codex 进程会在后台残留，占用资源并可能干扰下次启动。

多轮：让会话延续

同一本笔记本写下多页——理解 Thread 与 Turn 的层级、FIFO 缓冲的真实含义，以及 /resume 与长期记忆的本质区别。

全景：从单轮到多轮的三个关键变化

s02 在 s01 基础上做了三处结构性扩展，先看差异再逐步拆解。

变化 1：Thread 跨 Turn 复用
s01：一次执行一个 Thread，结束即关闭。s02：同一 Thread 可以持续接收新 Turn，直到用户退出或执行 /resume 切换。
变化 2：FIFO 输入缓冲
用户可以快速连续输入多条消息，但系统只在上一 Turn 执行完毕后才取下一条。这是输入节奏控制，不是重写模型的推理循环。
变化 3：/resume 会话恢复
通过关键词检索历史 Thread 元数据（名称、开场预览），选定后调用 thread/resume 恢复上下文。恢复的是会话状态，不是"长期记忆注入"。
📌

谁保存历史？

多轮上下文由本机 Codex App Server 原生持久化。Node 端不维护历史消息数组，也不向模型重发历史，这些工作完全由 Codex 内部管理。

FIFO 是排队，不是推理

FIFO 输入缓冲是用户侧的节奏控制机制，不负责模型内部的推理循环。

容易混淆的两个概念
外
FIFO 缓冲 · Node 侧

用户消息入队、出队；决定何时发出下一个 turn/start，不决定模型如何推理。

内
ReAct / 内部 Loop · Codex 侧

处理一个 Turn 内的模型推理与工具调用往返；不管理下一条用户输入的排队。

关键区分

FIFO 决定的是"你的第三条消息要等第二条处理完才能发出"，而不是模型"思考"的步骤数。

从执行机制看，一个 Turn 可包含多次推理与工具往返，由 Codex 的内部循环控制。本阶段的工具能力受限，不能把这种机制理解为已开放外部工具。

结论：FIFO 是外部排队，ReAct 是内部循环，两者分工不同。

为什么需要 FIFO？
如果同时推进多个用户输入，客户端必须处理更复杂的会话状态。本阶段按顺序等待每个 Turn 完成，使输入与结果的对应关系清晰。
超时后恢复原会话
s02 超时后停止连接，提示重启并使用 /resume。任务状态持久化、unconfirmed 与 /continue 队列恢复属于 s03 的服务能力。

resume 恢复会话 vs 记忆注入：两件不同的事

这是最容易被混淆的概念对。用笔记本比喻：resume 是"重新翻开一本旧笔记本继续写"，记忆是"把多本笔记的精华摘录写到新本子的扉页"。

/resume 做了什么
1. 按关键词检索本地会话元数据（名称 / 开场预览）
2. 显示编号列表，用户输入数字选择
3. 发送 thread/resume RPC，Codex 恢复该 Thread 的原生历史
4. 后续 Turn 在此 Thread 上继续，上下文连贯
记忆（Memory）是什么
长期记忆可将有用信息跨会话保留并在后续会话召回；它与重新打开某一个历史会话是不同机制。
s02 不开启跨会话记忆（features.memories=false），/resume 恢复的是历史上下文，不是记忆注入。

唯一装配入口

JSON 文件 agents/writing-agent.json 是配置的唯一可编辑入口，遵循 schemaVersion: "1.0"。未知字段直接拒绝，缺少必填字段也会报错，保证运行状态与配置严格一致。

四个核心概念：装配台的底层语言

读懂配置文件前，先理解这四个词各自指的是什么，以及它们之间的边界。

Schema（模式）
writing-agent.json 的 schemaVersion: "1.0" 声明了当前配置遵循的 Schema 版本。加载器按 Schema 校验所有字段：多余字段拒绝，缺失必填字段报错。Schema 是配置的"格式合同"。
Registry（注册表）
ToolManager 的 build() 方法生成一个带版本号的 registry，其中包含当前版本的工具规格。list 和 call 都受工具白名单约束，Registry 是工具的"电话簿"。
MCP（模型上下文协议）
s03 的工具通过 mcp-server.mjs 提供一个本地 HTTP MCP 服务端，Codex 通过 MCP 协议发现并调用工具。一个 MCP 服务端承载本项目的工具，不是每个工具单独一个服务。
Skills（原生技能）
Skills 是方法指导文本，指导模型"如何做"某类任务（如写作流程）。工具权限由 tools.allow 单独控制——Skill 里提到某工具，不代表该工具自动被授权。两者必须分开配置。
🔑

方法 vs 授权：最重要的边界

Skills 告诉模型怎么做，tools.allow 决定模型能做什么。即使 Skill 里描述了"调用 write_file 保存结果"，如果 allow 列表里没有 write_file，模型调用时仍会被拒绝。

描述符版本机制与 Workspace 边界

配置变更如何被检测？文件操作的边界在哪里？这两个问题是排障时最常碰到的。

1
启动时生成描述符
每次服务启动，系统生成 Agent 描述符，写入 .data/agent-descriptors/，包含角色哈希、Skill 版本、工具版本。
2
Thread 绑定描述符版本
新建 Thread 时，其描述符版本写入 .data/thread-agents.json。恢复旧 Thread 时，先比对当前描述符哈希与记录值是否一致。
3
不匹配则提示 /new
配置、角色或 Skill 文件变更后先重启服务；如果新描述符与旧会话绑定不同，系统拒绝恢复并提示用户执行 /new 新建会话，不自动迁移旧 Thread。
4
文件权限边界
文件服务（files.mjs）自身执行权限边界，不依赖 Codex cwd 约束。工具快照工厂注入文件服务，无跨快照引用，防止历史快照影响当前操作。

想象银行转账：从 A 账户扣钱和向 B 账户加钱必须同时成功或同时失败，不能只做一半。 s04 把「写任务」和「写调度出口」绑进同一个 PG 事务——服务崩溃时，账本要么两条都有，要么两条都没有，不会出现任务存在但调度出口丢失的情况。

Redis 提醒铃：Set 唤醒，不是任务队列

Redis 在这里扮演的是"门铃"，而不是"信箱"。有人按铃（sAdd），调度器就去 PG 账本里按顺序领取；铃声本身不携带任务详情，也不保证顺序。 任务的权威顺序和状态，永远在 PG。

真实源码 · 9 行

第 1–2 行：从 PG 取待投递记录，并逐条处理；数据库失败会中断，Redis 失败只延迟派发。

第 3–4 行：sAdd 只放入 Thread ID；Set 去重仍留在集合中的 ID，不代表任务只执行一次。

第 5–8 行：Redis 失败就标记不健康并退出；尚未确认的 outbox 记录可在后续补投。

第 9 行：Redis 写入成功后，才确认本条调度出口已投递。

✅
Redis 负责
存 Thread ID Set；低延迟唤醒（200 ms 轮询）；sAdd / sPop 操作。
🚫
Redis 不负责
不存任务 ID 队列；不存任务详情；不保证顺序；不替代 PG 做业务状态存储；不存向量数据。
🛡️
Redis 失联时
outbox 记录留存在 PG，调度器健康标记置 false，下次恢复后可补投。任务不丢，只是延迟。
🔑 常见误区：Redis Set 不是任务队列（任务队列存的是任务详情、有顺序保证）。这里 Set 只是"有哪些 Thread 需要被调度器看一眼"的信号，PG 才是决定"领哪条任务"的权威。

不可变 Blob：内容寻址与来源追踪

单机单 owner、单 Agent 配置，支持多 Thread；并非多 Agent 编排。s04 使用数据库 agent_s04（schema v1），s05 使用 agent_s05（schema v2），PG 与 Redis 均必需。两套 Compose 绑定相同的 5432/6379 端口，不可同时启动；可共享一组依赖并使用不同数据库。

sha256 是内容指纹，正文按指纹命名保存。内容改动会生成新 blob，已登记版本不被覆盖；这不等于承诺永久保留。 这让系统能追踪“摘要声明引用的是 report.md 哪个版本”；读取或校验发现原文变化后，依赖链会传播失效。

🔒
create-only，不覆盖
write_file 只创建新路径，已有路径会被拒绝，即使内容相同。底层 blob 可按内容指纹复用；这是不同层次的规则。
📂
路径格式
.data/files/objects/<sha256>.txt——无子目录，所有版本平铺在同一目录。.data/codex/ 是 Codex 原生存储，由 Codex 管理，主进程不读写。
🔗
来源声明 vs 语义证明
dependencies 表记录版本依赖，source_versions 声明来源。这是声明，不证明模型语义引用完全——AI 可能引用了未声明的内容。
⚠️
跨存储非原子
blob 文件写入与 PG 写 resource_versions 之间没有跨存储事务保证。PG 内部操作是原子的；跨文件系统与数据库则不是。

03 层：通用门禁——谁能调哪个工具

门禁是同进程模块，不是网络服务。Codex 每次工具调用都经由 RPC envelope 进入此处，身份来自服务端签发的任务上下文，不依赖模型自称。权限判定按以下四关依次过滤，任意一关不过即返回 FORBIDDEN。

关卡 检查内容 来源
① 上下文有效 任务仍运行中、上下文未被 abort 服务端 AbortController
② 工具白名单 工具名在 Agent 配置声明的允许列表中 agents/*.json 声明
③ 资源所有权 目标资源属于当前任务的 data.scope 服务端签发，非模型自称
④ KB 挂载 + action knowledge[] 中挂载且 actions 包含当前操作；maintain 任务才能写 Wiki Agent 定义 + 任务上下文

  mount(kbId, action = 'read') {
    const context = this.current();
    const mount = (this.agent.definition.agent.knowledge || []).find(m => m.kbId === kbId);
    if (!mount || !mount.actions.includes(action)) denied();
    if (action !== 'read' && context.kind === 'task' && context.maintenanceKb !== kbId) denied();

第 3–4 行：在 Agent 挂载配置中找这个 KB；缺挂载或缺 action 都拒绝。

04 层：三类任务——Chat、Maintain、Index 各做什么

理解这三类任务是排查知识问题的关键。普通 chat 与 maintain 任务通过 Codex 执行，任务记录存于 tasks 表；index 任务由 KnowledgeWorker 执行，任务记录存于 knowledge_jobs 表，并通过独立的 Redis key 唤醒。

💬
普通对话 task
输入：用户消息
上下文：kind: 'task'，maintenanceKb: null
可用 KB 工具：kb_list、kb_read、kb_search（read action）
禁止：kb_submit_revision（写 Wiki）
存储：写 tasks + outbox 同事务，Redis 唤醒
🔧
maintain（仍为普通 task）
输入：npm run knowledge -- maintain <kbId> <提示>
上下文：kind: 'task'，maintenanceKb: <kbId>
额外权限：kb_submit_revision（需 update action）
输出：写 wiki_pages / wiki_versions，current_version 原子切换
注意：存于 tasks 表，不是 knowledge_jobs
🗂️
index（knowledge_jobs）
输入：npm run knowledge -- index <kbId>
执行者：KnowledgeWorker（不是 Codex）
输出：staging Chroma collection + BM25 JSON；两边就绪后 PG 切 index_revision
存储：knowledge_jobs 表，Redis 独立 key 唤醒
注意：这是独立的 knowledge_jobs，不在 tasks 表

RAG 索引：从 Wiki 到向量检索的切换路径

RAG 是可选层，Chroma 是可选依赖；未启用 RAG 时可使用 wiki 模式。切换到 RAG 必须走完以下路径——不能热切换，不能在运行时自动生效。

①
配置并重启
在 .env 添加 CHROMA_URL、EMBEDDING_* 变量，docker compose --profile rag up -d chroma，重启服务。配置变化后必须重启，运行中不热读。
②
发 index 任务
npm run knowledge -- index general 写入 knowledge_jobs 表，Redis 独立 key 唤醒 KnowledgeWorker（不是 Codex）。Worker 构建 staging Chroma collection + BM25 JSON 文件。
③
两边就绪后切指针
Chroma staging collection 与 BM25 文件均核验来源后，PG 更新 index_revision。RRF 60 融合双路结果，无 rerank，无查询失败 fallback。
④
Agent 配置改 rag + 重启
将 agents/writing-agent.json 的 mode 改为 "rag"，停止并重启服务，新建 Thread 才生效。旧 Thread 历史不可撤回，旧 Thread 中读到的知识无法移除。
已生效的 RAG 不兼容时（如 embedding 维度变化）服务拒绝启动，需重建索引。崩溃中的 building/running 状态重启后恢复为 failed，清理 staging collection 与 BM25 文件，失败时可能留孤儿，需运维核对；旧 ready 索引保留，不会无限自动重试。
首次请求 rag 但索引未 ready 时，挂载显示 pending、effectiveMode=wiki。已生效 rag 遇到运行错误不会 fallback 到 wiki；RAG 索引读取原始资料，Wiki 模式搜索已生效的 Wiki 正文（最多 200 页），不是两种搜索混用。

本轮新增 Web 外部客户端，s05 与当前项目接入受控上传，s01–s04 保留各自的能力边界。受控原文导入采用 operator 身份，仅支持 md/txt、单文件 ≤256 KiB，且只创建、不覆盖。Wiki 页面列表通过 GET /knowledge/pages 获取，读取时仍校验来源；教学页默认不连接服务，也不运行模型。

应用情景测验

三道场景题，测试你能否用所学定位真实问题、指导 AI 程序员。每道题都有针对各错误选项的解释。

场景一：你让 Agent 在普通对话中整理一篇 Wiki 页面，但服务端返回 FORBIDDEN，模型说"无权限"。你应该怎么告诉 AI 程序员这是为什么？

场景二：你已经成功运行了 npm run knowledge -- index general，job 状态显示 state: completed。你让当前 Thread 继续调用 kb_search，结果看起来还是 wiki 模式的文本匹配，没有向量排名。最可能的原因是什么？

场景三：Codex 调用 kb_submit_revision 时返回 VERSION_CONFLICT。你应该向 AI 程序员解释，这个错误意味着什么，以及正确的处理方式是什么？
