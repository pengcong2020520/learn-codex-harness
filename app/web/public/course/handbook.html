全景：一次请求怎样走完

先分清用户、我们的程序、Codex 和模型四个角色，再沿五步流程检查一轮问答。

📌

关键认知

Node.js 不直接调用模型 HTTP 接口。它是编排客户端，Codex 才是真正与远端模型通信的执行引擎。两者通过 stdio 连接。

邮局比喻：initialize → initialized

把这套通信想象成一个邮局系统：Node 是寄件人，Codex 是邮局，模型服务是收件目的地。寄信前必须先"在柜台登记开户"——这就是协议握手。

1
spawn 启动子进程
Node 调用 child_process.spawn，把 Codex App Server 作为子进程拉起。此刻"邮局开门"，但还没有任何账户。
2
发送 initialize 请求
Node 通过 JSON-RPC 2.0 发送 initialize 方法。Codex 返回初始化响应，客户端等待这一步成功。
3
发送 initialized 通知
Node 再发一条单向通知 initialized（无需回复），告知 Codex"我已收到你的初始化响应，正式开始"。握手完成。
为什么要两步握手？
initialize 返回初始化结果；initialized 是客户端的确认回执。两步保证双方同步进入"就绪"状态，避免客户端在服务端还未准备好时就发业务请求。
为什么本地不需要 HTTP 端口
Node 与本机 Codex 通过进程管道通信；握手完成后，thread/turn 请求沿用同一连接。远端模型调用仍然需要网络。

Thread 与 Turn：往来档案与一次寄送

Thread 是一个往来档案，Turn 是其中一次寄送。单轮 Demo 只新建一个档案、完成一次寄送，但架构已经为多轮做好了准备。

⚠️

事件先到缓存——关键时序细节

turn/start 触发的事件通知可能在 RPC 响应（含 turnId）返回之前就到达 stdio。代码先建立监听缓冲区，收到 turnId 后再回放已缓存的匹配事件，防止漏掉早到的通知。

turnId 不是递增数字
Turn 标识符由 Codex 服务端生成，是唯一字符串而非 1、2、3 这样的计数器。匹配时必须用完整 ID 对比，不能用序号推算。
finally 的责任
无论成功还是异常，finally 块都必须关闭子进程。否则 Codex 进程会在后台残留，占用资源并可能干扰下次启动。

FIFO 是排队，不是推理

FIFO 输入缓冲是用户侧的节奏控制机制，不负责模型内部的推理循环。

容易混淆的两个概念
外
FIFO 缓冲 · Node 侧

用户消息入队、出队；决定何时发出下一个 turn/start，不决定模型如何推理。

内
ReAct / 内部 Loop · Codex 侧

处理一个 Turn 内的模型推理与工具调用往返；不管理下一条用户输入的排队。

关键区分

FIFO 决定的是"你的第三条消息要等第二条处理完才能发出"，而不是模型"思考"的步骤数。

从执行机制看，一个 Turn 可包含多次推理与工具往返，由 Codex 的内部循环控制。本阶段的工具能力受限，不能把这种机制理解为已开放外部工具。

结论：FIFO 是外部排队，ReAct 是内部循环，两者分工不同。

为什么需要 FIFO？
如果同时推进多个用户输入，客户端必须处理更复杂的会话状态。本阶段按顺序等待每个 Turn 完成，使输入与结果的对应关系清晰。
超时后恢复原会话
s02 超时后停止连接，提示重启并使用 /resume。任务状态持久化、unconfirmed 与 /continue 队列恢复属于 s04 的服务能力。

resume 恢复会话 vs 记忆注入：两件不同的事

这是最容易被混淆的概念对。用笔记本比喻：resume 是"重新翻开一本旧笔记本继续写"，记忆是"把多本笔记的精华摘录写到新本子的扉页"。

/resume 做了什么
1. 按关键词检索本地会话元数据（名称 / 开场预览）
2. 显示编号列表，用户输入数字选择
3. 发送 thread/resume RPC，Codex 恢复该 Thread 的原生历史
4. 后续 Turn 在此 Thread 上继续，上下文连贯
记忆（Memory）是什么
长期记忆可将有用信息跨会话保留并在后续会话召回；它与重新打开某一个历史会话是不同机制。
s02 不开启跨会话记忆（features.memories=false），/resume 恢复的是历史上下文，不是记忆注入。

服务：让 Agent 常驻

这个云端 Agent 还缺一个独立运行的服务端。亲手接通 HTTP 入口，追踪一轮的执行归属，验证客户端离线后的结果与资源收尾。

这个云端 Agent 还缺什么？一个能一直工作的服务端

我们已经能在一个 Thread 里连续对话，也能用 /resume 找回历史。现在请它写一份长回答，回答到一半关掉终端：如果终端程序持有 Codex 子进程，这次执行就会跟着结束。要亲手做一个云端 Agent，先让执行拥有独立于用户窗口的生命周期。

本章要完成的体验很具体：在一个终端启动服务，在另一个终端聊天；关掉聊天窗口，服务继续工作；重新连接同一个 Thread，查看这一轮的结果。先在本机验证这条链路，服务默认只监听 127.0.0.1:4313，本章不提供公网部署或多用户授权。

服务端持有什么
读取 .env 中的模型配置，启动 Codex App Server，持有会话与执行中的 Turn。服务端接收 Codex 通知，即使此刻没有客户端查看，也会更新状态。
客户端持有什么
读取 .data/connection.json 中的地址与连接令牌，保存当前选中的 Thread id，通过 HTTP 提交和查看。客户端不读取 .env，不启动 Codex，不需要模型 API Key。

Thread 是会话，Turn 是其中的一轮。服务端进程、客户端进程、Codex 子进程则是运行边界。把这三种概念分清，就能回答“关掉哪一个进程会停止哪一部分工作”。

📌

先定验收条件

客户端退出只停止提交与查看，已交给服务端的一轮继续执行。停止服务端会结束 Codex 子进程；原生历史保留，但 s03 没有持久任务记录来核对中途执行。

接好入口：HTTP 请求先过连接校验

给 Agent 一个入口，并不意味着把模型密钥交给每个客户端。服务启动时生成随机连接令牌，写入权限为 0600 的连接文件。客户端每次发送 Authorization: Bearer <令牌>；这个令牌只用于访问 Agent 服务，与远端模型的 API Key 分别管理。

HTTP 负责外层请求；服务端通过 JSON-RPC 调用 Codex。读源码时先看谁在和谁说话，再看同样名为“请求”的操作实际跨过了哪条边界。

事件与消息：让任务有序执行

这个云端 Agent 还缺可靠的连续提交与状态同步。亲手串起任务记录、按会话调度和 SSE，遇到不确定执行时保留证据、暂停核对。

这个云端 Agent 还缺什么？能保存每条输入的任务记录

现在服务端能独立完成一轮了。试着在回答过程中再输入两条，然后关闭客户端：已经发出的那一轮可以继续，仍等在客户端的输入却没有服务端记录。一个能长期工作的云端 Agent，还要接住用户连续交来的事情，并告诉用户每一条走到了哪里。

本章的验收场景是：连续提交三条普通消息，三条都被服务端接收；关闭客户端后，服务端依次完成它们；回来时能看到队列和会话状态。如果执行结果拿不准，就停下来让用户核对，避免把同一件事做两遍。

messages：决定执行节奏
接收消息、按 Thread 排队、发 turn/start，处理追加、超时、暂停与继续。它决定哪条输入现在可以执行，不代替 Codex 内部的推理与工具循环。
data：保存任务事实
将消息和暂停状态写入 .data/messages.json，每次更新整体原子替换文件。进程退出后记录还在，重启时可据此判断哪些任务需要核对。
events：把变化交给订阅者
事件中心分发会话与队列状态，经 HTTP 的 SSE 连接交给对应 Thread 的客户端。它不负责启动下一轮，也不调用模型。

区分三个 ID：threadId 标识会话，clientMessageId 标识用户这次提交，turnId 标识 Codex 执行轮次。任务可以在还没有 turnId 时就处于 queued；追加也可能与已有任务关联到同一轮，三个 ID 不能相互替代。

实现边界

服务默认监听 127.0.0.1:4319，仍是本机单用户、单进程队列。同目录只运行一个服务；每个会话最多 100 条 queued 消息。本章验证可靠提交与状态同步，不提供多机器调度。

snapshot / session / queue
snapshot 是每次连接的首条完整状态，含会话与队列；session 表示会话变化，queue 表示任务状态、暂停或继续。客户端用这些内容更新显示。
fatal / shutdown
fatal 提示执行连接失效、服务停止调度；shutdown 表示服务正常关闭。看到这类事件要核对服务与任务状态，不能据此认定所有任务已完成。

客户端断线后约一秒再尝试连接，每次都先获取快照。事件序号用于排查问题，本章不按 Last-Event-ID 重放历史事件。快照帮助客户端重新看到当前状态，不承诺补齐离线期间每一条事件；订阅过程也不会替用户再提交一次消息。

普通事件写入积压超过 1 MiB 时连接会被断开，再由客户端重连取快照。快照之后的事件仍是状态更新，渲染时应以事件内容更新视图，不能把事件到达次数当作执行次数。

四个核心概念：装配台的底层语言

读懂配置文件前，先理解这四个词各自指的是什么，以及它们之间的边界。

Schema（模式）
writing-agent.json 的 schemaVersion: "1.0" 声明了当前配置遵循的 Schema 版本。加载器按 Schema 校验所有字段：多余字段拒绝，缺失必填字段报错。Schema 是配置的"格式合同"。
Registry（注册表）
ToolManager 的 build() 方法生成一个带版本号的 registry，其中包含当前版本的工具规格。list 和 call 都受工具白名单约束，Registry 是工具的"电话簿"。
MCP（模型上下文协议）
s07 的工具通过 mcp-server.mjs 提供一个本地 HTTP MCP 服务端，Codex 通过 MCP 协议发现并调用工具。一个 MCP 服务端承载本项目的工具，不是每个工具单独一个服务。
Skills（原生技能）
Skills 是方法指导文本，指导模型"如何做"某类任务（如写作流程）。工具权限由 tools.allow 单独控制——Skill 里提到某工具，不代表该工具自动被授权。两者必须分开配置。
🔑

方法 vs 授权：最重要的边界

Skills 告诉模型怎么做，tools.allow 决定模型能做什么。即使 Skill 里描述了"调用 write_file 保存结果"，如果 allow 列表里没有 write_file，模型调用时仍会被拒绝。

Redis 在这里扮演的是"门铃"，而不是"信箱"。有人按铃（sAdd），调度器就去 PG 账本里按顺序领取；铃声本身不携带任务详情，也不保证顺序。 任务的权威顺序和状态，永远在 PG。

🚫

Redis 失联时

不可变 Blob：内容寻址与来源追踪

单机单 owner、单 Agent 配置，支持多 Thread；并非多 Agent 编排。s08 使用数据库 agent_s08（schema v1），s09 使用 agent_s09（schema v2），PG 与 Redis 均必需。两套 Compose 绑定相同的 5432/6379 端口，不可同时启动；可共享一组依赖并使用不同数据库。

以下练习在 stages/s09-knowledge-layer 目录进行。准备知识库时先设置 AGENT_MEMORY_ENABLED=false，执行 npm run knowledge:init，把原文放到 workspace/inputs/general/；维护结束后再读取实际页面。实际运行还需先完成 npm ci、本地环境配置、docker compose up -d postgres redis、npm run data:migrate、npm run server。完整步骤见 s09 实践环境。

本轮新增 Web 外部客户端，s09 与当前项目接入受控上传，s01–s08 保留各自的能力边界。受控原文导入采用 operator 身份，仅支持 md/txt、单文件 ≤256 KiB，且只创建、不覆盖。Wiki 页面列表通过 GET /knowledge/pages 获取，读取时仍校验来源；教学页默认不连接服务，也不运行模型。

单机单 owner、单 Agent 配置，支持多 Thread；并非多 Agent 编排。s08 使用数据库 agent_s08（schema v1），s09 使用 agent_s09（schema v2），PG 与 Redis 均必需。两套 Compose 绑定相同的 5432/6379 端口，不可同时启动；可共享一组依赖并使用不同数据库。

应用情景测验

三道场景题，测试你能否用所学定位真实问题、指导 AI 程序员。每道题都有针对各错误选项的解释。

场景一：你让 Agent 在普通对话中整理一篇 Wiki 页面，但服务端返回 FORBIDDEN，模型说"无权限"。你应该怎么告诉 AI 程序员这是为什么？

场景二：你已经成功运行了 npm run knowledge -- index general，job 状态显示 state: completed。你让当前 Thread 继续调用 kb_search，结果看起来还是 wiki 模式的文本匹配，没有向量排名。最可能的原因是什么？

场景三：Codex 调用 kb_submit_revision 时返回 VERSION_CONFLICT。你应该向 AI 程序员解释，这个错误意味着什么，以及正确的处理方式是什么？
