## 设计原理

Demo 4 解决了业务数据的可靠存储与调度。Demo 5 解决两个新问题：

**1. 知识组织**：让 Agent 基于本机原始资料维护结构化知识（Wiki），并可选建立语义索引（RAG），而不是直接读取散落文件。

**2. 权限一致性**：工具调用、知识访问、文件读写的权限判定散落各模块，Demo 5 在同进程内以统一门禁拦截所有工具路径。

**设计要点：**

- **正文版本不可变**：工作区原文可以由操作者更新；登记的原文快照与 Wiki 正文以不可变 blob 保存，版本可追踪。
- **Wiki 基于原文**：Codex 阅读原始资料后，通过 `kb_submit_revision` 工具写 Wiki；Wiki 不能引用 Wiki 自身，仅引用当前有效原文版本（直接来源）。
- **门禁统一**：所有工具（文件、知识）通过同一 `server/modules/permissions/index.mjs` 判定，权限来自服务端签发的任务上下文，不依赖模型自称身份。
- **传输升级**：Demo 5 真实数据主流程使用 Codex 原生 **dynamicTools**（实验性 `item/tool/call`），通过 native RPC envelope 绑定任务上下文并进入统一门禁；MCP 实现保留供兼容测试，生产配置不向 Codex 暴露 MCP 入口（门禁模式下不启 MCP listener）。

**关键约束：**

- 单机单 owner，多 Thread；无登录、无共享 KB、无多主机。
- 挂 KB 须 `AGENT_MEMORY_ENABLED=false`；原生记忆禁用，原生会话历史继续保留；权限收窄后需新建 Thread，旧历史不可撤回。
- Chroma 可选；RAG 需先配置后重启构建，不热切换；已生效 rag 不兼容则拒绝启动，运行错误不 fallback 至 wiki。
- 使用数据库 `agent_demo5`（schema v2）；两个 Demo 的 Compose 都绑定 5432/6379，不能同时启动两套依赖；可共用一组 PG/Redis 并使用不同数据库。

## 架构改进

架构图分五层（图左）+ Codex 原生运行时（图右）。以下逐层说明职责。

### 01 交互入口

**为何存在**：统一对外接口，涵盖普通 chat 和 knowledge CLI，HTTP 知识与资源操作同样使用服务端签发的 operator 上下文进入 03 门禁。

| 方向 | 内容 |
|------|------|
| 输入 | HTTP POST `/messages`；POST / GET `/sessions`；knowledge CLI 命令 |
| 输出 | SSE token 流；任务 ID；知识 CLI 响应 |
| 代码 | [HTTP 路由](server/modules/http/index.mjs)、[knowledge CLI](scripts/knowledge.mjs) |

与 Demo 4 相比：新增 knowledge CLI 子命令入口，HTTP 也经过门禁（详见 03 层）。

### 02 Agent 装配与任务调度

**为何存在**：将 Agent 配置转化为运行态，并通过 dynamicTools 将工具调用路由至同进程门禁，而非直接暴露 MCP。

| 方向 | 内容 |
|------|------|
| 输入 | `agents/*.json`（schemaVersion 1.0/1.1）；KB 挂载配置 |
| 输出 | 写 PG `agent_versions`；task + outbox 同事务；Redis 唤醒；**dynamicTools RPC envelope → 03 门禁** |
| 代码 | [Agent 装配](server/modules/agents/index.mjs)、[调度](server/modules/messages/index.mjs)、[Thread 与动态工具注册](server/modules/sessions/index.mjs)、[回调绑定](server/main.mjs) |

`schemaVersion 1.1` 新增 `agent.knowledge[]` 字段声明 KB 挂载。以下仅展示知识相关配置片段，合并到已有 Agent 定义：

```json
{
  "schemaVersion": "1.1",
  "agent": {
    "knowledge": [
      { "kbId": "general", "mode": "wiki", "actions": ["read", "update", "index"] }
    ]
  },
  "bindings": {
    "knowledgeBases": {
      "general": { "sourceRoot": "inputs/general", "wikiRoot": "research/general/wiki" }
    }
  }
}
```

Codex 每次工具调用触发 `item/tool/call` → 02 层回调 → 03 层门禁判定 → 04 层执行。**不是自造 LLM loop，不给每个工具起 MCP 进程。**

### 03 通用门禁

**为何存在**：集中判定工具名单、资源所有权、KB 挂载权限和任务范围，以 fail-closed 原则保护所有工具路径。

| 方向 | 内容 |
|------|------|
| 输入 | 来自 02 层的工具调用请求 + 任务上下文 |
| 输出 | 放行或 `FORBIDDEN` 错误；上下文在任务结束后自动撤销 |
| 代码 | [PermissionGate](server/modules/permissions/index.mjs) |

先校验上下文由服务端签发且任务仍有效；工具调用再检查以下条件（涉及的目标全部满足）：

1. **工具名在白名单中** — Agent 配置声明的允许工具。
2. **资源所有权** — 来自 `data.scope`，非模型自称。
3. **KB 挂载 + actions 合法** — `knowledge[]` 中挂载且 actions 包含当前操作。
4. **任务范围允许** — 服务端签发的 task 上下文；任务结束后撤销，旧上下文不继承。

其他限制：`research/<kbId>/wiki` 路径上的普通 `read_file/write_file` 被拒绝，必须用 `kb_*` 工具；`shell/apply_patch/subagents` 禁用；一般对话不能执行 `kb_submit_revision`（需 `maintain` 任务上下文）；Agent 配置变化 fail-closed。

### 04 知识与资源服务

**为何存在**：实现 Wiki 并发控制、可选 RAG 索引构建，并复用资源服务管理原文版本与 Wiki 不可变正文。

| 方向 | 内容 |
|------|------|
| 输入 | `kb_*` 工具调用（经 03 层放行）；RAG 索引任务（`knowledge_jobs`） |
| 输出 | Wiki 页面内容（含 versionId）；搜索结果；RAG 索引 revision；PG 写入 |
| 代码 | [KnowledgeService](server/modules/knowledge/index.mjs)、[RagIndex](server/modules/knowledge/rag.mjs)、[KnowledgeWorker](server/modules/knowledge/worker.mjs) |

**知识工具集：**

| 工具 | 说明 |
|------|------|
| `kb_list` | 列已挂载 KB、模式、权限、索引版本；**不列页面** |
| `kb_read` | 读 Wiki 页面，返回正文 + `versionId`（用于乐观锁） |
| `kb_search` | Wiki 模式：有界文本搜索（≤200 页）；RAG 模式：Chroma+BM25 RRF 60，limit 1–20；无混合，无查询失败 fallback |
| `kb_submit_revision` | 提交 Wiki 修订；需 `maintain` 任务上下文；`expectedVersion` 乐观锁；新建传 `null`，更新传 `kb_read` 返回的 versionId；来源 1–50 条当前有效原文，不支持 wiki 引用 wiki；冲突返回 `VERSION_CONFLICT`，来源失效返回 `SOURCE_STALE` |

**Wiki 工作方式**：`knowledge:init` 只建目录、部署 `skills/knowledge/SKILL.md`，**不生成知识**。`maintain` 命令发普通任务，Codex 读原文后调用 `kb_submit_revision` 写 Wiki；提交成功自动生效，无手工 publish。生效 Wiki 由 PG 的 `wiki_pages.current_version` 指向正文版本，不直接扫描 `research/<kbId>/wiki` 目录。RAG 索引基于原始文件。

**RAG 索引生命周期**：

- `server/modules/knowledge/worker.mjs` 调用 RagIndex 构建 staging Chroma collection + BM25 文件（`.data/knowledge/bm25/<revision>.json`），两边完成并核验来源后，PG 切 `index_revision`。
- 崩溃中的 `building/running` 状态：重启时恢复为 `failed`，清理 staging；清理失败可能留孤儿，需运维核对。旧 `ready` 版本保留，无自动无限重试。
- 构建成功后须将 `agents/*.json` 的 `mode` 改为 `rag`，停止服务重启后新建 Thread 生效；**不热切换**。

### 05 数据与索引

**为何存在**：在 Demo 4 schema v1 基础上，以顺序迁移（`002-knowledge.sql`）扩展知识层所需表。

| 子系统 | 用途 | 关键约束 |
|--------|------|----------|
| **PostgreSQL** `agent_demo5` | v1 + 知识相关表 | schema v2；顺序迁移并验证旧 checksum |
| **Redis** | Thread ID Set + knowledge_jobs 独立 key | 两个独立唤醒路径 |
| **文件** `.data/files/objects/` | 资源与 Wiki immutable blob | 无 hash 子目录 |
| **BM25** `.data/knowledge/bm25/` | 持久 BM25 索引文件 | 每 revision 一个 JSON 文件 |
| **Chroma**（可选） | 向量索引，独立服务 | chunkId/indexRevision 与 BM25 共享；需独立 embedding 服务 |

<details>
<summary>schema v2 新增表</summary>

| 表 | 用途 |
|----|------|
| `knowledge_bases` | KB 归属、路径、生效索引指针 |
| `knowledge_mounts` | Agent 与 KB 的期望/生效模式；actions 来自 Agent 配置 |
| `wiki_pages` | Wiki 页面（slug、`current_version` 指针） |
| `wiki_versions` | Wiki 不可变版本元数据；正文另存 blob 文件 |
| `knowledge_indexes` | RAG 索引版本元数据 |
| `knowledge_jobs` | 索引构建任务（独立 PG 持久任务，Redis 独立 key 唤醒） |

`tasks` 表新增 `knowledge` 字段记录知识任务类型。Wiki 维护使用普通 `tasks`。

## 限制说明

| 限制项 | 说明 |
|--------|------|
| 单机单 owner | 无多账户、无登录、无共享 KB、无多主机 |
| 端口独占 | 两套 Compose 不能同时绑定 5432/6379；可共用依赖、分数据库 |
| 原生记忆 | 挂 KB 须 `AGENT_MEMORY_ENABLED=false`；旧 Thread 历史不可撤回，从新 Thread 生效 |
| Wiki 非自动 | 无后台 LLM Wiki 工人；须 `maintain` 发任务，Codex 主动调用 `kb_submit_revision` |
| RAG 可选 | 不配置 Chroma 则仅 Wiki；首次 rag 未 ready 显示 pending + effectiveMode=wiki；不热切换 |
| rag 不兼容拒绝启动 | embedding 维度变化等情况下拒绝启动，需重建索引 |
| 无 rerank | BM25 + Chroma RRF 融合（常数 60），无 rerank |
| 孤儿清理 | 崩溃后 staging collection / BM25 文件可能保留，需运维核对 |
| 跨存储非原子 | blob 写文件 + PG 切版本指针非原子；PG 内操作原子 |
| wiki 不引用 wiki | Wiki 来源只能是当前有效原文版本，1–50 条；不支持嵌套引用 |
| 历史不可撤回 | 收窄权限不能移除旧 Thread 中已读到的知识；需新建 Thread |
| 语义质量未验收 | 回归测试的 embedding 使用固定模拟向量，未证明真实语义质量 |

    if (!run || run.turnId !== turnId || run.controller.signal.aborted) denied();
    return run.context;
  }
  end(threadId, turnId) {
    const run = this.runs.get(threadId);
    if (run && (!turnId || run.turnId === turnId)) {
      run.controller.abort(new Error('任务已结束。')); this.runs.delete(threadId);
    }
  }
  close() { for (const id of this.runs.keys()) this.end(id); }
  mount(kbId, action = 'read') {
    const context = this.current();
    const mount = (this.agent.definition.agent.knowledge || []).find(m => m.kbId === kbId);
    if (!mount || !mount.actions.includes(action)) denied();
    if (action !== 'read' && context.kind === 'task' && context.maintenanceKb !== kbId) denied();
