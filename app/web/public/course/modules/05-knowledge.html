03 层：通用门禁——谁能调哪个工具

门禁是同进程模块，不是网络服务。Codex 每次工具调用都经由 RPC envelope 进入此处，身份来自服务端签发的任务上下文，不依赖模型自称。权限判定按以下四关依次过滤，任意一关不过即返回 FORBIDDEN。

关卡 检查内容 来源
① 上下文有效 任务仍运行中、上下文未被 abort 服务端 AbortController
② 工具白名单 工具名在 Agent 配置声明的允许列表中 agents/*.json 声明
③ 资源所有权 目标资源属于当前任务的 data.scope 服务端签发，非模型自称
④ KB 挂载 + action knowledge[] 中挂载且 actions 包含当前操作；maintain 任务才能写 Wiki Agent 定义 + 任务上下文

来自 server/modules/permissions/index.mjs 的真实代码展示 mount() 如何检查挂载、操作授权与任务维护范围；上下文在任务开始时签发，结束后撤销。

源码：stages/s05-knowledge-layer/server/modules/permissions/index.mjs:51–57

真实源码 · 7 行
  mount(kbId, action = 'read') {
    const context = this.current();
    const mount = (this.agent.definition.agent.knowledge || []).find(m => m.kbId === kbId);
    if (!mount || !mount.actions.includes(action)) denied();
    if (action !== 'read' && context.kind === 'task' && context.maintenanceKb !== kbId) denied();
    return mount;
  }

第 1–2 行：取得服务端签发且仍有效的当前上下文。

第 3–4 行：在 Agent 挂载配置中找这个 KB；缺挂载或缺 action 都拒绝。

第 5 行：task 的非 read 操作，还要 maintenanceKb 与目标库一致。普通对话没有维护范围。

第 6–7 行：校验通过才返回挂载配置；maintain 也仍需对应 action 授权。

门禁模式禁用 shell、apply_patch、subagents；Agent 配置变化时按 fail-closed 拒绝。MCP 仅保留兼容测试实现，主流程不启动 MCP listener；Skill 只指导操作方法，不授予权限。
普通对话 task 的 maintenanceKb 为 null，因此 kb_submit_revision（写 Wiki）永远被拒绝。research/<kbId>/wiki 路径上的 read_file/write_file 同样被门禁拒绝，必须用 kb_* 工具经 04 层操作。

04 层：三类任务——Chat、Maintain、Index 各做什么

理解这三类任务是排查知识问题的关键。普通 chat 与 maintain 任务通过 Codex 执行，任务记录存于 tasks 表；index 任务由 KnowledgeWorker 执行，任务记录存于 knowledge_jobs 表，并通过独立的 Redis key 唤醒。

💬
普通对话 task
输入：用户消息
上下文：kind: 'task'，maintenanceKb: null
可用 KB 工具：kb_list、kb_read、kb_search（read action）
禁止：kb_submit_revision（写 Wiki）
存储：写 tasks + outbox 同事务，Redis 唤醒
🔧
maintain（仍为普通 task）
输入：npm run knowledge -- maintain <kbId> <提示>
上下文：kind: 'task'，maintenanceKb: <kbId>
额外权限：kb_submit_revision（需 update action）
输出：写 wiki_pages / wiki_versions，current_version 原子切换
注意：存于 tasks 表，不是 knowledge_jobs
🗂️
index（knowledge_jobs）
输入：npm run knowledge -- index <kbId>
执行者：KnowledgeWorker（不是 Codex）
输出：staging Chroma collection + BM25 JSON；两边就绪后 PG 切 index_revision
存储：knowledge_jobs 表，Redis 独立 key 唤醒
注意：这是独立的 knowledge_jobs，不在 tasks 表

Wiki 无后台自动工作进程。knowledge:init 只建目录、部署 SKILL.md，不生成任何 Wiki 内容。必须执行 maintain 命令发任务，Codex 读原文后主动调用 kb_submit_revision 才写入 Wiki。

RAG 索引：从 Wiki 到向量检索的切换路径

RAG 是可选层，Chroma 是可选依赖；未启用 RAG 时可使用 wiki 模式。切换到 RAG 必须走完以下路径——不能热切换，不能在运行时自动生效。

①
配置并重启
在 .env 添加 CHROMA_URL、EMBEDDING_* 变量，docker compose --profile rag up -d chroma，重启服务。配置变化后必须重启，运行中不热读。
②
发 index 任务
npm run knowledge -- index general 写入 knowledge_jobs 表，Redis 独立 key 唤醒 KnowledgeWorker（不是 Codex）。Worker 构建 staging Chroma collection + BM25 JSON 文件。
③
两边就绪后切指针
Chroma staging collection 与 BM25 文件均核验来源后，PG 更新 index_revision。RRF 60 融合双路结果，无 rerank，无查询失败 fallback。
④
Agent 配置改 rag + 重启
将 agents/writing-agent.json 的 mode 改为 "rag"，停止并重启服务，新建 Thread 才生效。旧 Thread 历史不可撤回，旧 Thread 中读到的知识无法移除。
已生效的 RAG 不兼容时（如 embedding 维度变化）服务拒绝启动，需重建索引。崩溃中的 building/running 状态重启后恢复为 failed，清理 staging collection 与 BM25 文件，失败时可能留孤儿，需运维核对；旧 ready 索引保留，不会无限自动重试。
首次请求 rag 但索引未 ready 时，挂载显示 pending、effectiveMode=wiki。已生效 rag 遇到运行错误不会 fallback 到 wiki；RAG 索引读取原始资料，Wiki 模式搜索已生效的 Wiki 正文（最多 200 页），不是两种搜索混用。

以下练习在 stages/s05-knowledge-layer 目录进行。准备知识库时先设置 AGENT_MEMORY_ENABLED=false，执行 npm run knowledge:init，把原文放到 workspace/inputs/general/；维护结束后再读取实际页面。实际运行还需先完成 npm ci、本地环境配置、docker compose up -d postgres redis、npm run data:migrate、npm run server。完整步骤见 s05 实践环境。

本轮新增 Web 外部客户端，s05 与当前项目接入受控上传，s01–s04 保留各自的能力边界。受控原文导入采用 operator 身份，仅支持 md/txt、单文件 ≤256 KiB，且只创建、不覆盖。Wiki 页面列表通过 GET /knowledge/pages 获取，读取时仍校验来源；教学页默认不连接服务，也不运行模型。

单机单 owner、单 Agent 配置，支持多 Thread；并非多 Agent 编排。s04 使用数据库 agent_s04（schema v1），s05 使用 agent_s05（schema v2），PG 与 Redis 均必需。两套 Compose 绑定相同的 5432/6379 端口，不可同时启动；可共享一组依赖并使用不同数据库。

限制项说明
单机单 owner无多账户、无共享 KB、无多主机
原生记忆挂 KB 须 AGENT_MEMORY_ENABLED=false；原生记忆关闭后仍保留原生会话历史。收窄权限后需新建 Thread，旧历史不可撤回
RAG 不热切换改配置须重启；embedding 维度变化时拒绝启动
wiki 不引用 wiki来源只能是当前有效原文版本，1–50 条
跨存储非原子blob 写文件 + PG 切指针非原子；PG 内操作原子
无 rerankBM25 + Chroma RRF 融合（常数 60），无后处理重排

应用情景测验

三道场景题，测试你能否用所学定位真实问题、指导 AI 程序员。每道题都有针对各错误选项的解释。

场景一：你让 Agent 在普通对话中整理一篇 Wiki 页面，但服务端返回 FORBIDDEN，模型说"无权限"。你应该怎么告诉 AI 程序员这是为什么？

场景二：你已经成功运行了 npm run knowledge -- index general，job 状态显示 state: completed。你让当前 Thread 继续调用 kb_search，结果看起来还是 wiki 模式的文本匹配，没有向量排名。最可能的原因是什么？

场景三：Codex 调用 kb_submit_revision 时返回 VERSION_CONFLICT。你应该向 AI 程序员解释，这个错误意味着什么，以及正确的处理方式是什么？
