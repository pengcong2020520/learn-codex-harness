部署单元：健康、就绪与可恢复状态

用独立 Compose 交付运行环境，用就绪探测和容量限制守住入口，用固定路径与停服备份保留恢复依据。

交付一个部署单元，明确进程与数据的归属

已有的 Agent 可以组织任务、使用工具和知识、执行 Workflow，并通过模型网关选择模型。让它在服务器上持续工作，还需要回答几件具体的事：运行环境怎样复现，服务什么时候能接任务，退出后由谁重新启动，数据库和原生历史放在哪里，升级失败以后能恢复到什么状态。本章把这些责任收进一套独立部署，不改变 Codex 的推理与工具执行循环。

部署单元 包含 postgres、redis、gateway、agent 四个服务。PostgreSQL 保存业务事实，Redis 承担队列唤醒，Bifrost 承接模型请求，agent 运行既有服务。只有 agent 发布宿主回环端口；客户端使用 SSH 隧道进入。它不加入 app 的共享 stages 容器，也不登记为工作台默认实时目标。

边界本章负责什么仍需保留的依据
Codex管理 Thread、Turn、上下文与工具执行。原生 SQLite / JSONL 历史与固定路径。
Agent 服务判断就绪，限制排队、执行和连接，关闭时保存不确定状态。PostgreSQL 任务记录、执行器与队列状态。
Compose / Docker固定服务版本、依赖健康、挂载与退出重启。镜像、锁文件、卷与宿主目录。
宿主 Bash / systemd开机启动、远程部署、停服备份和恢复。部署版本、成功备份、权限与操作结果。

镜像固定 Node 版本和 digest，按 npm 锁文件安装依赖，使用非 root 的 node 用户。Agent 镜像额外安装 lsof 和 bubblewrap；数据库转储使用正在运行的 postgres 容器，不要求在 Agent 镜像里安装 PostgreSQL 客户端。构建可以配置 NPM_REGISTRY 与 APT_MIRROR，配置改变镜像下载来源，不改变服务的责任。

PostgreSQL 和 Redis 使用命名卷；.data、.runs、workspace 和 backups 使用宿主目录挂载。代码和镜像可以替换，持久状态需要保留。正文、产物与原生历史都不应该因为容器重建而消失。部署脚本不会把镜像当成数据备份，也不会把删除数据卷作为日常停止方式。

固定路径 是恢复契约。CONTAINER_APP_DIR 必须等于宿主部署目录，容器内工作位置保持一致。使用带时间戳的新目录运行下一版代码，看起来便于保留版本，却会改变历史引用的位置。本章在固定位置替换代码与镜像；要转移原生历史，需要连同原路径保持一致，没有实现跨路径历史改写。

密钥保存在权限为 600 的宿主 .env，Compose 按服务列出变量。服务商密钥只交给 gateway；agent 获得访问网关的凭据和自己的数据库配置，通过不含密钥的服务商名称清单判断模型可用范围。生成配置保存环境变量引用，镜像和命令参数不包含密钥正文。实例身份和正文属于恢复数据，服务商密钥则需要另行妥善保管。

每个服务采用 json-file 日志轮转，单文件 10m、保留 3 个。默认内存分别为 PostgreSQL 256m、Redis 128m、gateway 256m、agent 768m，可通过对应的 MEMORY_LIMIT 变量覆盖。这些是容器资源边界，不能替代应用层的任务并发和请求限制。文件产物仍在 workspace；本章没有接入对象存储。

依赖健康决定启动顺序，/ready 判断当前能否接任务

启动顺序解决的是“后续进程什么时候开始”，就绪检查解决的是“现在是否可以工作”。gateway 等待 postgres 健康，agent 等待 postgres、redis 和 gateway 健康。数据库、Redis、网关各有自己的探针，agent 的探针执行 deploy/ready.mjs。下面是 agent 的依赖与 healthcheck 原文。

gateway 的依赖条件是 service_healthy；同一 depends_on 段还包含 postgres 和 redis。

agent 的探针执行 Node 脚本，周期 5 秒、超时 10 秒、最多重试 20 次。

这些条件约束启动时机。依赖在运行途中失效时，Compose 不会持续按依赖图重新排布全部服务。

四个服务都采用 restart: unless-stopped 和 30 秒停止宽限。systemd 负责开机执行 Compose；Docker restart policy 处理进程退出后的重新启动。容器标为 unhealthy 并不等于进程已经退出，也不会仅凭这个标记自动重启。排障时要分别查看进程、健康结果和业务就绪结果，不能把它们当成同一个状态。

/health 只返回 HTTP 进程的存活事实，状态为 alive；/ready 核对数据库、网关、模型目录以及执行相关状态，不能接任务时返回 503。两个接口都返回 version，读取 REVISION，没有文件时为 dev；它们不需要连接令牌，不扣请求额度，也不输出凭据。

源码 · stages/s12-deploy/server/modules/deployment/index.mjs · 第 24–34 行 
export function createReadiness({ config, data, messages, tools, fetcher = fetch, stopping = () => false }) {
  const version = revision(config.root);
  return async () => {
    const checks = { database: false, gateway: false, models: Boolean(config.registry && config.launch.router && config.launch.catalog?.models?.length) };
    try { await data.pool.query({ text: 'SELECT 1', query_timeout: 3000 }); checks.database = true; } catch { /* No credentials in responses. */ }
    try {
      const url = new URL('/health', config.media.endpoint.baseUrl);
      checks.gateway = (await fetcher(url, { signal: AbortSignal.timeout(3000) })).ok;
    } catch { /* Gateway health does not call a model. */ }
    const ready = Object.values(checks).every(Boolean) && !stopping() && !messages.failure && !messages.closed && !messages.stopping && !tools?.broken && data.queue?.healthy !== false;
    return { status: ready ? 'ready' : 'not-ready', version, checks };

📌

不要把一次健康检查扩大成服务质量承诺

Compose 的依赖健康是启动条件；/ready 是当前运行状态检查；真实模型调用还要验证鉴权、额度和响应。三种证据分别保留，故障时才能知道是哪一层不满足条件。

接多少、做多少、连多少：四个容量边界

服务长期运行后，一次请求所占的资源并不一样。普通 HTTP 请求可能很快结束；SSE 可以保持连接；数据库中的 queued 任务等待执行；一个运行中的模型轮次可能持续较久。只限制请求频率不能限制活动轮次数，只限制轮次又挡不住连接耗尽。因此部署配置分别给出四个上限。

每个配置值先经过正整数校验；非法值会在启动配置阶段报错。

maxConcurrentTurns 限制新轮次派发，maxQueued 限制进入排队，rateLimit 约束每个来源窗口，maxSse 限制全局连接名额。

修改一项不意味着其余三项跟着改变。容量应按实际资源分别安排。

资源默认上限达到上限后的行为
活动轮次跨会话 2 个后续任务保持 queued，等待执行名额。
排队任务全局 200；单会话 100新入队操作返回 429 QUEUE_FULL。
HTTP 请求每个令牌与实际来源组合每 60 秒 120 次超频返回 429 RATE_LIMITED 与 Retry-After。
SSE 连接全局 20 个满额返回 429 SSE_FULL，Retry-After 为 5 秒。

任务创建、用户确认和 Workflow 再排队都会进入同一个数据库容量门禁。仓储在事务里先获取实例级 advisory lock，再检查全局和本会话 queued 数量。检查与写入共享事务边界，避免两个并发请求都看到“还剩一个位置”，最后同时入队。等待确认和提议没有算入 queued 容量；确认进入队列时才需要重新过门禁。

调度器全局串行扫描，按 tasks.sequence 查找可执行任务，并保留已有的会话内追加优先语义。跨会话的活动轮次达到默认 2 个时，不继续开启新轮次。已有活动 Turn 的追加走 steer，不额外占用新轮次名额。暂停会话和预算不足的任务不阻塞其他可执行会话，因此这里不承诺一个阻塞所有会话的严格总 FIFO。

滑动窗口 以连接令牌和实际 socket peer 为键。实现不信任 X-Forwarded-For，无效令牌合并到同一来源桶，不能通过不断换无效令牌绕过限制。代理后看到的是代理的实际地址；本章没有用户身份系统，也没有跨进程共享的限流账本。

源码 · stages/s12-deploy/server/modules/deployment/index.mjs · 第 45–59 行 
  request(token, address) {
    const now = this.now();
    for (const [key, values] of this.windows) {
      while (values.length && values[0] <= now - 60000) values.shift();
      if (!values.length) this.windows.delete(key);
    }
    const key = createHash('sha256').update(`${token}\0${address}`).digest('hex');
    const values = this.windows.get(key) || [];
    if (values.length >= this.rateLimit) {
      const error = new AppError('请求过于频繁。', 429, 'RATE_LIMITED');
      error.retryAfter = Math.max(1, Math.ceil((values[0] + 60000 - now) / 1000));
      throw error;
    }
    values.push(now);
    this.windows.set(key, values);
源码解读 · 对照运行边界

每次请求清理过期记录，空桶也会删除；仍在 60 秒窗口内的记录参与计数。

令牌和 socket peer 组合后计算摘要作为键；无效认证由 HTTP 层传入统一的 unauthenticated 标识。

达到额度时创建 429 RATE_LIMITED。等待时间由最早请求到期的剩余毫秒向上取整，最少为 1 秒。

未超限才追加当前时间。因此拒绝的第 121 次请求不会延长已有窗口。

假设窗口内已有 120 次请求，最早一条发生在一秒前，下一次请求会被拒绝，并建议等待 59 秒。HTTP handler 把 error.retryAfter 写入 Retry-After 响应头。等待是客户端重试的依据，不能把 429 当成模型已经执行失败；这次请求可能根本没有进入业务处理。进程重启会清空内存窗口，这是当前实现的范围。

SSE 使用独立名额：在异步读取会话数据前先 acquireSse，连接 close 时释放。释放函数带有 released 标记，即使清理路径重复调用，也只减一次计数。满额错误与请求超频错误都使用 429，但错误码和等待时间不同。健康接口绕过限流，让运维仍然能检查进程和依赖。

关闭先停止派发，重启保留不确定事实

一次轮次可能已经执行了外部操作，但尚未来得及把最终结果完整持久化。进程此时收到停止信号，不能把未收到终态等同于“模型完全没做事”，也不能把残留任务直接再发一次。部署的关闭逻辑要先阻止新增工作，再保存已经确定的状态，并给未确认的执行留下人工核对入口。

源码 · stages/s12-deploy/server/modules/deployment/index.mjs · 第 74–80 行 
export function gracefulShutdown({ stopDispatch, markUnconfirmed, close, exit = code => process.exit(code), timer = setTimeout, clear = clearTimeout }) {
  let pending;
  return () => pending ||= (async () => {
    stopDispatch();
    const deadline = timer(() => exit(1), 30000);
    try { await markUnconfirmed(); await close(); }
    finally { clear(deadline); }
源码解读 · 对照运行边界

pending 让多次关闭请求共享一次流程，避免重复关闭资源。

stopDispatch 同步执行，收到信号后先停止继续派发。

随后保存 unconfirmed，再关闭 HTTP、SSE、RPC 和数据资源；30 秒定时器是资源卡住时的退出截止。

正常清理结束后取消截止定时器；无法在截止前落库的残留执行状态，交给启动恢复再次处理。

SIGTERM 到达后，关闭入口按这个顺序组织服务：同步停止派发，把执行中的不确定状态持久化为 unconfirmed，然后关闭连接和资源。queued 任务仍保留。重启时沿用已有 recover 处理残余 starting、running、steering，不会自动重发需要核对的任务。这个设计保留了事实的不确定程度。

停止前状态停止或恢复后的含义下一步动作
queued尚未派发的持久任务仍在。服务恢复后按队列机制处理。
starting / running / steering可能已发生执行，结果需要核对。恢复为 unconfirmed，先查看任务结果与产物。
完成且已落库保留已有完成事实。根据已保存结果继续业务流程。
资源关闭卡住30 秒截止后强制退出。启动恢复检查残留状态，不能推断外部操作未发生。

优雅关闭并不是跨模型、数据库和文件系统的原子事务。执行器依赖 PostgreSQL 独占锁，服务停止后重建连接与锁仍需验证；模型工具内部的行为也不是部署模块重新实现的。真实 SIGTERM 验收应观察派发停止、任务状态、进程退出时间和重启后的恢复结果。离线断言能验证调用顺序，不能取代服务器上的完整故障过程。

代码回滚同样要区分事实。remote.sh 保留上一版目录和 previous 镜像标签，回滚替换代码与镜像，数据目录维持原路径。它不恢复 .env 的历史版本，也不会自动倒转数据库和 workspace。如果升级包含破坏性 schema 变化，需要兼容代码或升级前的完整备份，不能只切换镜像就宣称业务数据已恢复。

部署失败会留下 pending 标记，下一次部署前需要先处理回滚。首次部署没有上一版，排除故障并确认没有部署进程后，才能清除 pending 再重试。这个标记记录的是未完成的交付事实；它和 flock 锁文件不是同一概念。flock 在进程退出后释放，不需要通过删除锁文件来解锁。

📌

先核对结果，再决定是否重做

unconfirmed 表示证据尚不足。查看任务、产物和外部系统后再继续；直接重发可能重复已经发生的操作。部署模块保留这种不确定性，而不是替使用者猜测结果。

同一停服窗口完成备份，失败路径也有确定行为

完整恢复需要数据库与目录相互对应。数据库记录任务和资源版本，workspace 和不可变正文保存文件，.data/codex 保存原生历史。若 agent 一边写入，一边分别复制数据库和目录，两份数据可能来自不同时间。本章采用短暂停止 agent 的办法，把备份组织在一个没有业务写入的窗口里。

宿主 Bash 负责流程编排，真正的数据库工具在 postgres 容器内运行。宿主不依赖 Node/npm，但需要 Docker、Compose、Bash、flock、gzip/gunzip 等工具；打包程序在一次性 agent 容器内使用已有 Node 和 tar。agent 镜像不额外安装 postgresql-client。

cleanup 保存原始退出码并清理未发布 partial，无论成功还是失败都尝试 up -d --wait agent；重启失败也保留非零结果。

EXIT trap 安装在 stop 之前，停止操作失败或被中断时仍尝试恢复 agent。INT 和 TERM 被转为明确退出码。

pg_dump 在 postgres 容器内执行，gzip 将纯 SQL 写入隐藏 partial；pipefail 让转储失败可以传播。

root 创建的目录与 SQL 交给 uid 1000；一次性 agent 容器用 --no-deps 避免重新拉起依赖，并执行打包发布。

备份、恢复和实际 rsync sender 共用 backups/.download.lock，锁持续覆盖整个操作。锁文件保留同一 inode，进程退出后自动释放。删除再创建锁文件可能让不同操作持有不同 inode，破坏互斥；因此流程不把删除锁文件当成清理动作。下载通过 SSH 与 rsync，限速 200 KB/s，备份不会经 HTTP 提供。

SQL 先写入隐藏的 .partial 目录，再由 backup.mjs 打包 workspace、原生历史、实例身份和不可变文件正文。manifest 包含大小、SHA-256 与版本。目录归档和校验完成后原子重命名为正式备份，只保留最近 7 份成功备份。partial 不存在或缺少 SQL 时拒绝发布，失败包不能占用成功备份的名额。

内容是否包含恢复含义
数据库 gzip 纯 SQL包含用运行中的 postgres 容器重放。
workspace、原生历史、实例身份与不可变正文包含与 SQL 在同一停服窗口内保存。
Redis 缓存、.runs 日志不包含不作为完整业务恢复的事实来源。
.env、服务商密钥、镜像不包含需要另行保管凭据与可运行代码镜像。

SHA-256 可以发现文件被修改或损坏，但 manifest 本身不是数字签名；攻击者如果能同时替换包和 manifest，摘要无法证明来源。恢复只接受管理员信任的备份。恢复还要求相同部署路径与兼容数据库 schema，不能把完整包理解成任意机器、任意版本之间的自动转移格式。

restore.sh 先持有同一个锁并停止 agent，再从 /dev/tty 确认；非交互运行且未提供 --yes 时拒绝。确认后，一次性 agent 容器先校验 manifest；宿主使用 gunzip 与 postgres 容器里的 psql 重放 SQL，开启单事务和 ON_ERROR_STOP；之后恢复目录，保留 bind mount 根目录，最后启动 agent 并检查 /ready。

恢复取消或任何一步失败都保持 agent 停止；启动或就绪失败也再次停止，避免继续提供数据库与文件混合的数据。备份失败则尝试重启 agent，因为原业务数据仍是工作的依据。两种失败策略不同，不能把备份 cleanup 机械地复制给恢复。恢复跨数据库和文件系统，不是一个总原子事务，失败后应继续停服并重新恢复完整备份。

运行步骤、离线证据与外部验收

本机体验需要 Node.js 24+、Docker 和 Compose v2。进入 stages/s12-deploy，按 README 安装锁定依赖、复制 .env.example 并生成网关访问密钥。实际凭据只写入本机 .env，设置权限 600；CONTAINER_APP_DIR 使用部署目录的实际绝对路径，不把真实路径写进教学材料。模型和数据库配置完成后再构建运行。

cd stages/s12-deploy
npm ci
cp .env.example .env
npm run gateway:key
# 按 README 填写 .env，再执行以下步骤
docker compose build agent

curl --fail http://127.0.0.1:4326/ready

预期 /ready 返回 ready，checks 全部为 true；没有 REVISION 时版本为 dev。Linux 的 bind mount 目录需要 uid 1000 可读写，管理员可按 README 的 configure 步骤初始化权限。普通停止使用 docker compose stop，保留数据卷。实际部署要记录代码版本、检查结果与未完成项，不把预期输出当作已经运行成功的证据。

远程目标使用 systemd 的 Linux 服务器，准备 Docker、Compose、rsync、flock、tar、gzip 和 sha256sum。SSH 用户需要管理 Docker 与安装 systemd 单元的权限。remote.sh init-env 通过固定版本的 Node 容器准备远端配置，重新生成数据库与网关凭据，拒绝覆盖已有文件；deploy 交付当前工作区并记录基准版本与工作区部署时间，不执行 Git 提交。

export DEPLOY_HOST=example.com
bash deploy/remote.sh check
bash deploy/remote.sh init-env
bash deploy/remote.sh deploy
bash deploy/remote.sh status
bash deploy/remote.sh tunnel

s12 是一套独立部署，用 remote.sh tunnel 经 SSH 隧道连接本机 http://127.0.0.1:4326。工作台提供课程、机制演示和 README 入口，不直接代理这个部署。生产域名、HTTPS、Basic 口令和路径白名单见 s12 的 production 文档；这些不属于教学启动步骤，也不等于完整用户身份系统。
