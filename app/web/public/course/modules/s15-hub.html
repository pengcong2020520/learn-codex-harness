权限与资源 Hub：能用什么，谁说了算

把资源可见性、动作、权益与分享审批放在同一处判定；执行中的轮次保留快照，下一轮核对新规则。

用户已经隔离，怎样让资源有边界地共享

bob 和 carol 各有自己的运行环境、原生历史与工作目录。现在 bob 想把一个知识库分享给 carol，又想让 carol 使用自己写的 Skill。共享不能等同于把两个目录合在一起：carol 可以读知识库，却不能改 bob 的原文；Skill 是会影响模型行为的指令，不能在 bob 提交名单时就进入 carol 的执行环境。服务还要知道，授权撤销后哪一次请求开始拒绝，以及正在执行的任务是否继续。

权限与资源 Hub 回答两个问题：这个用户能不能看到资源，以及看到以后能做哪个动作。资源包括 Agent、工具组、知识库和 Skill，动作固定为 use、read、modify、share、delete。GET /hub 返回可见资源的类型、scope、所有者用户名与可执行动作，客户端不必自己猜权限。

单元本章职责继续保留的边界
Hub可见范围、动作、权益、授权审批、配额与审计。身份来自认证或持久任务 owner，不接受模型提供的身份。
PermissionGate把最新授权快照绑定到可信轮次上下文。Agent 挂载、workflow 临时授权和输出范围仍需满足。
sessions / messages新轮次重验共享知识库，按用户权益决定派发。任务继续持久化排队，全局同时最多两轮。
runtimes / Codex同步用户 Skill，空闲时受控重启并核验发现结果。每用户进程、目录与 uid 保持独立，Codex 执行 Thread / Turn。
PostgreSQL保存权益、授权、审批、scope 联动和只追加审计。数据库提交不等于文件系统同步已成功。

会话与普通文件仍是个人隔离对象。admin 能管理 Hub 资源，不代表可以通过分享接口进入别人的会话。工具组与 Agent 都是 system 资源，由部署者提供定义和代码；本章不允许用户上传新的工具实现，也不提供动态 Agent 上传。用户可以上传的 Skill 只包含指令文本，实际执行能力仍取决于可信工具与权限判定。

这套服务是独立部署，默认端口 4329。工作台展示教材和部署说明，通过 remote.sh tunnel 建立 SSH 隧道后，CLI 连接本机 http://127.0.0.1:4329。共享工作台不会把 s15 注册成实时代理目标。这里的授权说明用于理解服务端行为，静态卡片和泳道演示本身不会创建账号、授权或安装 Skill。

同一判定：先决定看得见，再决定能做什么

scope 描述资源面向谁。private 由所有者和 admin 使用、修改；shared 增加指定接收者的 use/read，修改仍由所有者和 admin 管理；system 对用户开放使用，但受权益限制，修改由 admin 管理。知识库删除有显式所有者规则，不能把通用表格当成省略具体动作检查的理由。

请求结果原因
carol 读取 bob 未分享的 private 知识库404资源对 carol 不可见，不透露存在性。
bob 分享后，carol 读取该库200指定授权使资源可见，read 是允许动作。

bob 撤销后，carol 发起新的读取404新快照中不再存在 carol 的授权。

Hub 的 can 方法委托给策略内核，checkResource 则从当前可信快照查资源，再检查动作。模型不能通过参数声称自己是 bob；currentIdentity 来自认证上下文，后台执行则取持久任务的 owner。列表也用同一个 decision 过滤，并逐项计算 actions，避免列表显示与实际请求使用两套不同规则。

源码 · hub/policy.mjs · 第 9–30 行
export function decision(user, action, resource) {
  if (!ACTIONS.includes(action)) throw new AppError('未知权限动作。', 400);
  if (!user || user.disabled_at || !resource) return 404;
  // 会话、普通文件仍属于个人隔离边界；admin 不借 Hub 进入别人的会话。
  if (resource.type === 'personal') return owns(user, resource) ? 200 : 404;
  if (user.role === 'admin') return 200;
  const scope = resource.scope ?? resource.visibility ?? 'private';
  const owner = owns(user, resource);
  const granted = user.grants?.includes(`${resource.type}:${resource.id}`);
  const visible = owner || scope === 'system' || (scope === 'shared' && granted);
  if (!visible) return 404;
  const plan = user.plan || PLANS.basic;
  if (resource.type === 'agent' && !includes(plan.agents, resource.planId || resource.id)) return 404;
  if (resource.type === 'tool_group' && !includes(plan.tool_groups, resource.id)) return 404;
  if (resource.type === 'knowledge' && action === 'delete' && owner) return 200;
  return ['use', 'read'].includes(action) || (scope !== 'system' && owner) ? 200 : 403;
}
export function can(user, action, resource) {
  const status = decision(user, action, resource);
  if (status !== 200) throw new AppError(status === 404 ? '资源不存在或未授权。' : '没有执行这个动作的权限。', status, 'HUB_DENIED');
  return true;
}
源码解读

首先拒绝不存在、禁用或缺少资源的情况。personal 在 admin 分支之前检查归属；随后判断 owner、scope 和指定授权。Agent 与工具组还检查权益，最终才按 use/read 或所有者管理动作放行。can 将非 200 结果转为带状态码的 HUB_DENIED。

bob 分享知识库无需审批，但名单有严格限制：每个资源最多授权 20 人，不能授权给自己、不存在或已禁用账号。禁用账号的旧授权保留，身份加载失败使其不能继续使用。有授权时 scope 为 shared，最后一条撤销后回 private。这些约束在业务方法和数据库约束中落实，不能仅靠前端禁用按钮。

所有 Hub 写操作在实例级事务锁内执行，资源行再用 FOR UPDATE 取得，分享名单与审计一起提交。发布为 system 会清除指定授权；取消发布回 private，不会自动恢复发布之前的名单。两次操作均把清除的用户 ID 写到 publish 审计的 detail.revokedGrantees，因此管理员能够追踪一次公开范围调整究竟撤掉了哪些指定授权。

源码解读

先检查 share 动作，system 资源无需指定授权。targets 验证用户名与剩余名额，insertGrant 写授权，audit 记前后名单；外层 mutate 管理事务。

授权通过只是读取链路的起点。知识库还要符合 Agent 的挂载规则，修改与索引继续需要对应知识库的 workflow 授权，读取再核验原文版本、Wiki 或 RAG 索引。共享原文按登记 owner 的工作区定位，由原 owner 的 uid 辅助进程读取；请求身份仍是 carol，不会为了读一份共享资料就临时变成 bob。

普通用户可以通过 POST /knowledge 创建自己的 private 库，所有者取登录身份。库 ID 为 1–64 位小写字母、数字或连字符，在实例内唯一；标题为 1–200 字。数量检查、登记与目录准备共用事务边界。用户创建的库只可继承 Agent 第一个 knowledge 挂载项的默认动作和模式；没有挂载项就不挂载，未声明的静态库也不能借这个规则获得权限。

删除只允许所有者或 admin。在持久任务或活动 gate 上下文中仍被挂载、或索引正在执行时，返回 409 KNOWLEDGE_BUSY。允许删除后，清理授权、Wiki 和索引登记、外部索引与 owner 目录，并将原文资源标为 revoked。数据库和目录没有跨系统事务：清理失败不能报告成功，已清理的文件也不能靠 SQL 回滚自动恢复。

工具三方交集与权益：有一层不允许，就不能执行

Agent 配置可以声明 read_webpage，但 basic 用户没有 web 工具组权益；同样，pro 可以使用全部系统工具组，也不能调用 Agent 没有声明的工具。有效工具 把三道限制合起来：Agent 白名单 ∩ 权益工具组 ∩ 工具组可见范围。

export function effectiveTools(user, agent, groups) {
  return [...new Set(groups.filter(group => decision(user, 'use', { ...group, type: 'tool_group' }) === 200)
    .flatMap(group => group.tools).filter(name => agent.tools.allow.includes(name)))];
}

配额同样发生在派发前。服务按 owner_id 汇总用量，时区沿用 AGENT_BUDGET_TIMEZONE；读取前等待账本写入链，写入失败保持拒绝派发。达到每日上限时任务仍为 queued，由定时唤醒在预算时区的次日再检查。已在运行的一轮与当前轮次的追加继续完成，因此配额不是对正在生成的 token 做逐个截断。

并发按执行任务与活动会话去重计数，先服从全局两轮，再服从用户权益。basic 的另一个任务可以继续等待，并不意味着其他用户必须一起等待。admin 豁免每日 token 与资源数量的权益上限，也不能突破全局轮次容量。降级保留已有资料，数量超额时拒绝新增；它不会为了凑回额度而删除用户知识库。

一次降级还可能改变工具和原生搜索的允许集合。新的轮次取得最新权益，必要时在空闲边界重启用户进程。旧轮次继续使用启动快照，避免执行到一半时同一个工具动作突然换用另一套身份事实。这里要分别观察任务排队状态、用户运行环境集合与用量账本，不能只看客户端按钮是否显示。

Skill 分享：提议不授权，批准后还要安装与核验

Skill 上传后是 private，先同步到所有者自己的 CODEX_HOME/skills。上传接口接收 JSON 文本文件映射，不解压归档，只接受 SKILL.md 与 references/ 下的 .md/.txt，最多 50 个文件，合计 128 KiB。路径穿越、链接与代码文件不被接受。Codex 负责 frontmatter 解析和原生发现，服务负责验证允许集合；文本指令不会凭空得到新的工具执行能力。

bob 提议把 Skill 分享给 carol 时，shareSkill 校验所有者和接收名单，然后写入 pending。它只记录需要审阅的申请，不插入 resource_grants。carol 此时既没有新授权，也没有因此安装的新副本。再次提议会更新待审名单并清除旧审批身份，不能把之前的一次通过当成任意新名单的授权。

  async reviewSkill(id, approve) {
    const result = await this.mutate('skill', id, 'share', async (client, actor, row, before) => {

时点数据库状态carol 的执行环境
bob 上传private，所有者 bob没有新副本。
bob 提议 carolpending，没有新 grant仍没有新副本。
admin approveapproved、授权与审计提交开始安装集合对账；失败会报错。
carol 下一轮重新读取权限快照集合变化等待空闲重启，发现核验后可用。
bob 撤销删除 grant，也从 pending 名单移除立即移除安装副本；活动轮次保留原快照。

“下一轮可用”包含明确前提。批准之后，运行环境先以接收者 uid 对账安装集合，冷启动与同步共享该 owner 的串行边界；集合改变时等待活动轮次结束，在空闲租约关闭旧进程，重新启动并核验 Skill。若旧会话的指纹已不兼容，需要新建会话，原历史仍保留。批准动作不直接把新指令塞进 carol 正在执行的一轮。

reject 只把申请置为 rejected 并写审计，不授予权限。所有者撤销无需再次审批，会立即移除接收者安装副本；同时把该接收者从待审批名单删除，防止旧申请之后又把已撤销对象授权回来。对账只删除本服务 manifest 管理的 Skill，不触碰 .system 或其他目录。

数据库提交和文件同步之间没有分布式事务。同步失败时授权可能已经提交，接口会报错，不能把 SQL 回滚当成已完成的补偿。重试撤销会再次清理副本，下一次用户进程启动完整对账，在核验完成之前不执行新轮次。这也是演示中必须分别显示申请、授权、安装、轮次四种状态的原因。

权限撤销不会远程抹去已经发送给模型的正文。活动轮次继续持有启动快照，下一轮才按新规则检查 Agent、Skill 与会话已挂载知识库。普通 HTTP 读取则取得最新快照，所以 bob 撤销知识库分享后，carol 新请求返回 404，与旧轮次继续完成并不矛盾。

revocation旧轮次保留快照，新任务用新规则，集合变化受控重启。已经进入模型上下文的资料能够被抹除。

外部验收要验证另一组事实。PostgreSQL 测试真实执行重复执行数据库升级、并发授权竞争、审批、scope 联动与审计修改拒绝；Linux uid 测试真正启动文件辅助进程并检查跨用户读取拒绝。服务器验收还要经 HTTP 走完整路径：bob 创建、导入与分享知识库，carol 读取成功而写入 403，未获授权用户 404，bob 撤销后新的访问与下一轮被拒绝。

permission_events 保存 actor、动作、资源、前后状态、detail 与时间，UPDATE、DELETE、TRUNCATE 都被触发器拒绝。这保护正常数据库写接口下的审计记录，并不取消数据库超级管理员的管理能力。共享来源也要保持版本一致：原文变化但尚未登记新版本时返回 SOURCE_STALE，不能为了让读取看似成功而返回旧内容。

本章边界保持清楚：只支持指定用户名，没有组织、小组、支付、Skill 市场或多主机。权益由 admin 手动分配，工具代码由部署者交付。文件系统与数据库的跨系统失败通过报错、可重试对账和新轮次前核验收敛；路径复核仍存在同 uid 恶意进程造成的竞态窗口，不能替代系统隔离。本机非 root 模式没有系统 uid 隔离，生产容器不能切 uid 时应拒绝启动。

动手时先完成阶段 README 中的独立部署、账号初始化和模型配置，再保持 SSH 隧道运行，以自己的账号登录 CLI。审批使用另一位 admin 的身份，读取与撤销结果用 carol 的新请求验证。需要数据库、端口或容器的检查应单独记录执行结果，不能将离线实验成功写成部署已验收。
