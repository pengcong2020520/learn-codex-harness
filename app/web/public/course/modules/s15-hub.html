权限与资源 Hub：谁能用、谁能改，一处判定

资源范围决定向谁开放，权益决定能用多少；分享需要明确授权，每轮使用自己的权限快照。

隔离之后，团队还需要有边界地共享

上一章让云端 Agent 的每个用户都有独立运行环境。但团队还需要一起用：bob 想把知识库给 carol 读，不让她修改；用户写的 Skill 想影响别人的 Agent，需要有人审阅；一个人用完预算，也不该拖住其他人。

权限与资源 Hub统一回答“这个用户，能不能对这个资源做这个动作”。使用、读取、修改、分享、删除五种动作都到这里判定，避免工具、知识库和调度器各说各话。

身份来自认证或持久任务，Codex 继续执行轮次，不参与授权。Hub 管理资源范围、权益、分享和审计；会话与普通文件仍是个人隔离对象，admin 也不能借 Hub 访问别人的会话。工具和 Agent 由部署者提供，用户不能上传新的工具实现或动态 Agent。

资源范围：私有、分享、系统

scope说明资源面向谁。私有资源面向所有者，分享增加指定接收者的读取与使用，系统资源向用户开放但受权益限制；管理员管理 Hub 资源，也可访问这些资源，但个人会话不在这个例外内。

看不见的资源返回 404，不透露其存在；看得见却不能做某个动作返回 403。例如 carol 获得分享后能读 bob 的知识库，却不能修改、删除或再分享。

源码 · hub/policy.mjs · 第 9–30 行
export function decision(user, action, resource) {
  if (!ACTIONS.includes(action)) throw new AppError('未知权限动作。', 400);
  if (!user || user.disabled_at || !resource) return 404;
  // 会话、普通文件仍属于个人隔离边界；admin 不借 Hub 进入别人的会话。
  if (resource.type === 'personal') return owns(user, resource) ? 200 : 404;
  if (user.role === 'admin') return 200;
  const scope = resource.scope ?? resource.visibility ?? 'private';
  const owner = owns(user, resource);
  const granted = user.grants?.includes(`${resource.type}:${resource.id}`);
  const visible = owner || scope === 'system' || (scope === 'shared' && granted);
  if (!visible) return 404;
  const plan = user.plan || PLANS.basic;
  if (resource.type === 'agent' && !includes(plan.agents, resource.planId || resource.id)) return 404;
  if (resource.type === 'tool_group' && !includes(plan.tool_groups, resource.id)) return 404;
  if (resource.type === 'knowledge' && action === 'delete' && owner) return 200;
  return ['use', 'read'].includes(action) || (scope !== 'system' && owner) ? 200 : 403;
}
export function can(user, action, resource) {
  const status = decision(user, action, resource);
  if (status !== 200) throw new AppError(status === 404 ? '资源不存在或未授权。' : '没有执行这个动作的权限。', status, 'HUB_DENIED');
  return true;
}
源码解读

首先拒绝不存在、禁用或缺少资源的情况。personal 在 admin 分支之前检查归属；随后判断 owner、scope 和指定授权。Agent 与工具组还检查权益，最终才按 use/read 或所有者管理动作放行。can 将非 200 结果转为带状态码的 HUB_DENIED。

分享只给指定的人，不等于公开。知识库由所有者直接授权，最多 20 人，不接受自己、不存在或禁用账号；撤销最后一条授权就回到 private。发布为 system 会清除指定名单，取消发布也不自动恢复名单。

源码解读

先检查 share 动作，system 资源无需指定授权。targets 验证用户名与剩余名额，insertGrant 写授权，audit 记前后名单；外层 mutate 管理事务。

授权、范围变化和审计在同一事务提交。读取还要符合 Agent 挂载和原文版本要求：来源变化但未登记新版本时返回 SOURCE_STALE。共享读取使用所有者的文件权限，请求身份仍是接收者，不能为取文件而冒充主人。

用户可创建自己的私有知识库，受权益数量限制。仍被任务挂载或正在索引的库返回 409 KNOWLEDGE_BUSY；删除后的数据库与文件清理不能原子回滚，失败必须报错。格式和接口细节见设计说明。

权益决定能用多少，工具取三份清单的交集

权益描述能选哪些 Agent、工具组，以及每日用量和并发上限。有效工具必须同时满足 Agent 白名单、权益工具组和工具组可见范围；任何一层没允许，都不能因为另两层允许就执行。

export function effectiveTools(user, agent, groups) {
  return [...new Set(groups.filter(group => decision(user, 'use', { ...group, type: 'tool_group' }) === 200)
    .flatMap(group => group.tools).filter(name => agent.tools.allow.includes(name)))];
}
源码解读

源码解读

nativeSearch 重新取用户快照，要求 web 组允许 use，且组内包含 read_webpage。原生能力与业务工具因此服从同一权益来源。

配额在新轮次派发前检查。当天 token 用完，只停该用户的新任务，queued 保留到预算时区的次日再检查；正在执行的一轮与轮内追加继续完成，其他用户不受影响。因此额度不是生成中逐 token 截断，也不能突破全局 2 轮上限。

权限在轮次边界生效：每轮开始取最新快照，该轮一直按它执行，撤销或降级从下一轮生效。降级保留已有资料，超额时拒绝新增；必要的进程重启等到空闲边界进行。

用户 Skill：可以提议，不能自批

Skill 会改变别人的 Agent 如何工作，所以分享需要另一位管理员审阅批准；知识库是所有者的资料，分享不需要这道审批。用户 Skill 只能是指令文本，执行能力仍来自可信工具。

上传默认私有，只安装到自己的 CODEX_HOME。格式限定 SKILL.md 和 references 中的 Markdown 或文本，最多 50 个文件、合计 128 KiB，拒绝代码、链接和路径穿越。

提议分享只写入 pending，不授予权限，也不安装到接收者环境。更新名单需要重新审批，不能沿用先前批准。

源码解读

只有 approve 分支调用 insertGrant。授权、approved/rejected 和审计在同一事务提交；syncSkills 放在提交之后，且只在批准时调用。返回 approved 的前提还包括同步调用没有报错。

批准提交授权后，还要以接收者 uid 同步安装集合，在空闲边界重启并核验 Skill，下一轮才可使用。数据库提交和文件同步不是同一事务：同步失败会报错，重试或下次启动须完整对账，核验前不执行新轮次。

撤销移除安装副本，但不能抹去已送入模型的正文。活动轮次保留原快照；普通 HTTP 读取取最新权限，下一轮也重新检查。会话指纹不兼容时需新建会话，历史仍保留。

变更留下审计，规则要验证拒绝路径

权限决定谁能使用资源，审计解释这份权力如何变化。每次分享、撤销、发布、权益调整和 Skill 审批，都追加记录谁、对什么、从什么改成什么以及时间，正常数据库接口不能修改或删除这些记录。

验证时同时看允许与拒绝：被分享者能读不能改，未授权者看不见，撤销后的新请求被拒绝，旧轮次继续遵循快照。离线实验验证这些规则；真实数据库约束、Linux uid 和文件同步需外部验收，步骤见本章 README。

本章只支持指定用户，没有组织、小组、支付或 Skill 市场。权限数据库与文件之间仍有失败窗口，不能把一次批准等同于安装成功。
