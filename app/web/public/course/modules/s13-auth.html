账号与认证：请求有身份，资源有归属

密码校验建立身份，令牌维持登录状态，owner 检查贯穿数据、缓存、任务、文件与事件。

服务已经部署，谁在使用它？

服务能够启动、恢复和限制容量之后，还要回答：谁在提交任务，谁能看到结果？如果只用同一个连接凭据，客户端可以进入服务，却无法表达“这个会话属于当前用户”。账号与认证把使用者变成明确的身份，但登录成功只是起点；会话、知识库、产物和用量都要沿用这个身份。

认证 回答“你是谁”。归属 回答“这份资源属于谁”。一个用户知道别人的会话 ID，不应因此获得访问权。即使是 admin，也不能越过资源的 owner 检查。

执行位置负责什么可观察证据
Codex管理原生 Thread、Turn、模型调用、上下文与工具循环。现有协议与任务执行结果；不负责认定 HTTP 用户。
accounts / HTTP校验密码、签发与吊销令牌、建立请求身份。登录响应、会话查询、401 和请求上下文。
数据、工具与事件按 owner 查询和定位文件，后台沿用持久记录的身份。他人资源 404、他人事件不推送、用户目录不同。
管理员与使用者交互设置密码，维护账号，保管客户端凭据，验证真实部署。账号命令、双客户端检查和交付记录。

账号仅有 admin 和 user 两种技术角色，用户名规范化为小写。没有注册、邮箱、找回密码或 Web 登录页，账号通过管理命令创建。identity.json 继续标识实例；它在首次初始化时帮助确定已有数据的首个 admin，不能成为业务请求缺少身份时的默认值。

本章沿用单实例的数据范围。用户名在实例内唯一，知识库 ID 也仍在实例内唯一。首个 admin 保留已有知识库，新账号看不到其他 owner 的库；创建一个账号不会复制别人的资料，也不会自动授予共享知识权限。

密码验证：随机盐、固定成本与统一错误

密码不能以明文保存。hashPassword 使用 Node 内置 scrypt，参数固定为 N=32768、r=8、p=1，每次生成 16 字节随机盐，派生 64 字节结果。数据库保存包含参数、盐与派生结果的字符串。随机盐让同一个密码的不同保存结果也不同，但校验时仍能从已保存的盐重新派生。

verifyPassword 只接受这组固定参数与固定长度编码，不从数据库字符串读任意成本设置。格式不符合预期时，使用同参数的哑哈希格式完成派生；未知用户名在 Accounts.login 中也传入 DUMMY_HASH。昂贵的密码计算不会因为“没有这个账号”而被直接省略。

export const DUMMY_HASH = `scrypt$32768$8$1$${'00'.repeat(16)}$${'00'.repeat(64)}`;
export async function verifyPassword(password, encoded, kdf = derive) {
  const match = /^scrypt\$32768\$8\$1\$([a-f0-9]{32})\$([a-f0-9]{128})$/.exec(encoded || '')
    || /^scrypt\$32768\$8\$1\$([a-f0-9]{32})\$([a-f0-9]{128})$/.exec(DUMMY_HASH);
  const actual = await kdf(typeof password === 'string' ? password : '', Buffer.from(match[1], 'hex'), 64, SCRYPT_OPTIONS);
  const equal = timingSafeEqual(actual, Buffer.from(match[2], 'hex'));
  return typeof password === 'string' && Boolean(password) && encoded !== DUMMY_HASH && equal;
}

  async login({ username, password }, source) {
    const finish = this.limits.begin(username, source);
    let success = false;
    try {
      const user = await this.store.byUsername(normalizeUsername(username));
      const valid = await this.verify(password, user?.password_hash || DUMMY_HASH);
      if (!valid || !user || user.disabled_at) throw new AppError('用户名或密码错误。', 401, 'LOGIN_FAILED');
      const token = randomBytes(32).toString('base64url');
      const now = this.now(), expiresAt = new Date(now + ABSOLUTE_MS).toISOString();
      // 再锁定用户并核对哈希，避免改密码/禁用与登录并发时签出旧凭证。
      const saved = await this.store.createSession(user, { id: randomUUID(), userId: user.id, tokenHash: tokenHash(token),
        createdAt: new Date(now), expiresAt, clientHint: 'CLI' });
      if (!saved) throw new AppError('用户名或密码错误。', 401, 'LOGIN_FAILED');
      success = true;
      return { token, expiresAt, user: publicUser(user) };
    } finally { finish(success); }
  }

登录限流按“规范化用户名 + 实际来源”限制 15 分钟内 5 次失败，按来源限制 15 分钟内 20 次；超限返回 429 和 Retry-After。先预占再执行 scrypt，避免并发请求同时绕过计数。成功后释放本次预占，失败保留。计数在当前进程内，服务重启会清空窗口。

密码验证通过之后，管理命令可能已经修改密码或禁用账号。因此创建令牌前还要锁定账号，重新核对哈希和禁用状态。验证与签发之间的竞争由数据库事务处理。改密码和禁用同样在事务内更新账号并吊销会话；离线测试能核对调用顺序，真实锁和约束要在 PostgreSQL 上验收。

令牌不是身份自述，每次请求都要查库

登录返回 randomBytes(32) 生成的 base64url 不透明令牌。客户端把它保存到权限 0600 的 .data/credentials.json；.data/connection.json 只保存服务地址。服务端只存令牌 SHA-256。这里没有 JWT，也没有 refresh；客户端获得 401 后重新运行 npm run login。

令牌有两条期限：绝对 7 天，闲置 12 小时。last_seen_at 最多每分钟更新一次，降低持续请求的写入频率。认证依然每次查库，更新时间节流不等于缓存认证结果。数据库中的账号禁用、会话吊销和期限状态共同决定当前令牌是否可用。

源码 · stages/s13-auth/server/modules/accounts/index.mjs · 第 32–42 行
  async authenticate(authorization) {
    const match = /^Bearer ([A-Za-z0-9_-]{43})$/.exec(authorization || '');
    if (!match) throw unauthorized();
    const row = await this.store.session(tokenHash(match[1]));
    const now = this.now();
    if (!row || row.disabled_at || row.revoked_at || now >= +new Date(row.expires_at)
      || now - +new Date(row.created_at) >= ABSOLUTE_MS || now - +new Date(row.last_seen_at) >= IDLE_MS) throw unauthorized();
    if (now - +new Date(row.last_seen_at) >= TOUCH_MS) await this.store.touch(row.session_id, new Date(now));
    return { userId: row.id, role: row.role, authSessionId: row.session_id, user: publicUser(row) };
  }
  async logout(identity) { await this.store.revokeAll(identity.userId); }

触发条件服务端行为客户端观察
有效 Bearer查库检查状态与期限，返回认证身份。进入业务请求，仍受 owner 门禁约束。
缺少或错误令牌认证失败。401，提示重新登录。
登出、改密码或禁用吊销该用户全部会话令牌。旧令牌的下一次请求返回 401。
有效身份访问他人资源归属检查没有得到当前 owner 的资源。404 NOT_FOUND，与资源不存在相同。

HTTP 认证成功后用 AsyncLocalStorage 携带 { userId, role, authSessionId }，再进入门禁和实际处理。模型不能修改这个身份。业务请求按 userId 限制每分钟 120 次，未认证请求按实际 socket 来源限制，不信任 X-Forwarded-For。/health 和 /ready 免认证，带 Origin 的请求仍被拒绝，认证响应设置 Cache-Control: no-store。

📌

区分下一次请求和现有连接

已有 SSE 不逐帧重新验证令牌。吊销保证下一次请求失效，不承诺当前订阅立刻断开；当前订阅仍只能接收所属用户的事件。验收应分别观察这两条边界。

owner 贯穿缓存、任务与 SSE

数据库查询按 instance_id、owner_id 和资源 ID 限定范围，缓存命中也要重新核对归属。否则只要曾经加载过别人的会话，后续请求就可能绕过数据库过滤。资源不存在与不属于当前用户统一返回 404 NOT_FOUND，避免接口暴露“这个 ID 实际存在，只是不属于你”。

后台执行没有当前 HTTP 用户。outbox 和调度维护可以扫描实例任务，但派发每个任务前必须从记录取得 owner，再绑定执行上下文。媒体任务和知识索引 worker 也从持久记录获取归属。延迟写入用量时，在入链时捕获 owner，不能等待异步执行时再猜当前请求是谁。

SSE 有实时推送、连接建立期间的缓冲、断线补发和快照四条路径。listener 先检查 owner 和 Thread，再决定立即写入或放入缓冲。重连时 hub.since 也带 userId；历史不能因为已经在内存中就跳过归属过滤。

EventHub 在 publish 入口就拒绝没有 ownerId 的事件，发出警告并返回 null，不让无主事件进入历史或推送。不能把缺少 owner 当成“所有人可见”。一个真实属于用户 B 的事件也不会进入用户 A 的订阅，哪怕客户端构造了相同 Thread ID。

文件 locator 继续是相对路径，可信 owner 决定实际工具根 workspace/users/<ownerId>/。目录按需创建，权限 0700；原有路径校验继续拒绝越界、符号链接和不允许的文件类型。不同用户可以拥有同名相对路径，数据唯一键包含 owner_id。请求参数不能直接选择另一个用户的物理根。

这仍有明确边界：所有用户共用一个 Codex 进程、一个 CODEX_HOME 和一个 workspace，Codex cwd 没有按用户变化。原生文件能力保持关闭，文件经过工具层。工具目录和 API 门禁不是操作系统沙箱，不能抵御同机管理员或恶意插件，也不能自动清除 Thread 中已有上下文。

独立部署与首次账号初始化

s13 使用自己的 Compose 项目，默认端口 4327，不进入工作台实时目标或共享 stages 容器。工作台提供本章内容、机制演示与 README 链接。实际连接由 SSH 隧道与终端客户端完成；s13 需要登录：remote.sh tunnel 后 npm run login。

首次 deploy 等待 postgres、redis、gateway 健康，用 agent 镜像的一次性容器准备数据库与目录并查询启用账号数。没有启用账号时，deploy 成功退出并提示 auth-init，agent 尚未启动，此时没有 /ready。不能把这次部署命令退出 0 当成已经可以接受用户请求。

cd stages/s13-auth
# 按 README 准备依赖与 .env，显式设置 AGENT_MEMORY_ENABLED=false
export DEPLOY_HOST=example.com
bash deploy/remote.sh check
bash deploy/remote.sh init-env
bash deploy/remote.sh deploy
bash deploy/remote.sh auth-init
bash deploy/remote.sh user -- add bob
bash deploy/remote.sh tunnel

auth-init 通过 SSH TTY 交互设置首个账号，密码隐藏输入，不放入命令参数。成功后启动 agent，注册开机启动并输出包含 status: ready 的 JSON。已经初始化时拒绝重新初始化，远程命令仍确保 agent 启动；其他错误不能被当成“已经做过”而忽略。

初始化保留 identity.json 中原 owner 的标识，使已有会话和知识库继续归首个 admin。已有顶层资料进入该 admin 的用户目录。数据库与文件系统不能作为一个事务提交，处理已有数据前要停服、备份，遇到同名资料冲突时核对目录，不能覆盖目标资料后继续。文件移动中断后的重试同样不覆盖已经移动的内容。

保持隧道终端打开，在另一个终端进入本阶段目录：

export AGENT_SERVER_URL=http://127.0.0.1:4327
npm run login
npm run chat
# 结束当前账号的登录会话
npm run logout

两个账号应使用两个独立客户端工作副本，避免共用 credentials.json。用户 A 创建会话后，用户 B 的列表里看不到它，尝试恢复其 ID 应为 404；知识库列表和按 kbId 读取也遵循同样规则。两个用户生成同名产物时，应落在不同的用户工具目录中。

启用账号达到两个时必须显式设置 AGENT_MEMORY_ENABLED=false，否则启动与添加第二个账号都会拒绝。原生共享记忆可能把一个用户的内容提供给另一个用户。启动检查和添加账号使用数据库锁串行核对；仅给管理命令临时设置 false，不能绕过尚未重启且仍启用记忆的服务。关闭记忆后 API 不再返回旧共享摘要，但底层文件与已有 Thread 上下文仍保留。

用拒绝路径验收账号边界

“能够登录”只能证明成功路径。验证归属还要检查密码错误、未知账号、旧令牌、他人资源、缺少 owner 的事件和跨用户缓存。每项实验都运行实际模块并由断言决定退出码，不能把预期输出当作已通过记录。

多个用户共享全局并发两轮，没有按用户配额。账号角色不会增加资源范围，没有共享知识权限，也没有 Web 登录页。本章完成的是经过认证的 owner 传递；理解了这个范围，才能准确解释哪些请求应为 401，哪些资源应为 404，以及为什么底层运行环境还需要更强隔离。
