s07

记忆：Codex 提炼，服务端管控

把跨会话记忆接到服务中：默认关闭，逐项核验配置，限制查看范围，并让会话参与设置服从策略。

这个云端 Agent 还缺什么：跨会话使用经验

上一章，Agent 可以读取资料、查看网页并保存结果。这个云端 Agent 还缺什么？同一 Thread 可以延续历史，但新开的 Thread 不会仅凭另一段会话记录就自动继承其中的偏好。本章接入 Codex 原生记忆，同时明确谁能使用、谁能贡献、什么结果已经生成。

原生记忆 的提炼与使用由 Codex 负责。服务端不自行拼接历史摘要、不把摘要塞进用户消息，而是管理配置、存储位置、核验与会话参与资格。CLI 只展示服务端结果并提出设置请求。

固定产物含义
raw_memories.md提炼得到的原始记忆。
MEMORY.md合并后的详细记忆。
memory_summary.md供后续会话使用的摘要。

这些文件位于本服务的 .data/codex/memories/。启动配置固定 CODEX_HOME 与 CODEX_SQLITE_HOME 到本项目的状态目录。查看接口只认这三个固定文件名，拒绝符号链接和硬链接，不接受客户端指定任意路径；摘要最多读取 64 KiB，脱敏后返回。

📌

本阶段不能清空记忆

服务不提供清空接口。关闭开关或会话贡献设置不会删除已经提炼的内容；现有 Thread 也可能保留之前注入的内容。本阶段是单机单用户的状态目录，不提供多用户记忆隔离（每个用户各自的记忆见 s14 用户隔离）。

三道开关：总开关、Agent 策略、会话参与

默认不启用记忆。即使客户端提出“让这个会话贡献记忆”，也必须满足服务端的前提。contribute 与 use 分别表达贡献和使用，不能用一个开关概括。

控制层设置默认与作用
服务总开关AGENT_MEMORY_ENABLED默认 false；总开关关闭时，读取与后台生成即使已配置也不生效。修改需重启。
Agent 策略agent.memory.use / contribute默认都为 false；决定 Agent 能否使用记忆，以及新会话的贡献默认值。contribute 为 false 时也禁止客户端开启贡献。
会话参与/memory contribute on|off控制当前 Thread 的后续参与资格；不能绕过总开关与 Agent 策略。

还有两个独立的服务配置：AGENT_MEMORY_USE 与 AGENT_MEMORY_GENERATE 默认 true，分别配置读取和后台生成，但都以总开关为生效前提。使用记忆还要求 agent.memory.use 为 true。生成配置允许处理，不等于每个 Thread 都有资格贡献，更不等于已经产生摘要。

config/read：核验实际配置，不把开启当成生成

服务启动时先写入 .data/codex/config.toml 中的 [features] 与 [memories]，再向 Codex 调用 config/read。有效配置核验 要检查的不只是总开关，还包括读取、生成、模型、空闲时长和专用记忆工具。

📌

当前配置下，后台合并写不出最终摘要

本阶段使用的 Codex 0.154.0 在原生 shell 与写文件工具关闭时，后台合并不能写出最终记忆摘要。/memory 会报告这一限制，generationCapability 为 blocked。即使三道开关都允许参与、出现中间产物，也不能把它说成最终摘要已经生成。

原生后台按空闲时间等条件运行，不是每轮结束就保存记忆。默认 AGENT_MEMORY_MIN_IDLE_HOURS 为 6，可配置范围为 1–48；等待达到这个值也不能解除上面的写入限制。

查看状态时把三件事分开：effective 表示核验后的配置，hasSummary 表示摘要文件非空，generationCapability 表示当前写入能力判断。generationProgress 为 unknown、modelCompatibility 为 unverified，不能拿配置通过替代真实模型验证；已有摘要也不证明本次运行刚刚生成了它。

会话参与设置：先核对归属，再等当前轮次结束

某一段对话不适合参与后续提炼时，在聊天客户端使用 /memory contribute off。请求送到服务端后，先确认 Thread 属于本项目、Agent 版本兼容，再在 执行边界 内提交原生协议方法。

源码 · stages/s07-memory/server/modules/memory/index.mjs · 第 71–84 行 
  async contribute(threadId, enabled) {
    requireId(threadId, "Thread id");
    if (typeof enabled !== "boolean") throw new AppError("enabled 必须为布尔值。");
    if (enabled && !this.effective?.enabled) throw new AppError("记忆总开关尚未开启，请配置 AGENT_MEMORY_ENABLED 并重启服务。", 409);
    if (enabled && this.config.agent && !this.config.memory.contribute) throw new AppError("当前 Agent 策略禁止会话贡献记忆。", 409);
    await this.sessions.ensure(threadId); // 复用项目会话校验，不能操作其他项目的 Thread。
    return this.sessions.atBoundary(async () => {
      if (this.sessions.sessions.get(threadId)?.activeTurnId) throw new AppError("请在当前 turn 结束后修改记忆参与设置。", 409);
      const mode = enabled ? "enabled" : "disabled";
      await this.rpc.request("thread/memoryMode/set", { threadId, mode });
      return { threadId, mode, note: "设置已提交：只控制此 Thread 后续参与提炼的资格；不停止已运行的后台任务，不立即删除过去贡献的记忆，也不控制读取。" };
    }, { allowBusy: true });
  }
}

关闭贡献之后
这个 Thread 后续不再具有参与提炼的资格。已经运行的后台任务不会因这一命令被停止，过去贡献的记忆不会被删除；如果读取策略仍允许，它仍可使用已有记忆。
开启贡献之前
总开关和 Agent contribute 都必须允许；目标 Thread 还必须没有活动 Turn。想体验设置变化，应先准备服务策略、受控重启并新建会话，再操作 CLI。

查看用 /memory 和 /memory show，设置用 /memory contribute on 或 /memory contribute off。它们都经服务端处理；查看摘要不会触发模型提炼，也没有“清空”或“读取任意文件”的命令。

终端 1 保持服务运行；终端 2 进入同一个阶段目录，执行 npm run chat。以下以 / 开头的命令都输入在这个聊天客户端中。

  1. 先看默认关闭：输入 /memory，查看总开关、使用设置、新 Thread 默认参与和摘要状态。/memory show 查看已有摘要；没有摘要时会提示，不应据此断言服务损坏。
  2. 尝试被拒绝的设置：执行 /new，发送一条普通消息以实际创建会话，等待该 Turn 结束后输入 /memory contribute on。总开关默认关闭时应拒绝；只开总开关而 Agent contribute 仍为 false 时也应拒绝。/new 只清除当前选择，不会立即创建 Thread。
  3. 准备参与策略：停止服务，在 .env 设置 AGENT_MEMORY_ENABLED=true，并在 agents/writing-agent.json 将 agent.memory.use 与 contribute 设为 true，确认 AGENT_MEMORY_USE / GENERATE 未被关闭。重启服务和客户端，执行 /new，发送一条普通消息以创建匹配当前策略的会话，等待该 Turn 结束；在空闲时依次执行 /memory contribute off 与 /memory contribute on。再发送一条普通消息，在该 Turn 仍执行时尝试 /memory contribute off，观察活动轮次检查；若它已结束，则需在后续活动 Turn 中重试。
  4. 核对能力限制：再次 /memory，应看到后台合并写不出最终摘要的说明。不要把开启状态、设置提交成功或中间文件出现当成最终摘要生成成功；本阶段不能通过 CLI 清空记忆。
