Agent 装配：定义它是谁

从可靠运行的服务出发，用一份定义装配角色、Skills 与执行策略，并让会话绑定可核对的版本。

这个云端 Agent 还缺什么：明确的角色与工作方法

上一章，服务已经能保存输入、按顺序执行，并把状态推送给客户端。这个云端 Agent 还缺什么？它还需要一份明确的定义：是谁、按什么方法工作、执行边界是什么。否则每换一种助手，就得在服务代码里寻找那段角色文字。

本章用一份 JSON 装配 Agent。定义交给服务端校验，角色和工作方法交给 Codex 执行；会话与排队消息记录自己使用的装配版本。

定义决定装配内容
agents/writing-agent.json 指定角色文件、原生 Skills、工作区和执行策略。一个服务实例只加载一份定义；AGENT_DEFINITION 可以指定另一份定义文件。
Codex 执行角色与方法
服务端把角色放进 baseInstructions，Codex 负责原生 Skill 的发现、解析和正文注入。普通消息保留用户文本，并附加明确引用的已启用 Skill；角色正文不重复拼入用户消息。

追加消息的目标 Turn 已结束时，服务端会另起一轮接续，把补充说明、目标 Turn ID 和可取得的原任务用户要求引用一起组织成输入，再附加明确引用的已启用 Skill。

📌

本阶段没有任何工具

Agent 不能联网，不能读写资料，也没有跨会话记忆。角色里即使写着“可以执行命令”，也不会获得能力；只读沙箱、关闭原生 shell 和写文件的执行策略仍然有效。服务端读取定义与角色文件，不代表模型获得了文件工具。

一份定义：把角色、Skills 和执行策略装配起来

下面是本阶段完整的 Agent 定义。JSON Schema 先检查结构，再由装配器读取角色和 Skill 文件、核对引用。schemaVersion 是定义格式的版本，agent.version 是 Agent 的声明版本，两者用途不同。

源码 · stages/s05-agent-assembly/agents/writing-agent.json · 第 1–15 行 
{
  "schemaVersion": "1.0",
  "agent": {
    "id": "writing-assistant",
    "version": "1.0.0",
    "instructions": "roles/writing-assistant.md",
    "skills": [],
    "executionRef": "restricted-local"
  },
  "bindings": {
    "workspaceDir": "../workspace",
    "skills": {},
    "executions": { "restricted-local": { "sandbox": "read-only", "approvalPolicy": "never", "nativeShell": false, "nativeFileWrite": false } }
  }
}
逐行解读 · 行号对应源文件

1–3 行：打开定义对象，声明格式版本 1.0，并开始 agent 配置。

4–5 行：声明 Agent 标识与版本；文件内容的实际变化还会由哈希检测，不能只依赖这个版本字符串。

6 行：角色正文相对定义文件目录定位，本例读取 agents/roles/writing-assistant.md。

7 行：默认不启用任何 Skill；发现工作区里的 Skill 不会自动把它加进来。

8–9 行：引用 restricted-local 执行策略，结束 agent 对象。

10–11 行：开始 bindings；工作区路径相对定义文件目录解析为本阶段 workspace。

12 行：Skill 绑定表为空；启用 Skill 时需在这里配置文件位置。

13 行：策略固定为 read-only、never，且原生 shell 和写文件均关闭。schema 不允许借配置放宽这些值。

14–15 行：结束 bindings 与整份定义。

角色正文通过 baseInstructions 同时用于 thread/start 与 thread/resume；启用模型目录时，也写入 instructions_template。它不拼进每一条用户消息。角色描述“怎样回答、哪些事不能做”，执行策略决定程序实际允许什么。

未知字段、缺少必填值、找不到执行策略或必需资源，都会使装配失败。启动后生成的描述符只记录角色哈希、Skill 版本、工作区和执行策略等信息，不复制角色正文或密钥。

Skills：发现了，还要核对是否允许启用

Skill 的发现由 Codex 完成，启用范围由 Agent 定义决定。服务端先调用 skills/list 获取清单，再按已声明文件的真实路径核对启用状态。

源码 · stages/s05-agent-assembly/server/modules/codex/skills.mjs · 第 11–20 行 
  const requested = new Map(agent.skills.map(skill => [skill.path, skill]));
  let discovered = await list(), changed = false;
  for (const skill of discovered) {
    const enabled = requested.has(canonical(skill.path));
    if (skill.enabled !== enabled) {
      await rpc.request("skills/config/write", { path: skill.path, enabled });
      changed = true;
    }
  }
  if (changed) discovered = await list();
逐行解读 · 行号对应源文件

11 行：把允许的 Skill 按文件路径建成 requested 映射，用路径核对而不是只相信显示名称。

12 行：读取 Codex 发现清单，并记录是否需要调整启用状态。

13–14 行：逐个检查发现项：路径在 requested 中，才应当启用。

15–18 行：实际状态与目标状态不同时，通过 skills/config/write 设置，并记下发生了变更。

19 行：结束发现清单的遍历，所有发现项都已按定义核对启用状态。

20 行：如果写过配置，再获取一遍清单，供后续核验实际结果。

必需与可选
定义里的 agent.skills 指定 id 与 required，bindings.skills 提供 path 和 requires。必需绑定或文件缺失时拒绝启动；可选缺失会降级并记录警告。Codex 未发现或未启用必需项也会报错，可选项则不进入有效集合。
只支持原生文本 Skill
bindings.skills 中 requires 非空时，必需 Skill 报错，可选 Skill 降级。若 Codex 发现项声明 dependencies.tools，不论必需还是可选，核验都会报错；不能把方法文本当作额外能力的授权。

范围外 Skill 若仍处于启用状态，核验直接失败。每轮发送前还会重新核验有效集合，要求与启动时一致。用户显式写出 $技能名称 时，服务端为已启用项生成 type: "skill" 输入；Codex 按名称和路径注入正文。服务端不自行解析 SKILL.md。

版本作废：会话与排队消息必须使用同一份定义

角色变了，已经排队的输入还能按另一种角色执行吗？本章选择先拒绝继续。内容哈希 检测源文件变化，描述符哈希则标识核验后的装配结果。

源码 · stages/s05-agent-assembly/server/modules/agents/index.mjs · 第 64–73 行 
  sourceHash() {
    return digest([fs.readFileSync(this.file, "utf8"), fs.readFileSync(this.roleFile, "utf8"),
      ...this.skills.map(skill => digest(fs.readFileSync(skill.path)))]);
  }
  assertCurrent() {
    try { if (this.sourceHash() !== this.expected) this.revoked = true; } catch { this.revoked = true; }
    if (this.revoked) {
      throw new AppError("Agent 定义、角色或 Skill 已变更；后续调用已停止，请受控重启服务后新建会话。", 409, "AGENT_CHANGED");
    }
  }
逐行解读 · 行号对应源文件

64–66 行：sourceHash 读取定义、角色与已绑定 Skill 的内容，组合计算指纹。文件名相同并不代表内容相同。

67–68 行：结束 sourceHash，开始 assertCurrent 当前版本检查。

69 行：读取到的指纹与启动时不同，或读取失败，都把 revoked 设为 true。

70–71 行：一旦标记作废就抛出 AGENT_CHANGED，后续调用不能继续使用这一实例。

72–73 行：结束条件与检查方法；这里没有把 revoked 重置为 false 的路径。

作废会在后续检查时阻止调用；这段逻辑不承诺立刻中断已经运行中的 Turn。即使把文件内容恢复，已作废的实例仍需受控重启。

启动核验完成后，描述符写入 .data/agent-descriptors/<哈希>.json。新建 Thread 时，.data/thread-agents.json 记录它绑定的描述符；消息提交时还保存 agentHash，避免排队后执行依据发生变化。

源码 · stages/s05-agent-assembly/server/modules/agents/index.mjs · 第 88–103 行 
  get bindingsFile() { return path.join(this.root, ".data/thread-agents.json"); }
  bind(threadId) {
    if (!this.descriptor) throw new Error("Agent 尚未完成能力核验。");
    const bindings = readJson(this.bindingsFile, {});
    if (Object.hasOwn(bindings, threadId) && bindings[threadId] !== this.descriptor.hash) this.assertCompatible(threadId);
    bindings[threadId] = this.descriptor.hash; writeJson(this.bindingsFile, bindings);
  }
  assertCompatible(threadId, jobHash) {
    this.assertCurrent();
    const previous = readJson(this.bindingsFile, {})[threadId];
    this.checkBinding(previous, jobHash);
  }
  checkBinding(previous, jobHash) {
    if (!previous) throw new AppError("旧会话没有 Agent 版本绑定，历史已保留；本版不会把旧会话自动迁到新版本，请新建会话。", 409, "LEGACY_THREAD");
    if (previous !== this.descriptor?.hash || (jobHash && jobHash !== previous)) throw new AppError("会话/排队消息的 Agent 版本与当前不兼容，请新建会话；原历史未修改。", 409, "AGENT_INCOMPATIBLE");
  }

88 行：集中定义 Thread 与 Agent 版本绑定文件的位置。

89–90 行：开始绑定新 Thread；尚未完成能力核验、没有描述符时不能绑定。

91–93 行：读取已有绑定；同一 Thread 若已有不同版本，先核对兼容性，再把当前哈希写盘。

94–96 行：结束绑定方法，开始兼容性检查，并先确认当前源文件未变。

97–99 行：读取该 Thread 保存的版本，将它和消息提交时的 jobHash 交给 checkBinding。

100–101 行：开始检查；缺少版本绑定时返回 LEGACY_THREAD，要求新建会话，历史仍保留。

102 行：Thread 版本与当前描述符不同，或排队消息版本与 Thread 不同，都返回 AGENT_INCOMPATIBLE。

103 行：结束绑定检查；只有所有条件通过才会继续准备输入。

恢复会话和每轮发出前都要核对版本；轮次准备阶段失败时，消息标记为 failed、队列暂停，不发送给 Codex。修改定义后先重启；若新描述符与已有 Thread 不兼容，使用 /new。历史记录不会因此被改写。
