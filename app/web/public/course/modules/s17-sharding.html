分片与路由：用户的历史留在自己的主节点

用用户分片定位独立磁盘，用 revision 核对缓存，用 SH001 保护写入；迁移先暂停、等轮次、拷贝，再切换与恢复。

把用户放在一个主节点，让任意入口找到他

一台机器放不下所有用户时，首先要决定搬走什么。请求只是一次通信，用户的原生历史才是后续对话的依据。Codex 将 SQLite 状态、JSONL 历史和记忆保存在这个用户的 CODEX_HOME；如果把连续两条消息随机发往不同磁盘，下一轮未必看得到上一轮的上下文。本章因此按用户分片，以数据库用户 UUID 作为稳定分片键，用户名只用于管理命令的查找。

本章唯一新增单元是 sharding。它接入 HTTP、后台 worker、数据库事务和用户运行环境，回答三个问题：这个用户现在属于哪个分片，哪个节点负责这个分片，切换节点时怎样保持一份可继续使用的历史。协调模块仍管理 lease、Election、任期和失权重入；Hub 仍决定能读哪些知识、能用哪些工具。分片不会代替授权，也不会改变 Codex 的执行循环。

分片与节点是两层不同的关系。一个用户先得到分片 ID，再用 shards 表找到 primary 和 epoch。主节点负责用户业务，control 负责放置与更新元数据。所有存活且完成业务恢复的成员都能服务自己的用户，不再把全部业务集中到 control。

三个节点各自挂载独立的 .data、workspace 和 .runs；只有部署 identity UUID 相同。PG 保存全局账号、Hub 授权和业务记录，Redis 唤醒任务，各节点本地保存自己的原生历史和文件。共享配置目录中的模型网关清单不等于共享用户数据。读取 PG 会话索引能知道会话存在，却不能替代丢失的原生文件。

独立部署入口为 4335，内部 node-a、node-b、node-c 分别使用 4340、4341、4342。Compose 项目网络隔离后，内部端口可以相同，宿主入口必须区分。工作台的本阶段卡片只提供课程和 README 链接；通过 remote.sh tunnel 保持 SSH 隧道，在阶段目录设置本机入口并登录 CLI，才进入真实集群。

策略只算分片，override 优先于两种策略

默认 slots 策略先对用户 ID 做 SHA-256，取前 32 位无符号整数，再对 64 取模。64 个槽按 slot % 3 分给分片 0、1、2，槽数为 22、21、21。槽数量是固定规则，不意味着任意三个用户正好一人占一个分片。示例账号的 UUID 随机生成，观察分布时应看实际映射，而不是用用户名猜测。

range 策略便于直观看到边界：去掉 UUID 的连字符，取第一个十六进制字节，00–54 归 0，55–a9 归 1，aa–ff 归 2。这是对照策略，不是对哈希槽算法的另一种写法。用户 ID 分布不均时会产生热点；所有节点必须选择一致的策略，已有数据不能通过改一个环境变量就当作完成搬迁。

两种 shardOf 都返回分片 ID；slots 与 range 是不同策略。

策略不关心 node-a 或 node-b，它只返回分片 ID。RouteCache 再查询 /codex/shards 下的归属记录，取得 primary 和 epoch。管理员对单个用户的调整通过 /codex/overrides/<userId> 表达，优先级高于槽和范围。override 的值是 JSON 编码的分片字符串；兼容旧数字值时，计算结果仍统一为文本 ID，避免与 PG 的 text 列比较失败。

这份兼容处理保留了诊断所需的原始值。routeStatus 可以同时显示 override 的值与类型、归一化后的 shardId、PG shard_id、本地暂停和 canDispatch。若某个非法 override 无法解释，代码不会悄悄回退到 slots，否则管理员看见一份指定映射，请求却走另一条默认规则，故障会被隐藏。

    // Older controls wrote bare 0/1/2: JSON.parse turns those bytes into numbers.

override 优先；旧数字 override 统一转换为文本分片 ID。

control 初始化时按当前成员排序，把三个分片放到三个成员。没有成员可选时保留空主，后续新增成员只填无主分片。已有主节点离开时保留原 primary，状态变为 unavailable；它的磁盘尚未复制到另一台机器，不能只改一个节点名称就声称完成接管。成员列表变化与分片数据归属变化是两件事。

缓存通过一次 /codex/ 整前缀快照读取 shards、slots 和 overrides，三张表共享同一个 MVCC revision；随后从 revision+1 Watch。一个整前缀 Watch 比三个独立 Watch 更容易判断跨表进度。路由 apply 只处理需要的键，revision 用十进制字符串与 BigInt，不把可能很大的版本号转为不精确的 Number。

快照与事件会交错到达。读快照期间收到的更新不能被旧快照覆盖，代码重放比快照新的后缀；断线或压缩后整表重读，再接新的 revision+1。每五秒对账作为兜底。Watch 提供快速传播，但“路由发布了”不等于“所有进程已经同时应用”，请求协议仍需要版本核对与有限重试。

入口转发带版本，目标主节点再做一次判断

Caddy 根据 /ready 选择任意可服务成员。入口先验证 Bearer，从认证和资源记录确定路由用户，不能接受客户端随意提供的 x-route-user 作为可信归属。非主入口用本地缓存选择成员地址，携带内部节点密钥、用户 ID 与 revision 转发；目标仍重新认证请求，节点密钥不代替用户身份。

目标的 validateRoute 同时检查自己是否是用户主节点，以及自己的缓存 revision 是否不落后于请求。前者防止旧入口把用户送到已经失去归属的节点，后者防止较新的入口把请求交给尚未应用新信息的接收方。任一条件不通过都返回 409 STALE_ROUTE，这只是路由状态不一致，不授权任何节点绕过检查。

export function validateRoute(cache, userId, nodeId, revision) {
  if (!/^\d+$/.test(String(revision)) || cache.routeOf(userId).primary !== nodeId || BigInt(cache.revision) < BigInt(revision)) throw staleRoute();
}
export async function routedRequest({ cache, userId, nodeId, members, local, remote }) {
  for (let attempt = 0; attempt < 2; attempt++) {
    const route = cache.routeOf(userId), address = targetOf(route, members);
    try {
      const result = route.primary === nodeId ? await local(route) : await remote(address, route);
      if (result?.status === 409 && result.headers?.get('x-cluster-error') === 'STALE_ROUTE') {
        await result.body?.cancel(); throw staleRoute();
      }
      return result;
    } catch (error) {
      if (error.code !== 'STALE_ROUTE' || attempt === 1) throw error;
      await cache.refresh();
    }
  }

源码解读

主节点核验版本；只有 STALE_ROUTE 允许整表刷新后重试一次。

routedRequest 最多进入两次循环：第一次请求，发生 STALE_ROUTE 后 refresh，再进行最后一次尝试。HTTP 返回还必须带 x-cluster-error: STALE_ROUTE，普通业务 409 不触发这条路径。刷新不会保证远端立刻追上；第二次仍不一致就向客户端返回错误。无限重试会让持续故障放大成请求风暴，也让用户无法知道任务是否进入执行。

可以按两个例子理解同一个 409。第一种是入口的路由旧了，用户已经切到新主，旧主明确拒绝；入口刷新后改投新主。第二种是入口较新而目标 revision 落后，目标暂时不能确认请求；入口刷新重试时，目标还需要通过 Watch 或对账赶上。这两个窗口都不能靠伪造 revision 或忽略归属消除。

普通 HTTP 转发有 30 秒超时，连接失败或超时返回不可用。SSE 不设同样的总时限，代理保留背压和断开传播，不把长连接当成卡死请求。事件在用户主节点产生，代理不重编 Last-Event-ID；迁移或重启之后事件代次改变，客户端回到快照，不承诺跨节点永久连续的全局事件序号。

转发地址只来自已选择的 etcd 成员。即使外部请求采用 HTTP 绝对形式 URL，也只取 pathname 和 query 拼到成员地址，不能把内部节点密钥发送到请求者指定的外部域名。跳跃头和来路中的节点身份头需要过滤，再由服务端写入可信值。可以用 example.com 作为说明域名，但不能将任意 URL 当作转发目标。

GET /cluster/route?username=… 是管理员诊断入口。它按成员内容里的 nodeId 查询每个节点，观察各自缓存、原始 override 类型、本地暂停和 PG 映射，不自动 refresh，以免把 Watch 滞后证据消掉。真实成员 Map 的键是 /codex/members/node-a 这样的完整 etcd 键，节点身份必须取 value.nodeId，不能把完整键误当作节点名。

观察到的错误可能位置下一步核对
409 STALE_ROUTE归属已变或目标 revision 落后比较各节点缓存 revision，再看一次重试结果。

准入挡住新派发，SH001 挡住错误的行写入

入场检查不能只看“这个容器 ready”。同一个节点可以负责许多用户，其中一个正在迁移时，其余用户还应继续服务。ShardRuntime.owns 要求本节点租约有效且缓存 primary 等于本节点；canDispatch 再看本地暂停，并查询 PG 的 paused 和 shard_id。只有两边映射一致且都未暂停，才允许继续派发；admit 将不满足条件的请求转成不可用错误。

后台任务也要服从同一归属规则。任务扫描、恢复、媒体轮询、知识索引和用户目录初始化都过滤本节点用户。Redis 的 ready key 带 nodeId，但 Redis 只负责唤醒，不能决定哪个节点拥有任务。用户迁走以后，旧节点收到迟到唤醒不代表重新获得执行权，仍要以 PG 和当前缓存判断。

CREATE FUNCTION agent_data.check_shard(owner uuid) RETURNS void
LANGUAGE plpgsql SET search_path=pg_catalog,agent_data AS $$
DECLARE actual record; supplied text := current_setting('app.node',true);
BEGIN
 -- Lock BOTH mappings until commit: migration cannot overtake an old owner's transaction.
 SELECT s.node_id,s.epoch INTO actual FROM user_shards u JOIN shard_owners s USING(shard_id)
 WHERE u.user_id=owner FOR SHARE OF u,s;
 IF actual IS NULL OR actual.node_id IS DISTINCT FROM supplied OR
    actual.epoch::text IS DISTINCT FROM nullif(current_setting('app.shard_epoch',true),'') OR
    current_user <> 'agent_' || replace(supplied,'-','_') THEN
  RAISE EXCEPTION 'missing, foreign or stale shard owner' USING ERRCODE='SH001';
 END IF;
END $$;

check_shard 从 user_shards 联到 shard_owners，锁住用户映射与分片归属行直到提交。映射切换因此要等待已持锁的旧事务结束；切换完成后，新来的旧主事务不能继续用旧归属写入。它同时比较真实 current_user 与 app.node 对应的节点角色，避免仅伪造事务变量就获得另一节点权限。

SH001 表示缺失、外来或过期的分片写入。诊断先取实际被拒行的 owner，不能只用当前 requester 猜测，因为跨用户资源操作的写入目标可能不同。刷新前认为自己是主，刷新后确认用户已移走，只让这一请求失败并保留本节点其他分片；如果仍认为自己是主，或刷新失败，则隔离这个代次并记录诊断。旧 control 的元数据写入仍由 CT001 任期规则保护。

export async function shardFailure(error, generation, origin, statement) {
  if (error.code !== 'SH001' || error.shardDiagnostic) return;
  // The rejected ROW is authoritative. Requester identity alone cannot identify its shard.
  const row = rowFenceDetail(error), owner = row.ownerId;
  let before, after, refreshFailed = false;
  try { before = owner && generation.routes?.routeOf(owner); } catch {}
  try { await generation.routes?.refresh(); after = owner && generation.routes?.routeOf(owner); }
  catch { refreshFailed = true; }
  const believedPrimary = before?.primary === generation.nodeId;
  const isolate = believedPrimary && (refreshFailed || after?.primary === generation.nodeId);
  error.shardDiagnostic = { ownerId: owner || null, believedPrimary, refreshFailed, isolate };
  logFailure(error, generation, origin, statement, 'SH001', {
    classification: isolate ? 'stale-primary' : believedPrimary ? 'ownership-moved' : owner ? 'wrong-shard-write' : 'unknown-row-owner',
    rowRouteBefore: before || null, rowRouteAfter: after || null, ...error.shardDiagnostic,
  });
  if (isolate) generation.isolate?.(refreshFailed ? 'shard-refresh-failed' : 'database-stale-shard');
}

这些锁与触发器保护 PostgreSQL 的写入。已经发生的工具副作用、磁盘写入和外部模型调用不在 SQL 事务里，不能因为数据库拒绝就声称其他动作已撤销。迁移还需要停止新派发、等待在途工作，并明确处理不确定的提交结果。离线测试可以验证错误分支与隔离决策，实际触发器和锁等待必须用真实 PostgreSQL 验收。

迁移先等旧轮次结束，再移动文件与发布新归属

管理员执行 cluster move 时，请求由 control 编排。它持有单用户 advisory lock，先把 PG 的 paused 设为 true，再请求源节点关闭新入场。已经进入 starting、running 或 steering 的轮次允许完成；迁移等待在途 HTTP、进程引用、执行中任务、索引和媒体工作结束，然后关闭用户进程与 SSE。迁移不是强制中断后把同一任务在另一台机器重跑。

暂停不是一个仅存在于内存的按钮。PG 的持久暂停覆盖节点重启和控制切换，本地暂停则及时关住当前节点的入场门。每次内部查询仍有超时，但管理员编排可以等长轮次，CLI 不使用整体 15 秒超时。等待过久时需要检查尚未完成的工作，而不是跳过 drain 直接复制正在写的 SQLite。

  if (!SHARDS.includes(shardId)) throw new Error('分片必须是 0、1、2。');
  const source = cache.routeOf(userId), target = cache.shards[shardId];
  if (!target?.primary) throw unavailable('目标分片无主节点。');
  if (source.shardId === shardId) {
    if (await control.isPaused?.(userId)) { await resume(source.primary, userId); await control.pause(userId, false); return { resumed: true, shardId }; }
    return { unchanged: true };
  }
  let switched = false, paused = false, releaseStarted = false;
  try {
    await control.pause(userId, true); paused = true;
    await pause(source.primary, userId);
    await drain(source.primary, userId);
    await copy(source.primary, target.primary, userId);
    await control.switchUser(userId, shardId); switched = true;
    await resume(target.primary, userId);
    await resume(source.primary, userId);
    releaseStarted = true;
    await control.pause(userId, false);
    return { userId, from: source.shardId, shardId };
  } catch (error) {
    if (releaseStarted) {
      // A lost resume COMMIT reply can mean the target already dispatched. Never revive the old copy.
      error.rollbackFailed = true;
      await control.pause(userId, true).catch(() => {});
      throw error;
    }
    try {
      if (switched) await control.switchUser(userId, source.shardId);
      if (paused && !error.rollbackFailed) { await resume(source.primary, userId); await control.pause(userId, false); }
    } catch { error.rollbackFailed = true; }
    // Uncertain rollback stays paused. A new control must never automatically resume an incomplete copy.
    throw error;

源码解读

PG 映射与 etcd override 按控制任期更新，但不构成跨库原子事务。

switchUser 先更新 PG 映射，在控制任期保护下发布 override，然后确认并提交。这些动作跨越 PG 与 etcd，不是一个分布式原子事务。paused 在过程中保持 true，映射锁阻止旧事务越过切换；缓存短暂领先 SQL 时仍由 SH001 拒写。两端刷新并解除本地暂停后，control 最后把持久 paused 改回 false，目标才可以接受新派发。

失败处理要看发生在哪一步。copy 失败没有切换，确认补偿后源节点继续服务。切换阶段的 COMMIT 回复丢失，暂停期间同时补偿 PG 与 override；如果无法确认回滚，保持暂停，交给管理员核对。更特殊的是解除暂停的 COMMIT 回复丢失：目标可能已经派发，不能盲目恢复旧磁盘。实现重新持久化暂停，保留目标归属，再由管理员重试核对。源副本保留并不意味着它仍有服务权。

迁移成功后的验收是用同一用户继续同一会话。先查 cluster route 看各节点缓存与 PG 映射，再通过任意入口续聊，确认请求到新主且历史可读。只看到 tar 成功或 override 改变，不足以证明整条流程完成。节点磁盘已损坏或源节点离线时，这套手动迁移也不能凭空恢复数据。

授权、故障与实验：分别核对每一层证据

共享知识库仍只有所有者主节点的一份权威内容。被授权者的节点先按现有 kb、mount 与 Hub 检查，再向所有者节点发内部只读请求；所有者用 requester 的新权限快照再次核对，最后读取自己的文件或不可变 blob。不能切成 owner 身份读取来省掉第二次授权，否则两次检查之间发生的撤销就可能被绕开。

内部知识接口只允许 read、search、pages 和 resource。跨分片 RAG 查询在请求者节点生成 query embedding 并按请求者计费，内容读取仍由所有者主节点执行。未授权者看到 404，失效来源和未挂载知识库仍被拒绝。迁移不会让一份被撤销的授权恢复，也不会因为文件复制到了新节点就改变 Hub 的资源所有者。

故障实验先用 cluster status 确认分片归属，再停止选定节点。成员租约约十秒到期以后，该节点负责的分片返回不可用，其他分片继续服务；重启后原主恢复并核对未确认任务，不自动重放可能已产生副作用的轮次。暂停进程超过 TTL 后再恢复，也需要隔离旧代并按重新加入规则建立新租约，不能延续过期的服务权。

本章没有副本、复制位点、自动提升、故障切换或自动重平衡。etcd、PostgreSQL、Redis 与模型网关在教学部署中仍是单实例，三个业务节点不能消除这些依赖的单点。手动迁移要求源目标在线；失去主磁盘就失去该用户的原生历史，PG 会话索引不是它的备份。系统能证明的是归属、有限重试、数据库拒写和停写后的手动搬迁，不能把这些能力扩展成无损自动恢复承诺。
