分片与路由：用户的历史留在自己的主节点

用用户分片定位独立磁盘，用 revision 核对缓存，用 SH001 保护写入；迁移先暂停、等轮次、拷贝，再切换与恢复。

把用户放在一个主节点，让任意入口找到他

一台机器放不下所有用户时，首先要决定搬走什么。请求只是一次通信，用户的原生历史才是后续对话的依据。Codex 将 SQLite 状态、JSONL 历史和记忆保存在这个用户的 CODEX_HOME；如果把连续两条消息随机发往不同磁盘，下一轮未必看得到上一轮的上下文。本章因此按用户分片，以数据库用户 UUID 作为稳定分片键，用户名只用于管理命令的查找。

本章唯一新增单元是 sharding。它接入 HTTP、后台 worker、数据库事务和用户运行环境，回答三个问题：这个用户现在属于哪个分片，哪个节点负责这个分片，切换节点时怎样保持一份可继续使用的历史。协调模块仍管理 lease、Election、任期和失权重入；Hub 仍决定能读哪些知识、能用哪些工具。分片不会代替授权，也不会改变 Codex 的执行循环。

分片与节点是两层不同的关系。一个用户先得到分片 ID，再用 shards 表找到 primary 和 epoch。主节点负责用户业务，control 负责放置与更新元数据。所有存活且完成业务恢复的成员都能服务自己的用户，各自承担所属用户的业务。

三个节点各自挂载独立的 .data、workspace 和 .runs；只有部署 identity UUID 相同。PG 保存全局账号、Hub 授权和业务记录，Redis 唤醒任务，各节点本地保存自己的原生历史和文件。共享配置目录中的模型网关清单不等于共享用户数据。读取 PG 会话索引能知道会话存在，却不能替代丢失的原生文件。

独立部署入口为 4335，内部 node-a、node-b、node-c 分别使用 4340、4341、4342。Compose 项目网络隔离后，内部端口可以相同，宿主入口必须区分。工作台的本阶段卡片只提供课程和 README 链接；通过 remote.sh tunnel 保持 SSH 隧道，在阶段目录设置本机入口并登录 CLI，才进入真实集群。

阅读后面的流程时，要把“有权接收”“有权执行”和“有权写入”分开观察。Caddy 的 ready 检查只选择可接入节点；入口随后按用户定位，主节点继续检查暂停与映射，SQL 最后检查实际行归属。前一个检查通过，不能提前替后一个检查作承诺。

策略只算分片，override 优先于两种策略

默认 slots 策略先对用户 ID 做 SHA-256，取前 32 位无符号整数，再对 64 取模。64 个槽按 slot % 3 分给分片 0、1、2，槽数为 22、21、21。槽数量是固定规则，不意味着任意三个用户正好一人占一个分片。示例账号的 UUID 随机生成，观察分布时应看实际映射，而不是用用户名猜测。

range 策略便于直观看到边界：去掉 UUID 的连字符，取第一个十六进制字节，00–54 归 0，55–a9 归 1，aa–ff 归 2。这是对照策略，不是对哈希槽算法的另一种写法。用户 ID 分布不均时会产生热点；所有节点必须选择一致的策略，已有数据不能通过改一个环境变量就当作完成搬迁。

export const defaultSlots = () => Object.fromEntries(Array.from({ length: SLOT_COUNT }, (_, n) => [n, SHARDS[n % 3]]));

export const strategies = {
  slots: { shardOf: (userId, map) => map.slots[slotOf(userId)] },
  range: { shardOf(userId) {
    const prefix = String(userId).replaceAll('-', '').slice(0, 2);
    if (!/^[a-f0-9]{2}$/i.test(prefix)) throw new Error('范围策略需要十六进制用户 ID。');
    const n = parseInt(prefix, 16);
    return n < 0x55 ? '0' : n < 0xaa ? '1' : '2';

slots 与 range 都返回分片 ID；完整策略对象不包含节点选择。

策略不关心 node-a 或 node-b，它只返回分片 ID。RouteCache 再查询 /codex/shards 下的归属记录，取得 primary 和 epoch。管理员对单个用户的调整通过 /codex/overrides/<userId> 表达，优先级高于槽和范围。override 的值是 JSON 编码的分片字符串；兼容旧数字值时，计算结果仍统一为文本 ID，避免与 PG 的 text 列比较失败。

这份兼容处理保留了诊断所需的原始值。routeStatus 可以同时显示 override 的值与类型、归一化后的 shardId、PG shard_id、本地暂停和 canDispatch。若某个非法 override 无法解释，代码不会悄悄回退到 slots，否则管理员看见一份指定映射，请求却走另一条默认规则，故障会被隐藏。

  routeOf(userId) {
    // Older controls wrote bare 0/1/2: JSON.parse turns those bytes into numbers.
    // Keep the raw override for diagnostics, but all routing/PG comparisons use text IDs.
    const raw = this.overrides[userId] ?? this.strategy.shardOf(userId, this);

    const owner = this.shards[shardId];
    return { shardId, primary: owner?.primary ?? null, epoch: owner?.epoch ?? null, revision: this.revision };

源码解读

override 优先；合法数字值归一化为文本分片 ID，非法值不回退到默认策略。

control 初始化时按当前成员排序，把三个分片放到三个成员。没有成员可选时保留空主，后续新增成员只填无主分片。已有主节点离开时保留原 primary，状态变为 unavailable；它的磁盘尚未复制到另一台机器，不能只改一个节点名称就声称完成接管。成员列表变化与分片数据归属变化是两件事。

缓存通过一次 /codex/ 整前缀快照读取 shards、slots 和 overrides，三张表共享同一个 MVCC revision；随后从 revision+1 Watch。一个整前缀 Watch 比三个独立 Watch 更容易判断跨表进度。路由 apply 只处理需要的键，revision 用十进制字符串与 BigInt，不把可能很大的版本号转为不精确的 Number。

快照与事件会交错到达。读快照期间收到的更新不能被旧快照覆盖，代码重放比快照新的后缀；断线或压缩后整表重读，再接新的 revision+1。每五秒对账作为兜底。Watch 提供快速传播，但“路由发布了”不等于“所有进程已经同时应用”，请求协议仍需要版本核对与有限重试。

输入与状态处理结果不能推断的结论
没有 override使用所选 shardOf 策略不能据此跳过 PG 用户映射。
合法 override优先采用指定分片不能据此认定主节点在线。

原 primary 离线503 SHARD_UNAVAILABLE不能自动读取另一节点的磁盘。

入口转发带版本，目标主节点再做一次判断

Caddy 根据 /ready 选择任意可服务成员。入口先验证 Bearer，从认证和资源记录确定路由用户，不能接受客户端随意提供的 x-route-user 作为可信归属。非主入口转发原用户令牌，并写入自己的 x-node-id、x-node-key、路由用户 ID 与 revision；目标重新认证用户和调用节点，节点密钥不代替用户身份。

目标的 validateRoute 同时检查自己是否是用户主节点，以及自己的缓存 revision 是否不落后于请求。前者防止旧入口把用户送到已经失去归属的节点，后者防止较新的入口把请求交给尚未应用新信息的接收方。任一条件不通过都返回 409 STALE_ROUTE，这只是路由状态不一致，不授权任何节点绕过检查。

export function validateRoute(cache, userId, nodeId, revision) {
  if (!/^\d+$/.test(String(revision)) || cache.routeOf(userId).primary !== nodeId || BigInt(cache.revision) < BigInt(revision)) throw staleRoute();
}
export async function routedRequest({ cache, userId, nodeId, members, local, remote }) {
  for (let attempt = 0; attempt < 2; attempt++) {
    const route = cache.routeOf(userId), address = targetOf(route, members);
    try {
      const result = route.primary === nodeId ? await local(route) : await remote(address, route);
      if (result?.status === 409 && result.headers?.get('x-cluster-error') === 'STALE_ROUTE') {
        await result.body?.cancel(); throw staleRoute();
      }
      return result;
    } catch (error) {
      if (error.code !== 'STALE_ROUTE' || attempt === 1) throw error;
      await cache.refresh();
    }
  }
}
源码解读

主节点核对归属与 revision；仅 STALE_ROUTE 允许 refresh 后再试一次，普通业务 409 不触发重试。

routedRequest 最多进入两次循环：第一次请求，发生 STALE_ROUTE 后 refresh，再进行最后一次尝试。HTTP 返回还必须带 x-cluster-error: STALE_ROUTE，普通业务 409 不触发这条路径。刷新不会保证远端立刻追上；第二次仍不一致就向客户端返回错误。无限重试会让持续故障放大成请求风暴，也让用户无法知道任务是否进入执行。

可以按两个例子理解同一个 409。第一种是入口的路由旧了，用户已经切到新主，旧主明确拒绝；入口刷新后改投新主。第二种是入口较新而目标 revision 落后，目标暂时不能确认请求；入口刷新重试时，目标还需要通过 Watch 或对账赶上。这两个窗口都不能靠伪造 revision 或忽略归属消除。

普通 HTTP 转发有 30 秒超时，连接失败或超时返回不可用。SSE 不设同样的总时限，代理保留背压和断开传播，不把长连接当成卡死请求。事件在用户主节点产生，代理不重编 Last-Event-ID；迁移或重启之后事件代次改变，客户端回到快照，不承诺跨节点永久连续的全局事件序号。

转发地址只来自已选择的 etcd 成员。即使外部请求采用 HTTP 绝对形式 URL，也只取 pathname 和 query 拼到成员地址，不能把内部节点密钥发送到请求者指定的外部域名。forwardHeaders 过滤跳跃头和来路中的 x-node-id、x-node-key、x-route-user、x-route-revision，再由服务端写入本次转发值。

每个节点持有独立的 AGENT_NODE_KEY_A/B/C 中属于自己的明文密钥，以及全部节点的 SHA-256 验证哈希。authenticateNode 用 x-node-id 选择预置哈希，再以 timingSafeEqual 核对来钥的哈希，验证通过才返回调用节点身份。仅自报 node-a 或知道自己的节点密钥，不能冒充另一个节点；内部接口还要按具体操作检查权限，不能把“来自集群”当作管理员授权。

export function authenticateNode(headers, keyHashes) {

准入挡住新派发，SH001 挡住错误的行写入

入场检查不能只看“这个容器 ready”。同一个节点可以负责许多用户，其中一个正在迁移时，其余用户还应继续服务。ShardRuntime.owns 要求本节点租约有效且缓存 primary 等于本节点；canDispatch 再看本地暂停，并查询 PG 的 paused 和 shard_id。只有两边映射一致且都未暂停，才允许继续派发；admit 将不满足条件的请求转成不可用错误。

  async canDispatch(userId) {
    if (!this.owns(userId) || this.paused.has(userId)) return false;
    const row = (await this.pool.query('SELECT paused,shard_id FROM agent_data.user_shards WHERE user_id=$1', [userId])).rows[0];
    return this.owns(userId) && !this.paused.has(userId) && row && !row.paused && row.shard_id === this.cache.routeOf(userId).shardId;
  }
  async admit(userId) { if (!await this.canDispatch(userId)) throw unavailable('用户正在迁移、归属尚未初始化或本节点不是分片主节点。'); }

后台任务也要服从同一归属规则。任务扫描、恢复、媒体轮询、知识索引和用户目录初始化都过滤本节点用户。Redis 的 ready key 带 nodeId，但 Redis 只负责唤醒。媒体 tick 在每次 poll 前调用 canDispatch；暂停期间不启动新轮询。pollingOwners 在异步准入检查完成前就登记该次工作，drain 通过 waitOwner 等待已经开始的检查与轮询结束，避免复制期间又有媒体结果写盘。

  tick() {
    if (this.running || this.controller.signal.aborted) return this.running;
    this.running = (async () => {
      for (const job of await this.store.pending()) {
        if (this.controller.signal.aborted) break;

        const pending = (async () => {
          if (this.sharding && !await this.sharding.canDispatch(job.ownerId)) return;

        })();

        try { await pending; } finally { this.pollingOwners.delete(job.ownerId); }
      }
    })().finally(() => { this.running = null; });
    return this.running;

CREATE OR REPLACE FUNCTION agent_data.check_shard(owner uuid) RETURNS void
LANGUAGE plpgsql SET search_path=pg_catalog,agent_data AS $$
DECLARE actual record; supplied text := current_setting('app.node',true);
BEGIN
 -- Lock BOTH mappings until commit: migration cannot overtake an old owner's transaction.
 SELECT s.node_id,s.epoch,u.shard_id,u.paused INTO actual FROM user_shards u JOIN shard_owners s USING(shard_id)
 WHERE u.user_id=owner FOR SHARE OF u,s;
 IF actual IS NULL OR (actual.paused AND EXISTS(SELECT 1 FROM move_operations WHERE user_id=owner AND state IN ('copying','copied','switched','failed'))) OR actual.node_id IS DISTINCT FROM supplied OR
    actual.epoch::text IS DISTINCT FROM nullif(current_setting('app.shard_epoch',true),'') OR
    current_user <> 'agent_' || replace(supplied,'-','_') THEN
  RAISE EXCEPTION 'missing, foreign or stale shard owner' USING ERRCODE='SH001', DETAIL=json_build_object(
    'ownerId',owner,'shardId',actual.shard_id,'primary',actual.node_id,'epoch',actual.epoch::text,
    'nodeId',supplied,'suppliedEpoch',current_setting('app.shard_epoch',true))::text;
 END IF;
END $$;
源码解读

两张映射持锁到提交；核对真实 SQL 角色与 epoch，并在暂停且操作单处于 copying、copied、switched 或 failed 时拒写。

check_shard 从 user_shards 联到 shard_owners，锁住用户映射与分片归属行直到提交；切换必须等待已持锁的事务。它比较真实 current_user 与 app.node 对应的节点角色，并核对 epoch。操作单为 paused 时，已开始的轮次可以完成收尾写入；进入 copying、copied、switched 或 failed 且用户仍暂停时，数据库拒绝该用户业务写入。这样停写边界同时约束后台迟到写入。

行 owner 可能直接在 owner_id 或 user_id，也可能通过会话、知识库、资源引用追溯。UPDATE 同时检查 OLD 和 NEW，防止把别人的数据改成自己的 owner 后绕过保护。全局账号和登录令牌表服务所有节点，但节点角色校验之外还有列级权限：users 只允许 UPDATE(plan_id)；auth_sessions 允许 INSERT 与 UPDATE(last_seen_at, revoked_at)，无 DELETE；agent_versions 只允许 INSERT。建号、用户名、角色、密码和禁用状态由 maintenance 运维连接管理，plans、imports 也不向节点开放业务写入。

export async function shardFailure(error, generation, origin, statement) {
  if (error.code !== 'SH001' || error.shardDiagnostic) return;
  // The rejected ROW is authoritative. Requester identity alone cannot identify its shard.
  const row = rowFenceDetail(error), owner = row.ownerId;
  let before, after, refreshFailed = false;
  try { before = owner && generation.routes?.routeOf(owner); } catch {}
  try { await generation.routes?.refresh(); after = owner && generation.routes?.routeOf(owner); }
  catch { refreshFailed = true; }
  const believedPrimary = before?.primary === generation.nodeId;
  const isolate = believedPrimary && (refreshFailed || after?.primary === generation.nodeId);
  error.shardDiagnostic = { ownerId: owner || null, believedPrimary, refreshFailed, isolate };
  logFailure(error, generation, origin, statement, 'SH001', {
    classification: isolate ? 'stale-primary' : believedPrimary ? 'ownership-moved' : owner ? 'wrong-shard-write' : 'unknown-row-owner',
    rowRouteBefore: before || null, rowRouteAfter: after || null, ...error.shardDiagnostic,
  });
  if (isolate) generation.isolate?.(refreshFailed ? 'shard-refresh-failed' : 'database-stale-shard');
}

export async function authorizeMove(pool, { operationId, userId, caller, receiver, step, target }) {
  if (!/^[a-f0-9]{8}-[a-f0-9]{4}-[a-f0-9]{4}-[a-f0-9]{4}-[a-f0-9]{12}$/.test(operationId || '')) throw denied();
  const op = (await pool.query('SELECT * FROM agent_data.move_operations WHERE id=$1 AND expires_at > now()', [operationId])).rows[0];
  const states = { pause: ['paused'], drain: ['paused'], copy: ['copying'], transfer: ['copying'], content: ['copying'], resume: ['switched'] };
  if (!op || op.user_id !== userId || !states[step]?.includes(op.state)) throw denied();
  const data = ['transfer','content'].includes(step);
  if (caller !== (data ? op.source_node : op.control_node) ||
      (step === 'resume' ? ![op.source_node, op.target_node].includes(receiver) : receiver !== (data ? op.target_node : op.source_node)) ||
      (target !== undefined && target !== op.target_node)) throw denied();
  return op;
}

export async function moveUser({ userId, shardId, control, pause, drain, copy, resume }) {
  if (!SHARDS.includes(shardId)) throw new Error('分片必须是 0、1、2。');
  const term = control.coordination?.term();
  const op = await control.beginMove(userId, shardId);
  if (!op) return { unchanged: true };
  try {
    await pause(op.source_node, userId, op.id);
    await drain(op.source_node, userId, op.id);
    await control.advanceMove(op.id, 'paused', 'copying');
    await copy(op.source_node, op.target_node, userId, op.id);
    await control.advanceMove(op.id, 'copying', 'copied');
    await control.switchUser(userId, shardId, op.id);
    await resume(op.target_node, userId, op.id);
    await resume(op.source_node, userId, op.id);
    await control.finishMove(op);
    return { userId, from: op.from_shard, shardId, operationId: op.id };
  } catch (error) {
    // Never revive an old disk after an uncertain COMMIT or publish; retain both copies for recovery.
    await control.failMove(op.id, term).catch(() => { error.rollbackFailed = true; });
    throw error;
  }
}

copied → switched 与 PG 用户归属在同一任期事务内提交，之后才发布 etcd override；失败记录操作单并保持暂停。

switchUser 先在 PG 事务中核对操作单的用户、源分片、目标和暂停，将 copied 推进为 switched 并更新 user_shards；locked 返回代表 COMMIT 完成，此后才 guardedPut 发布 etcd override。这个顺序避免先发布路由、数据库却仍为旧归属。两库没有原子提交，仍可能出现 PG 已提交而 etcd 未发布的窗口；paused 持续阻止新派发，操作单与行触发器约束写入。两端刷新并解除本地暂停后，finishMove 在同一事务将单据推进为 resumed 并解除 PG 暂停。

失败统一进入 failMove：用原任期受 PG 锁保护地记录 failed 并保持 paused，不自动把 PG 或 override 改回源分片。copy 失败时归属仍在源，但也不自动恢复；切换或收尾 COMMIT 回复丢失时，以数据库实际状态为准，保留两份磁盘供运维核对。若较新 control 已取得任期锁，旧 control 的失败记录也会被拒绝，调用方标记 rollbackFailed 表示无法确认收尾。此字段不是自动回滚成功的承诺。

control 对账只采纳最新操作单处于 switched/resumed 且目标匹配的 override，更新也只针对暂停用户；缺单、未复制完成或 failed 的 override 会被记录并忽略。beginMove 拒绝已暂停用户，重复 move 不能充当自动恢复。管理员需核对操作单、PG、etcd 与两端副本后再安排恢复。

迁移成功后的验收是用同一用户继续同一会话。先查 cluster route 看各节点缓存与 PG 映射，再通过任意入口续聊，确认请求到新主且历史可读。只看到 tar 成功或 override 改变，不足以证明整条流程完成。节点磁盘已损坏或源节点离线时，这套手动迁移也不能凭空恢复数据。

真实数据库测试使用专用临时实例，验证旧节点 SQL 被 SH001 拒绝，更新 owner 的 OLD 与 NEW 都受约束，映射切换必须等待旧事务结束。etcd 集成测试使用独立认证实例，核对快照、Watch、控制任期和键空间权限。节点凭据的静态 RBAC 限制 /codex/ 前缀，“只有 control 写归属”由受信任节点的 guardedPut API 动态实现；不能将 API 拒绝等同于原始节点凭据完全没有 put 能力。

Linux UID 集成测试需要能切换 uid/gid 的 0:1000 容器。原生历史是用户私有文件，服务进程不依赖 DAC_OVERRIDE 直接打开；辅助进程以用户身份读写。知识维护完成后还要执行 Workflow 验收，验收拿到的 runtime.workspaceDir 已是用户目录，不能再追加 users/<id>。否则文件产物会查错位置，知识维护即使已生成有效 Wiki 也会因目录访问失败进入 needs-review。

部署操作按 README 初始化账号与模型网关，再启动 etcd、PG、Redis、各节点和入口。etcd 健康检查使用只读 health 键的独立账号，不复用 root；升级已有部署保留原凭据与数据卷，只补所需配置。备份按节点保留各自磁盘，停机操作覆盖全部节点，不能只停 control 后让其他成员继续写。这里的配置和启动不是课程网页自动替用户执行的动作。

故障实验先用 cluster status 确认分片归属，再停止选定节点。成员租约约十秒到期以后，该节点负责的分片返回不可用，其他分片继续服务；重启后原主恢复并核对未确认任务，不自动重放可能已产生副作用的轮次。暂停进程超过 TTL 后再恢复，也需要隔离旧代并按重新加入规则建立新租约，不能延续过期的服务权。

本章没有副本、复制位点、自动提升、故障切换或自动重平衡。etcd、PostgreSQL、Redis 与模型网关在教学部署中仍是单实例，三个业务节点不能消除这些依赖的单点。手动迁移要求源目标在线；失去主磁盘就失去该用户的原生历史，PG 会话索引不是它的备份。系统能证明的是归属、有限重试、数据库拒写和停写后的手动搬迁，不能把这些能力扩展成无损自动恢复承诺。
