s14

用户隔离：让 owner 落到进程与文件权限

请求确定身份，运行环境池提供连接，系统 uid/gid 约束文件访问；每次启动、读取和回收都有明确的用户范围。

接口有归属之后，原生状态也需要边界

登录让服务知道请求来自谁，owner 检查让资源查询只返回这个用户的数据。但一个 Codex App Server 还管理原生历史、索引、记忆和 Skill 副本。即使 HTTP 接口已经检查归属，这些底层状态仍需要说明：它们属于哪个用户，保存在哪个目录，由哪个进程读取。s14 把用户边界落实到运行环境，让每个 owner 拥有自己的 App Server、CODEX_HOME、工作目录和系统身份。

用户运行环境不等于一个请求，也不等于一条 Thread。一个用户可以有多个会话，它们进入同一用户的连接；不同用户不会因为使用相同 Agent 配置而共用原生状态。服务仍维护全局业务队列和模型预算，所有用户合计最多执行 2 轮。池中允许 4 个进程常驻，表达的是另一种容量。

组件负责的边界不能代替什么
RuntimeStore事务中分配 uid，持久化用户与目录映射，监听禁用通知。映射存在不代表进程已经启动。
RuntimePool控制 4 个名额、启动 Promise、租约、超时与回收。池容量不代替轮次并发和预算。
RuntimeRouter使用认证上下文或持久任务 owner 选连接，隔离通知和工具回调。用户提交的 owner 字符串不能作为授权凭据。
CodexConnection执行 stdio JSON-RPC，按 uid/gid、固定 umask 和白名单环境启动。执行循环不决定 HTTP 身份和资源权限。
SessionService / MessageService核对会话与任务归属，派发轮次，按 owner 恢复不确定状态。进程退出不意味着已经执行的任务可以安全重发。

用户 uid 从 10001 顺序分配，gid 与 uid 同号，不依赖系统账号文件。user_runtimes 保存 user_id、uid、codex_home、created_at，并由 instance_id 区分数据实例。第一个 admin 保留既有原生目录的绝对位置；后续用户使用各自的原生目录。进程被回收后，映射、原生历史和业务记录仍然存在，下一次访问可以重新启动并恢复会话。

路径属于系统映射的一部分，不能从聊天参数里随意覆盖。工具目录继续作为受信配置；Skill 的安装位置、核验结果和记忆对象属于各用户。启动时会同步 Agent 包 Skill 到当前用户目录，并向这个用户的 Codex 核验。真正的 Skill 输入和会话 cwd 都使用当前用户目录，避免一次用户切换影响另一个用户的运行状态。

首次请求：预留名额，再共享同一次启动

假设同一个账号的两个客户端几乎同时发起首次请求。服务不能只检查“现在有没有 ready 连接”，否则两个请求都会看到没有连接，各启动一个进程。池要把 starting 也作为已经占用名额的状态：第一个请求创建池项并保存启动 Promise，后来的同 owner 请求找到这个池项，等待同一份结果。这就是 single-flight。

withOwner 首先要求存在可信 owner，再处理当前上下文内的同 owner 嵌套调用。外层请求通过 serial 进入 admission：检查池是否关闭、账号是否禁用，再查已有池项。串行区域保护名额和租约，耗时的启动与核验则在锁外等待。这样一个用户启动较慢时，其他用户仍可申请自己的运行环境。

身份与上下文：owner 为空直接拒绝。同 owner 的 ready 嵌套调用复用当前 value；池关闭或账号禁用时不能沿用这个快捷路径。

串行 admission：先调用 assertEnabled 核对账号，再读取 entries。closing 项不能借用，等待清理时仍应返回繁忙。

占位与 Promise：entries.set 发生在请求等待之前。entry.ready 只在新项创建时赋值，同用户的请求自然汇合到一个 Promise。

请求租约：refs 在等待前增加，覆盖启动等待和业务执行。try / finally 确保成功、异常都减少租约并更新 lastUsed。

连接路由：await entry.ready 之后还检查 state；通过 context.run 才把 operation 放入当前用户运行环境。取得旧引用不等于可以使用已关闭连接。

启动有 30 秒期限。create 必须响应 AbortSignal，并在发布连接前再次检查是否已中止。超时后不能让一个晚到的进程重新成为可用对象：请求应失败，池项进入 closing，随后等待创建收尾并关闭晚到进程。清理完成才删除池项；否则旧进程尚未退出、新进程已经启动的瞬间，会突破最多 4 个进程的约束。

服务级 /ready 与用户连接 ready 也要分开看。运行环境按需启动，服务就绪并不意味着所有用户都完成了 Codex 初始化、Skill、工具和记忆核验。首次用户请求才会触发自己的启动链路。部署探测通过可以说明服务具备接入条件，不能替用户的实际启动结果作保证。

HTTP 使用认证后的 owner；后台派发使用持久任务记录的 owner；通知带上连接启动时绑定的 owner。工具回调还要比较 connectionOwner、task.userId 和 session.ownerId。只有这些身份一致，才继续执行账号状态、轮次和 PermissionGate 检查。参数里自称的身份不进入授权链，后台任务也不能因为复用了异步回调而借到别人的请求上下文。

容量到顶：先证明空闲，再等待旧进程退出

池满时，第 5 个用户不能拿一个正在执行任务的进程让位。候选必须 ready，refs 为 0，且没有执行中轮次和排队任务。lastUsed 只决定检查顺序，并不能单独证明对象空闲。池按时间从旧到新逐个检查，找到第一个满足条件的对象才回收；忙碌状态查询出错时保守跳过本轮回收。

源码 · runtimes/pool.mjs · 第 129–144 行
  async remove(entry, error) {
    if (entry.removing) return entry.removing;
    entry.state = 'closing';
    clearTimeout(entry.idleTimer);
    entry.controller.abort(error || new Error('运行环境已回收。'));
    entry.removing = (async () => {
      // 先停止进程与工具；确认任务状态后才释放名额，防止迟到通知与新进程交叉。
      if (entry.value) await this.closeValue(entry.value);
      else await entry.creating?.then(value => this.closeValue(value), () => {});
      if (error) await this.onLost(entry.owner, error);
      await this.onRemoved(entry.owner);
      if (this.entries.get(entry.owner) === entry) this.entries.delete(entry.owner);
    })();
    return entry.removing;
  }

逐段解读

共用清理：entry.removing 存在时直接返回，避免同一对象并发清理。设置 closing 并中止启动后，其他请求不能继续取得它。

先停止：已有 value 就 await closeValue；启动尚未返回则等待 creating 收尾并关闭结果。关闭前不能释放名额。

再收尾：带 error 时调用 onLost 核对该 owner 的任务状态，然后 onRemoved 清理缓存。最后确认 Map 中仍是当前 entry 才删除。

closeValue 同样按对象共享一次清理 Promise。它先尝试正常关闭；如果关闭抛错或超过 10 秒，进入强制终止兜底。隔离模式没有额外增加 KILL capability，而是用 SETUID/SETGID 启动同 uid/gid 的短命信号发送器。连接直接 exec 原生 Codex，可减少只杀掉包装器而留下孙进程的风险。

这里的“4 个进程”不能读成“4 轮同时执行”。进程池决定哪些用户的原生运行环境保持活动，MessageService 仍在全局最多派发 2 轮。一个 ready 进程可以暂时没有轮次，也可以有排队任务等待预算或并发名额。只要存在这些任务，就不能仅凭当前没有输出把它当成空闲对象。

回收只改变活动进程与内存缓存。下一次请求重新进入 withOwner，读取相同用户映射，使用自己的原生状态恢复。对使用者而言可能增加一次启动延迟，但不会因为池满而把会话转给其他用户的进程，也不会用另一个用户的 HOME 继续执行。

最终 spawn 与文件读取共同守住系统边界

系统权限必须在最终创建进程的位置生效，不能只停留在目录名称里。用户目录由用户 uid 所有，服务共享组为 gid 1000，模式为 2770。setgid 让目录内新文件继承共享组；用户子进程不加入这个共享组，因此不能靠共享组身份读取别人的目录。父目录只开放必要的穿越权限，用户边界目录不开放其他用户访问。

容器服务以 0:1000 运行，删除全部 capability 后只加回 SETUID、SETGID、CHOWN、FOWNER，并设置 no-new-privileges。没有 DAC_OVERRIDE，服务自身的读写也受权限位约束。独立数值 uid/gid 不需要为每个应用用户创建系统账号，但要求真正以这些身份启动子进程。非 root 本机运行会明确警告未启用系统用户隔离；容器内切换身份失败则拒绝启动。

即使模型进程已经降权，服务代读文件仍可能扩大权限。因此读取产物、原生状态或用户文件时，需要明确“以谁的权限读取”。readAsUser 在隔离模式创建指定 uid 的短命辅助进程，使用固定 PATH 与 LANG，不继承服务密钥。正文经 stdout 返回，单独的 fd 3 传递有大小上限的元数据；读取还受超时和字节上限约束。

故障只收口到当前 owner，证据按验证层次核对

用户进程的 fatal 通知带有连接归属。池先停止这个连接，再在该 owner 上下文调用 recoverOwner：starting、running、steering 等执行中状态变为 unconfirmed，相关会话暂停。因为进程可能已经完成了部分操作，服务不能把断线当成“尚未执行”，再自动重发同一轮。清理用户会话缓存后，下次访问从该用户的原生历史核对结果；其他用户的连接、failure 和任务状态保持不变。

账号禁用也必须到达活动进程。数据库事务同时吊销令牌并发出通知；通知到达就关闭对应进程并中止启动。每次取得运行环境和每次工具调用仍查询账号状态，覆盖通知与请求交叉的窗口。如果通知连接丢失，执行器会停止，避免继续使用无法及时吊销的进程。这种全局停止是控制通道失效的处理，不能混同于普通单用户 Codex 崩溃。

第一个 admin 被禁用后，保留的原生目录映射不会转移给另一个账号。原生记忆虽按用户物理分开，是否开启仍服从服务端总开关、读取与贡献语义，账号数量不再决定开关。开启也不代表摘要生成成功：固定版本禁用原生写工具时，后台合并仍不能写出最终摘要；知识库挂载策略对记忆的限制继续生效。

判断隔离时，分别寻找三类证据

业务层看认证与任务 owner；进程层看连接归属、租约和生命周期；系统层看真实 uid/gid、目录权限和有界读取。三层互相补充。只看到 HTTP 返回 404，不能证明底层文件不可跨读；只看到用户进程分开，也不能省略工具与资源归属检查。
