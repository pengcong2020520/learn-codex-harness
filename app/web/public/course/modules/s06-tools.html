s06

工具：让能力经过检查再执行

工具注册表负责名称与参数，资料规则负责路径与操作，MCP 把这些受限能力交给 Codex。

这个云端 Agent 还缺什么：接触资料的受控入口

上一章，Agent 已经有明确的角色、Skills 和执行策略。这个云端 Agent 还缺什么？写作助手只能处理用户粘贴的文字，不能读资料、查看网页或保存结果。本章给它工具，同时让每次调用都经过服务端检查。

Registry 从 config/tools/*.json 装配：配置声明工具规格和实现模块，加载器编译参数校验规则、加载工厂函数，再把名称绑定到实际执行函数。重名、缺实现、无效 schema 或越界模块路径会使装配失败。

本阶段的四个默认工具
list_files 列出授权范围内的资料，read_file 读取文本，write_file 新建文件，read_webpage 读取公开网页。没有网页搜索工具；读取网页不等于搜索互联网。
模型提出调用，服务端执行
Codex 通过 MCP 发现和调用工具。注册表检查工具名与参数，文件服务继续检查路径与权限。Skills 描述方法，但不会自动增加 tools.allow 中的授权。
📌

继承的边界仍然有效

Codex 原生 shell 与写文件仍然关闭；资料操作通过本章的受限工具完成。Codex 原生记忆保持关闭，跨会话记忆留到下一章。网页工具只读取静态正文，不执行 JavaScript、不读 PDF、不访问本机和内网地址；返回的网页文字仍是不可信资料。

先核对工具名与参数，再调用实现

模型能看见一个工具，不代表任意调用都有效。tools.allow 是 Agent 的允许名单，inputSchema 约束一次调用的参数。注册表生成 specs 时按名单过滤，处理调用时还要再检查一次。

源码 · stages/s06-tools/server/modules/tools/loader.mjs · 第 99–112 行 
    validate(name, args) {
      const entry = entries.get(name);
      if (!entry || (agent && (!agent.allowsTool(name) || !currentNames().has(name)))) throw new Error("未授权的工具。");
      if (!entry.validate(args)) throw new Error(`工具参数不合法：${entry.validate.errors?.[0]?.message || "请检查参数"}`);
      return entry;
    },
    async call({ tool, namespace, arguments: args }, { signal } = {}) {
      if (agent) signal = AbortSignal.any([agent.revocation.signal, ...(signal ? [signal] : [])]);
      try {
        signal?.throwIfAborted();
        if (namespace != null) throw new Error("未授权的工具命名空间。");
        const entry = this.validate(tool, args);
        const data = await entry.execute(args, { signal });
        return { success: true, contentItems: [{ type: "inputText", text: JSON.stringify(data ?? null) }] };

📌

工具已注册，不等于 Agent 已获准使用

新增一个工具需要提供规格和实现，并让 Agent 定义允许该名称。仅在 Skill 里写“调用 write_file”，或只把执行函数放入目录，都不能替代 tools.allow。修改 Agent 定义仍会触发上一章的作废与受控重启规则。

按用途授权资料：读取、新建和覆盖是不同操作

tools.allow 回答“能不能调用 write_file”，资料规则继续回答“能写到哪里”。dataBindings 和 outputs 一起组成文件访问边界。

文件服务自身执行边界，不靠 Codex 的 cwd 推断权限。绝对路径、上级目录 ..、隐藏路径、符号链接等会被拒绝；文件只支持 .md / .txt。已存在的文件不能覆盖，需用新文件名保存。写入后的产物检查在创建之后进行；会话的 turn.artifacts 只登记 write_file 成功返回的产物，不从模型回答中猜测。

MCP：一个入口承载工具，更新等到空闲边界

MCP 让 Codex 使用统一协议调用注册表。tools/list 获取工具清单，tools/call 提交名称与参数；这些协议方法由 MCP SDK 处理。

ToolManager.open() 构建带版本的注册表并启动本地入口，只监听 127.0.0.1 的动态端口。服务生成随机 Bearer 令牌，经环境变量传给 Codex；配置里只写入口地址和令牌变量名。入口拒绝带 Origin 的请求和无效令牌，按 URL 中的版本定位注册表。

源码 · stages/s06-tools/server/modules/tools/mcp-server.mjs · 第 23–31 行 
    server.setRequestHandler(ListToolsRequestSchema, () => ({ tools: registry.specs }));
    server.setRequestHandler(CallToolRequestSchema, async ({ params }, extra) => {
      state.activeCalls++;
      try {
        const result = await registry.call({ tool: params.name, arguments: params.arguments || {} },
          { signal: AbortSignal.any([extra.signal, controller.signal, AbortSignal.timeout(30000)]) });
        return { isError: !result.success, content: result.contentItems.map(item => ({ type: "text", text: redact(item.text) })) };
      } finally { state.activeCalls--; }
    });

服务启动还会通过 mcpServerStatus/list 核验 Codex 实际发现的工具：本项目入口必须发现成功，工具名必须与注册表一致；发现其他提供工具的 MCP 入口时拒绝继续。不是写入配置就认为接入成功。

工具目录更新
ToolManager 扫描配置和实现的内容版本。删除、禁用先收紧后续调用；新实现等所有活动 Turn 和工具调用结束后，才在 ExecutionBoundary 下切换。会话开始与更新共用边界，避免刚检查空闲就有新任务进入。
版本与失败处理
候选注册表经配置写入、MCP reload 和发现核验后才启用，并更新 Agent 描述符。版本不兼容的已有 Thread 需 /new。更新失败会尝试恢复上一版配置；恢复核验也失败时工具不可用。修改 Agent 定义、角色或 Skill 则仍需受控重启。

一个入口可以承载多个工具，不需要每增加一个工具就增加一个端口。这是本项目的组织方式，不是 MCP 协议限制只能有一个服务。
