模型网关：选谁来做，何时停派

用模型清单统一声明，用路由表达任务需求，用账本控制后续派发；协议转换与故障备用交给 Bifrost。

这个云端 Agent 还缺什么：协调模型与用量

上一章 s10 用 Skill 教方法，用 Workflow 管步骤、权限与确认。写作任务可以先产出大纲，等用户确认后再继续成稿。这个云端 Agent 还缺什么？大纲和成稿未必适合用同一个模型；知识检索需要向量模型，生成图片又是另一种用途。模型越来越多之后，谁负责挑选，谁持有密钥，花费达到上限时谁来停止派发，都需要明确的执行位置。

模型网关 是请求经过的服务。模型路由 是任务派发前的决策。名字相近，但发生时间和掌握的信息不同。

角色负责什么本章中的证据
Codex管理 Thread 与 Turn，执行推理和工具循环，报告模型用量。turn/start 参数、thread/tokenUsage/updated 通知。
服务端校验清单、挑选模型、关联任务、记账与控制派发。selectedModel、modelSource、用量账本与队列预算状态。
Bifrost持有服务商凭据，转换协议，处理请求失败后的备用链与限流。生成配置可离线检查，真实请求行为需要集成验证。

本章以网关模式为主：Codex 的地址与密钥指向网关，工具层也可通过同一入口使用向量、图像和视频模型。不要把这读成所有配置都强制经网关：没有启用网关时仍有直连路径，RAG 单独设置了 EMBEDDING_BASE_URL 时，使用这条独立连接，不再按 routes.embedding 改写模型和维数。

清单先通过检查，密钥再按边界传递

config/models.json 是配置事实的集中入口。providers 记录服务商接口类型、地址和密钥变量名；models 记录用途、上下文、输入类型、原生工具、推理档位、价格与备用模型；routes 和 scenes 描述候选顺序。用途有 chat、embedding、rerank、image、video、tts、asr，登记用途不等于已经实现了对应的产品工具。

purposes 先回答“做什么”。例如 embedding 必须声明 dimensions，chat 必须声明 contextWindow；走 anthropic 格式的对话模型还必须填 maxOutputTokens，供网关转换时使用。备用模型必须覆盖主模型全部用途，但可以缺少搜索或看图能力，启动时对此给出提醒。

validateRegistry 会拒绝不存在的模型引用、非法用途、错误推理档位与非法价格。服务商启用则由 enabledProviders 判断：它声明的 keyEnv、baseUrlEnv 都有值才启用。这个检查不访问上游，也不验证账号余额；Ollama 只声明地址变量时，可以不带供应商密钥启用。

  const unmet = (id, purpose, needs) => {
    const spec = registry.models[id];
    if (!spec?.purposes.includes(purpose)) return `不能做${LABELS[purpose]}`;
    const provider = registry.providers[splitModelId(id).provider];
    if (!enabled.has(splitModelId(id).provider)) return `服务商未启用（.env 里缺 ${[provider.keyEnv, provider.baseUrlEnv].filter(Boolean).join("、")}）`;
    if (needs.image && !(spec.inputModalities || ["text"]).includes("image")) return "不能看图";
    if (needs.contextTokens && (spec.contextWindow || 0) < needs.contextTokens) return `上下文只有 ${spec.contextWindow || 0}`;
    const missing = (needs.nativeTools || []).filter(tool => !spec.nativeTools?.includes(tool));
    if (missing.length) return `不支持原生能力 ${missing.map(tool => tool === "web_search" ? "联网搜索（web_search）" : tool).join("、")}`;
    return null;
  };

  const pick = (candidates, purpose, needs, source) => {
    const reasons = [];
    for (const id of candidates) {
      const reason = unmet(id, purpose, needs);
      if (!reason) return { id, ...splitModelId(id), purpose, spec: registry.models[id], source };
      reasons.push(`${id}：${reason}`);
    }
    throw new AppError(`没有可用的${LABELS[purpose]}模型（${source}）。${reasons.length ? `候选：${reasons.join("；")}` : "没有登记候选。"}`, 503, "MODEL_UNAVAILABLE");
  };

备用链发生在请求层
fallbacks 由网关处理，只生成已启用服务商的备用关系。它应对上游失败，并不重新理解任务语义。备用模型可能缺搜索或看图，提醒不会阻止启动；已经开始输出后才出错，也没有透明切换继续输出的保证。

向量、图像和视频同样按 purpose 选模型。媒体工具的 quality=fast 或 strong 只参与场景选择，不直接传给供应商；省略时使用各自 routes。视频生成提交后返回任务 ID，由后台查询与保存结果；提交结果不确定时不自动重提。本章用这条边界说明：选中了模型不等于异步产物已经完成。

本次用量怎样入账，达到预算怎样等待

一次 Turn 可能多次请求模型。Codex 的通知同时给出 Thread 累计 total 与本次 last；直接累加 total 会重复计算历史。累计水位 用来识别通知是否新增，账本用来记录本次消耗。

📌

停派不是费用精确封顶

服务端没有为未来消耗预留额度，活动轮次与指向它的 steer 可以继续，并发请求也可能超出预算。网关虚拟密钥另设每日 token 兜底：默认使用已配置日 token 预算的 1.5 倍向上取整，可由 AGENT_GATEWAY_DAILY_TOKENS 覆盖；两者都未设置时没有这条限流。兜底耗尽可能拒绝在途后续请求，网关重启又会清空自己的计数，不能保证任意长轮次完成。

正常超限只是预算等待。账本写入失败则是另一条故障路径：pending 链保留错误，真实通知处理触发 usageError，调度服务停止并要求核对任务。生产依赖 PostgreSQL，不会用一份空内存账本掩盖数据库故障。
