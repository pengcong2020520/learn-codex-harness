# 完整 PRD

章节改编自 [github/spec-kit 的 spec-template](https://github.com/github/spec-kit/blob/main/templates/spec-template.md)，MIT 许可证，Copyright GitHub, Inc.；全文见 [LICENSE-spec-kit.txt](LICENSE-spec-kit.txt)。产出的 PRD 开头也注明此来源及许可证。

先读 [总流程与产物约定](../agent-design-flow/SKILL.md)。所有路径相对于用户自己的工作区；只新建版本，不覆盖历史文件。使用最新且已获用户确认的输入版本；较新的未确认版本不能替代确认记录。当前阶段经用户明确选择「继续」后才进入下一阶段；「修改」重做当前步，「结束」保存进度并停止。

输入为 `brief-v1.md` 对应文件族中最新已确认版本，输出 `outputs/design/<项目 id>/prd-v1.md`，修订时编号递增。先读完整资料卡和用户已有材料，把内容直接落到下表对应章节。

| 资料卡字段 | PRD 章节 |
|---|---|
| 名称、一句话定位、交付物形式 | 产品概述；关键实体与输出 |
| 目标用户与使用场景 | 目标用户与场景；用户故事 |
| 核心任务、需要人确认的环节 | 用户故事；核心流程；功能需求 |
| 端、必须有的页面或功能 | 页面清单与核心流程；功能需求 |
| 资料来源 | 关键实体；功能需求；权限与隐私 |
| 明确不做的事 | 本期不做 |
| 参考产品或参考图 | 产品概述中的参考依据，说明借鉴范围 |
| 成功标准 | 可度量的成功标准 |
| 模型要求（看图、联网、成本） | 功能需求；非功能需求；假设与依赖 |
| 权限与隐私 | 非功能需求；边界情况；验收场景 |

## 澄清规则

spec-kit 的 `[NEEDS CLARIFICATION]` 不进入最终文档。遇到不清楚的内容先与用户澄清，和 agent-brief 合计最多约 3 轮，每轮最多 5 问，每问给 2–4 个选项和推荐项，允许自由回答。读取累计轮数，不重置预算。理解后直接写进 PRD，不留「待确认」、未填占位或含糊的二选一。用户明确说“以后再说”时，放进“本期不做”或“假设”，写明理由，不当作已承诺功能。

轮数到限但关键范围或权限仍无法确定时，不产出伪完整 PRD；把阻塞反馈保存，请用户明确缩减范围或结束。经用户认可的假设可以进入完整版本；不得为了填满文档自行推断权限、付费或外部写入授权。

## 必须具备的章节

1. **产品概述**：定位、要解决的问题、交付物、范围、参考依据。
2. **目标用户与场景**：用户角色、使用时机、任务起点和期望结果。
3. **用户故事与测试**：按 P1–P3 排优先级，说明优先级理由。每个故事是可独立测试并交付价值的用户旅程，写出独立测试方式。验收场景逐条用 **Given / When / Then** 写初始条件、动作、可观察结果；按实际故事数量组织，不为凑 P3 增功能。
4. **页面清单与核心流程**：为每页定稳定的屏幕 id、名称、Web/App、分组、位置、入口、字段分组、按钮位置、操作和去向、退出方式、所需状态。用表格串起主流程、分支、人工确认、失败恢复；状态采用总流程词表。这是线框的直接输入，不让下游猜按钮目的地。
5. **边界情况**：首次使用、权限拒绝、加载、空数据、错误、重复操作、异常恢复等与产品相关的边界，写预期行为；没有涉及的项写明不适用原因。
6. **功能需求**：逐条编号 `FR-001`、`FR-002` 等，写可验证的行为，映射故事和页面。确认点写清确认前后允许做什么、用户修改或结束如何处理。
7. **关键实体**：实体含义、关键属性、关系、来源、可见范围、生命周期与输出形式；无持久实体时说明，不强塞数据库实现。
8. **非功能需求**：权限、隐私、性能、可访问性、模型能力与成本约束。性能用已确认的场景和目标，不擅自抬高资源或并发门槛。
9. **成功标准**：`SC-001` 等可度量、可验收、与技术栈无关的结果；每项列度量方法和达标条件，映射用户任务。资料卡只有定性目标时将验收动作具体化并请用户认可，不捏造业务数据。
10. **假设**：已获认可的默认条件、依赖、适用范围和依据；写明“以后再说”导致的假设及理由。
11. **本期不做**：明确排除项、理由和本期替代方式（若有）。

交付前核对故事、FR、页面、状态、成功标准相互对应，资料卡所有字段有归属，最终文档没有待确认标记。展示完整 PRD，用户明确确认具体版本后才生成线框。
