# 有设计意图的高保真原型

改编自官方 frontend-design，见 [NOTICE.md](NOTICE.md) 和 [LICENSE.txt](LICENSE.txt)。保留以产品、受众和任务决定视觉取舍的方法，避免套用模板化 AI 风格。

## 已有线框工作方式

必须同时读取最新且已确认的 PRD、线框和主题，初版为 `prd-v1.md`、`wireframe-v1.html`、`theme-v1.json`。高保真产出是 `prototype-v1.html`，修订递增。先核对三者版本一致，没有线框或主题确认时返回对应阶段，不凭印象直接做视觉稿。

| 可以直接优化 | 必须先提出并等用户确认 |
|---|---|
| 字体、间距、控件样式、状态样式、图标、微交互 | 页面拆分或合并、字段分组、按钮位置、跳转去向、功能增加或删除 |

可直接优化的内容仍遵守已选主题；不能借“间距优化”移动按钮到另一操作区。结构调整逐条写进 `structure-changes-v1.md`（后续 `structure-changes-v<n>.md`），包含编号、具体变更、原因、影响到的屏幕 id / 状态 / 操作、涉及的 PRD 条目和用户确认结果。先展示提案，用户未明确确认不得应用；没有结构调整也写“无结构调整”。确认后更新对应 PRD / 线框版本及输入记录，再实现原型，保留旧版本。

必须保留线框的屏幕 id、状态、分组、定位约定和大纲。确需增删屏幕或状态时把标识映射写入结构提案并等确认，不能静默重编号。每一屏都可直接定位，状态示例数据与 PRD 一致。

## 视觉设计的两次检查

1. **先形成短设计计划**：用真实产品内容、受众和任务说明颜色、字体角色、布局内的对齐与层级、一个值得强调的特征。以已确认的主题令牌为基础，不另换配色，不重新规划页面结构。
2. **对照需求检查，再实现并自评**：视觉选择应能解释为什么适合当前产品。没有用户依据时，避免惯性的紫色渐变、奶油底配衬线标题、黑底荧光色、报纸细线布局、整页同样圆角卡片、装饰性编号和每节重复淡入动效。用户明确选择这些方向时尊重选择，不把审美偏好变成禁令。

字体用一至两个有分工的系统字体栈，以字重、字号、行高、宽度和留白形成层次。正文行长通常控制在约 80 字符内，衬线正文适当增加行高。不要机械地给标题某一个词上色、到处加全大写眉题或无意义标签。边框、分隔线、编号用于表达信息关系；编号只用于真实顺序。

把视觉重点集中在最能表达产品特征的地方，其余部分保持克制。首页入口根据任务选择文案、示例、交互等，不强加营销 Hero。用户操作触发的微交互解释状态变化；自动播放动效要少，尊重减少动态效果偏好。保证键盘焦点可见、对比度、响应式和 CSS 层叠可控；响应式不能悄悄改变已确认按钮关系。

文案帮助用户完成任务，不展示实现细节。按钮写具体动作并前后一致，错误说清问题和恢复方式，空态给出下一步。保留 PRD 的真实核心文案，不编造功能或数据来装饰页面。

HTML 必须是可离线打开的单文件，只用系统字体栈。每屏使用 `<section data-screen="<id>" data-state="<状态>" data-group="<分组>">`；支持 `#screen=<id>&state=<状态>` 只显示对应屏，且监听地址变化。内嵌 `design-outline`（`application/json`），结构与总流程一致。固定状态词表为 default、first-use、permission、loading、empty、error、recovery；自定义状态列入大纲。工作室中嵌入预览，不截图。

## 实现与交付

调用 [prototype-builder](../prototype-builder/SKILL.md) 决定简单单文件或复杂构建方式；两种方式都受这里的结构边界约束。原型只使用示例数据，不触发真实发红包、支付、发消息等外部动作。

交付时在原型总览附逐屏对照表：线框文件和屏幕 id / 状态 → 原型文件和屏幕 id / 状态 → 视觉改了什么 → 对应结构提案及确认记录（无则写无）。所有线框屏幕均有一行；不能只列改动页。定位到单屏时隐藏总览和对照表。

在工作室用实时嵌入预览自查排版、操作、分支和异常状态，不截图。用户确认具体版本后进入全流程走查；官方的截图自评方法只留给 K5 的真实产品开发侧。
