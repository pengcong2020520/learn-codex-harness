事件与消息：让任务有序执行

这个云端 Agent 还缺可靠的连续提交与状态同步。亲手串起任务记录、按会话调度和 SSE，遇到不确定执行时保留证据、暂停核对。

这个云端 Agent 还缺什么？能保存每条输入的任务记录

现在服务端能独立完成一轮了。试着在回答过程中再输入两条，然后关闭客户端：已经发出的那一轮可以继续，仍等在客户端的输入却没有服务端记录。一个能长期工作的云端 Agent，还要接住用户连续交来的事情，并告诉用户每一条走到了哪里。

本章的验收场景是：连续提交三条普通消息，三条都被服务端接收；关闭客户端后，服务端依次完成它们；回来时能看到队列和会话状态。如果执行结果拿不准，就停下来让用户核对，避免把同一件事做两遍。

messages：决定执行节奏
接收消息、按 Thread 排队、发 turn/start，处理追加、超时、暂停与继续。它决定哪条输入现在可以执行，不代替 Codex 内部的推理与工具循环。
data：保存任务事实
将消息和暂停状态写入 .data/messages.json，每次更新整体原子替换文件。进程退出后记录还在，重启时可据此判断哪些任务需要核对。
events：把变化交给订阅者
事件中心分发会话与队列状态，经 HTTP 的 SSE 连接交给对应 Thread 的客户端。它不负责启动下一轮，也不调用模型。

区分三个 ID：threadId 标识会话，clientMessageId 标识用户这次提交，turnId 标识 Codex 执行轮次。任务可以在还没有 turnId 时就处于 queued；追加也可能与已有任务关联到同一轮，三个 ID 不能相互替代。

实现边界

服务默认监听 127.0.0.1:4319，仍是本机单用户、单进程队列。同目录只运行一个服务；每个会话最多 100 条 queued 消息。本章验证可靠提交与状态同步，不提供多机器调度。

提交先落盘：同一个消息 ID 为什么不会做两遍

客户端为每条输入生成 clientMessageId，再调用 POST /messages。服务端先校验文本、模式和会话，进入同一 Thread 的串行操作区间，然后检查这个 ID 是否已有记录。幂等 在这里解决的是“同一提交的重复请求”，不是“所有意思相同的文本都只执行一次”。

首次提交返回 202 queued 表示已接收并记录。重复提交返回的可能是 running 或 completed，因为它返回的是已有任务当前状态。若用户用新的 ID 再发一遍同样文本，那是一个新的任务，服务端不会猜测它是不是重复意图。

文件写入成功后才调度，因此即便随后进程退出，已接收消息也有记录。这里的持久性依赖本机 .data 目录；它不等同于远端备份，也不意味着系统能自动证明所有外部动作“恰好执行一次”。对于已经发出、结果未知的调用，还需要后面的 unconfirmed 处理。

调度一次：普通消息 FIFO，显式追加另有去向

FIFO 的范围是同一个 Thread。调度器先看会话是否暂停，再看有没有正在执行的 Turn；不同 Thread 的任务互不阻塞，同一 Thread 的普通输入一次只启动一轮。

默认执行上限是 10 分钟，由 AGENT_TURN_TIMEOUT_MS 控制。到达上限后服务端暂停队列，并请求 turn/interrupt；发出中断请求本身不等于已经收到最终状态，后续通知或连接错误处理仍需核对结果。

让状态主动到达：SSE 先快照，后事件

客户端订阅 GET /events?threadId=…，建立 SSE 长连接。服务端有变化时发送数据，不需要客户端每 200 ms 询问一次。消息提交仍走 POST /messages；订阅只负责查看。

重连时最容易漏掉的时间窗口在“读快照”和“开始监听”之间。这里先登记监听者，把快照准备期间收到的事件暂存，发送完整快照后再发送暂存事件。下面的 listener 已处于 GET /events 路由内，id 是正在订阅的 Thread。

snapshot / session / queue
snapshot 是每次连接的首条完整状态，含会话与队列；session 表示会话变化，queue 表示任务状态、暂停或继续。客户端用这些内容更新显示。
fatal / shutdown
fatal 提示执行连接失效、服务停止调度；shutdown 表示服务正常关闭。看到这类事件要核对服务与任务状态，不能据此认定所有任务已完成。

客户端断线后约一秒再尝试连接，每次都先获取快照。事件序号用于排查问题，本章不按 Last-Event-ID 重放历史事件。快照帮助客户端重新看到当前状态，不承诺补齐离线期间每一条事件；订阅过程也不会替用户再提交一次消息。

普通事件写入积压超过 1 MiB 时连接会被断开，再由客户端重连取快照。快照之后的事件仍是状态更新，渲染时应以事件内容更新视图，不能把事件到达次数当作执行次数。

遇到不确定：保留记录，暂停后续执行

服务重启时，文件里有 A=running、B=queued。你能直接把 A 再发一次吗？不能：程序只知道 A 没有拿到确定结果，不知道它在中止前做到了哪一步。用 unconfirmed 明确表达这份不确定性，比把它当成“什么也没做”更准确。

源码 · stages/s04-events-messages/server/modules/data/index.mjs · 第 33–40 行 
  recover(reason) {
    this.mutate(s => {
      for (const job of s.jobs) {
        if (['starting','running','steering'].includes(job.status)) { job.status = 'unconfirmed'; job.error = reason; }
        if (job.status === 'unconfirmed' && !s.paused.includes(job.threadId)) s.paused.push(job.threadId);
      }
    });
  }

启动时恢复任务记录，再为有任务的会话安排调度。只有 queued、且会话没有暂停的任务可以继续；含不确定执行的会话停住。因此“排队消息保留”不等于“重启后每个会话都立即继续”。

执行中连接断了
发出调用后没有明确结果，任务可能成为 unconfirmed；队列暂停。明确失败或中断同样会暂停，防止后续输入建立在错误前提上。
用户核对后继续
先 /queue 查看记录，并检查同一会话的回答与实际结果，再 /continue。它解除暂停、唤醒调度器，不把 failed 或 unconfirmed 改回 queued。

若确实需要再执行一次，必须由用户另行明确提交新任务，不能把 /continue 当作“重试上一条”。这项选择在具备外部工具的 Agent 中尤其关键：结果未确认时，重复动作可能产生第二份副作用。本章先把这个判断点做成可查看、可继续的队列状态。

亲手验证：连续提交、断线重连、重启核对

终端 1 保持服务运行；终端 2 进入相同目录运行 npm run chat。提交一个较长任务，不等回答结束就再输入两条普通消息，用 /queue 查看记录。预期同一 Thread 只有一轮执行，其余仍排队；若实际回答失败，应看到队列暂停，而不是强行把实验判成成功。

  1. 客户端退出：第一轮执行时 Ctrl+C 退出客户端，等待后重新连接并 /resume 同一 Thread。核对三条任务的状态、顺序与回答，不仅看终端是否出现文字。
  2. 显式追加：任务执行中输入 /append 请用三点概括，查看关联的 turnId。若目标已成功完成且仍可定位、当前队列未暂停，则观察它作为优先的新一轮执行；/append-to 可明确指定目标。队列暂停时先核对再 /continue；无法定位的目标会被拒绝。
  3. 服务重启：确保有一条正在执行、一条排队，再停止终端 1 的服务并重启。退出终端 2 的旧 CLI，重新运行 npm run chat，再 /resume 并选中同一 Thread。服务每次启动都会生成新令牌；旧 CLI 自动重连仍用旧令牌，会收到 401，重新启动 CLI 才会读取新的连接文件。此时 /queue 应显示执行项 unconfirmed、排队项保留且会话暂停；核对后 /continue，只处理后续排队项。
