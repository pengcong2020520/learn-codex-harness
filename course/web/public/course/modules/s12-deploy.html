上云部署：没人看着，也能启动与恢复

交付固定的运行环境，分清活着与就绪；接不过来就拒绝，关闭和恢复都有依据。

交付物是镜像，代码和数据分开放

上一章，云端 Agent 已能聊天、使用工具和知识、执行工作流，并由模型网关管理模型。但它还依赖你的电脑：电脑合上，服务就停了。本章把它交给没人看着的服务器，补上启动、持久化、容量和恢复的责任。

在本机能跑，依赖的是本机的 Node、依赖和系统工具。镜像把这些固定下来，换机器也能得到同一运行环境。部署单元把 PostgreSQL、Redis、网关和 Agent 的镜像与依赖关系写进同一份 Compose 配置；Codex 仍负责每轮执行，Compose 与 systemd 负责启动和退出后的恢复。

镜像可以替换，数据不能跟着消失。数据库和 Redis 使用独立数据卷；会话历史、运行目录、资料产物和备份挂载在宿主机上。升级换代码与镜像，持久状态原地保留。

固定路径是一份持久化契约：Codex 原生历史记录绝对路径，容器内与宿主机的部署路径必须一致。回滚也在同一路径替换代码，否则旧会话找不到历史记录的位置。

密钥只放在权限为 600 的宿主 .env 中，镜像不带密钥。各服务只取自己需要的凭据：服务商密钥留在网关，Agent 只取网关访问密钥和自己的数据库配置。构建、资源与部署参数见设计说明。

活着，不等于能接活

健康检查问“进程还活着吗”，就绪检查问“依赖与执行器能接任务吗”。数据库或网关断开时，HTTP 仍可能响应；把这两个问题分开，入口才能停止向暂时不能工作的服务派发请求。

Compose 按依赖健康决定启动顺序。下面的配置让 Agent 等依赖就绪后启动，但运行途中依赖失效，还需要服务持续检查自己的状态。

gateway 的依赖条件是 service_healthy；同一 depends_on 段还包含 postgres 和 redis。

agent 的探针执行 Node 脚本，周期 5 秒、超时 10 秒、最多重试 20 次。

这些条件约束启动时机。依赖在运行途中失效时，Compose 不会持续按依赖图重新排布全部服务。

/health只报告存活；/ready核对数据库、网关、模型目录和调度状态，任一条件不满足就返回 503。进程退出由重启策略处理，容器标记 unhealthy 本身不会触发重启。

源码 · stages/s12-deploy/server/modules/deployment/index.mjs · 第 24–34 行 
export function createReadiness({ config, data, messages, tools, fetcher = fetch, stopping = () => false }) {
  const version = revision(config.root);
  return async () => {
    const checks = { database: false, gateway: false, models: Boolean(config.registry && config.launch.router && config.launch.catalog?.models?.length) };
    try { await data.pool.query({ text: 'SELECT 1', query_timeout: 3000 }); checks.database = true; } catch { /* No credentials in responses. */ }
    try {
      const url = new URL('/health', config.media.endpoint.baseUrl);
      checks.gateway = (await fetcher(url, { signal: AbortSignal.timeout(3000) })).ok;
    } catch { /* Gateway health does not call a model. */ }
    const ready = Object.values(checks).every(Boolean) && !stopping() && !messages.failure && !messages.closed && !messages.stopping && !tools?.broken && data.queue?.healthy !== false;
    return { status: ready ? 'ready' : 'not-ready', version, checks };
源码解读 · 对照运行边界

先建立 checks：数据库与网关默认失败，模型目录必须已经加载且存在可选模型。

SELECT 1 使用 query_timeout=3000；网关 /health 请求使用 AbortSignal.timeout(3000)。异常转成失败检查，不在响应中带出原始凭据。

最终 ready 还要求服务未停止、消息执行器无失败或关闭状态、工具连接未 broken、队列没有显式不健康。

返回结果保留 version 和各项 checks；模型目录与网关健康没有发起供应商模型请求。

源码解读 · 对照运行边界

HTTP handler 等待就绪检查，并把 ready 映射为 200、其余映射为 503。

这个分支在入口请求限流之前；健康诊断不会因普通请求额度用完而被挡住。

例如停掉网关，HTTP 仍存活时应看到 /health=200、/ready=503；恢复依赖后再核对就绪。就绪只说明本次探测满足条件，不保证模型额度、响应质量或下一轮成功。

📌

不要把一次健康检查扩大成服务质量承诺

Compose 的依赖健康是启动条件；/ready 是当前运行状态检查；真实模型调用还要验证鉴权、额度和响应。三种证据分别保留，故障时才能知道是哪一层不满足条件。

接不过来就明确拒绝

背压是在资源耗尽前限制工作进入，避免把所有请求都接下后一起变慢、一起失败。执行轮次、排队任务、请求频率和长连接占用不同资源，因此需要分别设上限。

源码 · stages/s12-deploy/server/modules/deployment/index.mjs · 第 13–16 行

    maxQueued: integer('AGENT_MAX_QUEUED', 200),
    rateLimit: integer('AGENT_RATE_LIMIT_PER_MINUTE', 120),
    maxSse: integer('AGENT_MAX_SSE', 20),
源码解读 · 对照运行边界

每个配置值先经过正整数校验；非法值会在启动配置阶段报错。

maxConcurrentTurns 限制新轮次派发，maxQueued 限制进入排队，rateLimit 约束每个来源窗口，maxSse 限制全局连接名额。

修改一项不意味着其余三项跟着改变。容量应按实际资源分别安排。

资源默认上限达到上限后
活动轮次跨会话 2 个后续任务保持 queued。
排队任务全局 200；单会话 100429 QUEUE_FULL。
HTTP 请求每个令牌与实际来源组合每 60 秒 120 次429 RATE_LIMITED，附 Retry-After。
SSE 连接全局 20 个429 SSE_FULL，5 秒后再试。

入队检查和写入在同一数据库事务中串行完成，防止并发请求抢到同一个空位。新建、确认、Workflow 再排队都过这道门禁；Workflow 遇到满队列会等待用户确认。执行名额满了只停止新轮次派发，已持久化的任务仍在。

源码 · stages/s12-deploy/server/modules/messages/index.mjs · 第 255–256 行 
    const maxConcurrentTurns = this.config.deployment?.maxConcurrentTurns ?? 2;
    if (running.size >= maxConcurrentTurns) return;
源码解读 · 对照运行边界

running 统计当前占用执行名额的会话；达到上限直接停止这次新轮次派发。

任务仍在持久队列中，后续扫描可以在容量释放后继续；这个 return 没有把任务标为失败。

调度按任务顺序寻找可执行会话，暂停或预算不足的会话不阻塞其他会话；已有轮次的追加走 steer，不另占新轮次名额。这是服务派发上限，不限制 Codex 内部工具并行。

滑动窗口按令牌与实际 socket 来源计数，不信任转发头；无效令牌合并到同一来源桶，避免换令牌绕过限制。

源码 · stages/s12-deploy/server/modules/deployment/index.mjs · 第 45–59 行 
  request(token, address) {
    const now = this.now();
    for (const [key, values] of this.windows) {
      while (values.length && values[0] <= now - 60000) values.shift();
      if (!values.length) this.windows.delete(key);
    }
    const key = createHash('sha256').update(`${token}\0${address}`).digest('hex');
    const values = this.windows.get(key) || [];
    if (values.length >= this.rateLimit) {
      const error = new AppError('请求过于频繁。', 429, 'RATE_LIMITED');
      error.retryAfter = Math.max(1, Math.ceil((values[0] + 60000 - now) / 1000));
      throw error;
    }
    values.push(now);
    this.windows.set(key, values);
源码解读 · 对照运行边界

每次请求清理过期记录，空桶也会删除；仍在 60 秒窗口内的记录参与计数。

令牌和 socket peer 组合后计算摘要作为键；无效认证由 HTTP 层传入统一的 unauthenticated 标识。

达到额度时创建 429 RATE_LIMITED。等待时间由最早请求到期的剩余毫秒向上取整，最少为 1 秒。

未超限才追加当前时间。因此拒绝的第 121 次请求不会延长已有窗口。

429 表示入口拒绝或要求稍后再试，不代表模型已经执行失败。SSE 断开时释放名额，健康探测不占请求额度。限流窗口在内存中，重启会清空；本章尚无按用户的身份与配额。

关闭先停派发，结果不明就待核对

关闭时最难的不是退出进程，而是保留执行事实：模型可能已经调用工具，却没来得及保存终态。不能把“没收到结果”当成“什么也没做”，自动重发可能造成重复操作。

源码 · stages/s12-deploy/server/modules/deployment/index.mjs · 第 74–80 行 
export function gracefulShutdown({ stopDispatch, markUnconfirmed, close, exit = code => process.exit(code), timer = setTimeout, clear = clearTimeout }) {
  let pending;
  return () => pending ||= (async () => {
    stopDispatch();
    const deadline = timer(() => exit(1), 30000);
    try { await markUnconfirmed(); await close(); }
    finally { clear(deadline); }
源码解读 · 对照运行边界

pending 让多次关闭请求共享一次流程，避免重复关闭资源。

stopDispatch 同步执行，收到信号后先停止继续派发。

随后保存 unconfirmed，再关闭 HTTP、SSE、RPC 和数据资源；30 秒定时器是资源卡住时的退出截止。

正常清理结束后取消截止定时器；无法在截止前落库的残留执行状态，交给启动恢复再次处理。

收到 SIGTERM 后，先停止派发新任务，再把执行中状态标为 unconfirmed，最后关闭连接，整个关闭过程以 30 秒为截止。queued 保留，重启后继续派发；残留 starting、running、steering 也按待核对处理，不自动重跑。

回滚解决代码版本的问题：保留上一版代码与镜像，在固定路径换回去。它不倒转数据库、workspace 或凭据；破坏性 schema 变化还需要兼容代码或升级前的完整备份。

📌

先核对结果，再决定是否重做

unconfirmed 表示证据尚不足。查看任务、产物和外部系统后再继续；直接重发可能重复已经发生的操作。部署模块保留这种不确定性，而不是替使用者猜测结果。

备份要对应同一时刻，恢复失败就保持停止

备份是数据库记录与文件历史的一组恢复依据。若两者在持续写入时分别复制，可能一份新、一份旧，所以本章短暂停止 Agent，在同一个停服窗口导出数据库并打包目录。

源码 · stages/s12-deploy/deploy/backup.sh · 第 9–34 行 
partial=''
cleanup() {
  local status=$?
  trap - EXIT
  if [ -n "$partial" ]; then rm -rf -- "$partial" || status=1; fi
  if ! docker compose up -d --wait agent; then
    echo 'agent 重启失败，请检查 docker compose ps。' >&2
    status=1
  fi
  exit "$status"
}
# Install before stop so even an interrupted/failed stop attempts to bring agent back.
trap cleanup EXIT
trap 'exit 130' INT
trap 'exit 143' TERM
docker compose stop agent
name=$(date -u +%Y-%m-%dT%H-%M-%S-000Z)
[ ! -e "backups/$name" ] || { echo '备份名称已存在，请稍后重试。' >&2; exit 1; }
mkdir "backups/.$name.partial"
partial="backups/.$name.partial"
# Keep these arguments in sync with backup-lib.mjs dumpCommand(agent, agent_s12).
docker compose exec -T postgres pg_dump --no-password -U agent --clean --if-exists --no-owner --no-privileges agent_s12 |
  gzip > "$partial/database.sql.gz"
# The agent image runs as uid 1000; root-created private files must be writable there.
if [ "$(id -u)" = 0 ]; then chown 1000:1000 backups "$partial" "$partial/database.sql.gz"; fi
docker compose run --rm --no-deps -T agent node scripts/backup.mjs --apply --partial "$name"
源码解读 · 对照运行边界

脚本此前已用文件描述符 9 获取共享非阻塞 flock；冲突立即返回 75。

cleanup 保存原始退出码并清理未发布 partial，无论成功还是失败都尝试 up -d --wait agent；重启失败也保留非零结果。

EXIT trap 安装在 stop 之前，停止操作失败或被中断时仍尝试恢复 agent。INT 和 TERM 被转为明确退出码。

pg_dump 在 postgres 容器内执行，gzip 将纯 SQL 写入隐藏 partial；pipefail 让转储失败可以传播。

root 创建的目录与 SQL 交给 uid 1000；一次性 agent 容器用 --no-deps 避免重新拉起依赖，并执行打包发布。

数据库、workspace、原生历史、实例身份与不可变正文一并保存；Redis 缓存、运行日志、密钥和镜像不在备份中。清单记录大小、SHA-256 与版本，全部完成才发布为成功备份，只保留最近 7 份。备份失败会清理未完成包，并尝试重启原服务。

恢复先校验，再重放数据库和恢复目录，最后检查就绪。任一步失败都保持 Agent 停止，避免用混合状态继续服务。跨数据库与文件系统没有总原子事务，失败后需重新恢复完整备份；具体互斥、下载与恢复步骤见设计说明。

校验和能发现损坏，不能认证备份来源；恢复只接受可信备份，并要求固定路径和兼容 schema。一个备份包存在，也不能证明整套服务已恢复。

📌

成功备份与可恢复部署分别验收

离线测试可以验证真实 tar 打包、manifest、保留策略、篡改拒绝和 Bash 成败分支。真实数据库备份恢复、权限、固定路径与就绪重查仍要在 Docker 环境完成。只有包存在，还不足以证明整套服务能恢复。

用故障理解部署的边界

部署能力要在依赖失效、容量耗尽和恢复失败时检验，不能只看一次启动成功。离线实验验证就绪、队列、限流和备份分支；真实容器、数据库、SIGTERM 与回滚仍需外部验收，步骤见本章 README。
