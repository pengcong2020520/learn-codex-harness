s03

服务：让 Agent 常驻

这个云端 Agent 还缺一个独立运行的服务端。亲手接通 HTTP 入口，追踪一轮的执行归属，验证客户端离线后的结果与资源收尾。

这个云端 Agent 还缺什么？一个能一直工作的服务端

我们已经能在一个 Thread 里连续对话，也能用 /resume 找回历史。现在请它写一份长回答，回答到一半关掉终端：如果终端程序持有 Codex 子进程，这次执行就会跟着结束。要亲手做一个云端 Agent，先让执行拥有独立于用户窗口的生命周期。

本章要完成的体验很具体：在一个终端启动服务，在另一个终端聊天；关掉聊天窗口，服务继续工作；重新连接同一个 Thread，查看这一轮的结果。先在本机验证这条链路，服务默认只监听 127.0.0.1:4313，本章不提供公网部署或多用户授权（上云见 s12，账号与用户隔离见 s13、s14）。

服务端持有什么
读取 .env 中的模型配置，启动 Codex App Server，持有会话与执行中的 Turn。服务端接收 Codex 通知，即使此刻没有客户端查看，也会更新状态。
客户端持有什么
读取 .data/connection.json 中的地址与连接令牌，保存当前选中的 Thread id，通过 HTTP 提交和查看。客户端不读取 .env，不启动 Codex，不需要模型 API Key。

Thread 是会话，Turn 是其中的一轮。服务端进程、客户端进程、Codex 子进程则是运行边界。把这三种概念分清，就能回答“关掉哪一个进程会停止哪一部分工作”。

📌

先定验收条件

客户端退出只停止提交与查看，已交给服务端的一轮继续执行。停止服务端会结束 Codex 子进程；原生历史保留，但 s03 没有持久任务记录来核对中途执行。

接好入口：HTTP 请求先过连接校验

给 Agent 一个入口，并不意味着把模型密钥交给每个客户端。服务启动时生成随机连接令牌，写入权限为 0600 的连接文件。客户端每次发送 Authorization: Bearer <令牌>；这个令牌只用于访问 Agent 服务，与远端模型的 API Key 分别管理。

HTTP 负责外层请求；服务端通过 JSON-RPC 调用 Codex。读源码时先看谁在和谁说话，再看同样名为“请求”的操作实际跨过了哪条边界。

发起一轮：为什么要同时检查 activeTurnId 和 starting

试想两个客户端几乎同时向同一个 Thread 提交。只检查 activeTurnId 不够：第一条请求可能已发出 turn/start，却还没拿到 turn id，第二条就趁这个空隙进来了。因此需要一个“正在发起”的标记。

源码 · stages/s03-service/server/modules/sessions/index.mjs · 第 32–43 行 
  async startTurn(threadId, text) {
    requireText(text);
    await this.ensure(threadId);
    const session = this.sessions.get(threadId);
    if (session.activeTurnId || this.starting.has(threadId)) throw new AppError("上一轮还在执行，请等它结束再发送。", 409, "TURN_IN_PROGRESS");
    this.starting.add(threadId);
    try {
      const result = await this.rpc.request("turn/start", { threadId, input: [{ type: "text", text: text.trim(), text_elements: [] }] });
      const turn = this.recordTurn(threadId, result.turn);
      return { threadId, turnId: turn.id, status: turn.status };
    } finally { this.starting.delete(threadId); }
  }
逐行解读 · 行号对应源文件

32–35 行：startTurn 接收会话与文本；先校验非空输入，再确保会话已载入，最后取到服务端保存的会话对象。

36 行：activeTurnId 表示已有一轮在执行；starting 表示启动请求还没结束。任一条件成立都返回 409 和 TURN_IN_PROGRESS。

37–38 行：在等待 RPC 之前写入 starting，再进入 try，挡住同一会话的第二个启动请求。

39 行：把文本包装成 Codex 的 input 数组，发 turn/start；await 等待的是启动响应，不是完整回答。

40 行：recordTurn 登记 turn id 与状态；它也保护已经收到的完成状态，避免早到通知被启动响应覆盖。

41 行：把 threadId、turnId 和状态返回给 HTTP 层，客户端从此按这两个 ID 查看结果。

42–43 行：finally 在成功和抛错时都会清除 starting；方法在此结束，后续通知由服务端订阅者接收。

202 表示这一轮已被接受
POST /turns 会等待 startTurn 返回，然后响应 202。它省去了等待完整模型回答的时间，但不是“收到 HTTP 就直接返回”，也没有把输入写入持久队列。
409 表示当前不能再开一轮
s03 服务端不排队。同一会话上一轮未结束时拒绝新提交；CLI 会等上一轮完成再发送下一条。仍留在客户端、尚未发送的输入不会因服务常驻而自动保存。

服务端收到 turn/started、item/agentMessage/delta、turn/completed 等通知后，把文字与状态整理成 快照。完整历史仍由 Codex 原生持久化，服务端的近期视图不承担历史数据库的职责。

查看一轮：停止轮询为什么不会取消执行

客户端要显示回复，先得知道回复写到了哪里。s03 使用 轮询：默认每隔 200 ms 查询一次会话快照，把新增的文字渲染到终端。界面可以逐渐出现文字，但传输方式仍是多次 HTTP 查询。

源码 · stages/s03-service/client/modules/connection/index.mjs · 第 42–54 行 
  async follow(threadId, turnId, onSession, { signal, interval = 200 } = {}) {
    while (!signal?.aborted) {
      const { session } = await this.request(`/state?threadId=${encodeURIComponent(threadId)}`);
      onSession(session);
      const turn = session.turns.find(item => item.id === turnId);
      if (turn && turn.status !== "inProgress") return turn;
      await new Promise(resolve => {
        const finish = () => { clearTimeout(timer); signal?.removeEventListener("abort", finish); resolve(); };
        const timer = setTimeout(finish, interval);
        signal?.addEventListener("abort", finish, { once: true });
      });
    }
  }
逐行解读 · 行号对应源文件

42 行：follow 接收 threadId、目标 turnId、渲染回调和可选取消信号；默认间隔是 200 ms。

43–45 行：没有停止查看就继续循环，GET /state 后把快照交给 onSession；这里没有提交文本。

46–47 行：在快照中定位这一轮；找到且状态不再是 inProgress 时返回，包括成功、失败或被中断。

48–50 行：等待下一次查询；finish 清除计时器和取消监听，并结束本次等待。

51 行：接到 abort 信号可提前结束等待；它不发送 turn/interrupt。

52–54 行：等待结束后回到循环条件，决定继续查询还是退出 follow。

现在可以解释验收现象：客户端 Ctrl+C 后，follow 不再运行，但服务端的 Codex 连接仍在接收通知。重新运行客户端并 /resume 选中同一个 Thread，只会读取并显示一次快照，不会自动继续轮询。若这一轮仍在执行，显示的可能只是部分回复；稍后再次 /resume 并选中同一 Thread，或通过带连接令牌的 GET /state?threadId=<Thread id> 核验最终状态。若模型报错，应看到失败状态；“客户端可离线”保证的是执行归属，不保证每次模型调用都成功。

📌

断线不等于未提交

如果 POST /turns 的响应在网络中丢失，客户端可能不知道服务端是否已经发起执行。s03 没有 clientMessageId 去重记录，不要把“没收到响应”当成“肯定没执行”而直接重复发送。下一章会为每条输入建立任务记录。

让服务长期运行：资源要能收回，历史要能找回

常驻服务还需要回答两个实际问题：启动到一半失败，已经拿到的端口和子进程怎么办？每次运行留下的日志，什么时候能清理？先把资源的生命周期写清楚，再处理运行目录的保留。

启动顺序是：配置与独占锁 → 运行目录 → Codex 配置和连接 → 会话模块 → 运行目录维护 → HTTP 监听 → 发布连接文件。每得到一个资源，就登记清理动作；关闭时倒序执行，先收回入口，再关闭内部依赖。

源码 · stages/s03-service/server/modules/lifecycle/index.mjs · 第 9–16 行 
    defer(action) { cleanup.push(action); },
    close() {
      closing ||= (async () => {
        const failures = [];
        for (const action of cleanup.reverse()) { try { await action(); } catch (error) { failures.push(error); } }
        if (failures.length) throw new AggregateError(failures, "部分资源未能正常关闭。");
      })();
      return closing;
逐行解读 · 行号对应源文件

9 行：defer 把清理函数放进 cleanup 数组，登记时不执行。

10–11 行：close 首次调用时创建关闭 Promise；closing ||= 让后续关闭请求复用同一个过程。

12 行：准备 failures 收集各资源的关闭错误。

13 行：reverse 按登记的反方向逐个 await；某个动作失败会被记录，其余动作仍继续。

14 行：所有动作都尝试完后，若有错误则统一抛出 AggregateError。

15–16 行：保存并返回同一个关闭 Promise，让调用者等待完整收尾。

长期保留的状态
workspace/ 是固定工作目录；.data/codex/ 保存 Codex 原生历史和配置；.data/session-index.json 保存会话位置。它们与每次启动的运行缓存有不同生命周期。
仅在运行时需要的入口
同一目录由 .data/server.lock 保证只运行一个服务；.data/connection.json 发布本次地址与令牌。正常关闭时回收这些入口，运行目录则标记结束。
有条件清理的缓存
维护模块启动时检查一次，此后每小时检查。保留最近 5 次运行和 7 天内修改过的目录，候选目录还需确认没有活进程、打开的文件或正在使用的会话。

清理 .runs/app-server-* 前，程序先把日志中的会话位置保存到索引，再核对目录有没有变化。出现链接、非缓存内容，或无法完整检查占用时，就跳过。这样删掉过期日志后，/resume 仍能定位历史；这里不要求你手工删除目录来完成练习。

在 .env 中配置模型地址、密钥和模型名后再运行 check。终端 1 保持服务运行；终端 2 进入同一个阶段目录，运行 npm run chat。输入一个需要长回答的问题，记下 Thread id，看到回复后按 Ctrl+C 退出客户端。稍后重新 npm run chat，用 /resume 找到并选中同一会话。恢复只读取一次快照；若这一轮尚未结束，终端不会自动更新，请稍后再次 /resume 并选中同一 Thread。也可通过带连接令牌的 GET /state?threadId=<Thread id> 核验状态；确认这一轮为 completed 后再恢复查看完整回复，失败或中断则核对对应状态。
