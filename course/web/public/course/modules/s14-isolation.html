s14

用户隔离：每个用户一个运行环境

接口之外，原生状态也要分开；独立进程和目录承接用户身份，操作系统权限兜底。

接口挡得住请求，挡不住底层文件

上一章让云端 Agent 认出每个用户，API 层彼此看不见。但 Codex 自己读写的历史、索引、记忆和 Skill 副本不经过 API，仍由同一个进程打开。要避免底层串话，不同用户的原生状态必须放在不同目录、由不同进程读取。

一个用户运行环境包含独立 Codex App Server、CODEX_HOME、工作目录和系统身份。同一个用户的多个会话共用自己的进程，不同用户不因 Agent 配置相同而共用状态。

用户映射持久化保存 uid 和目录，uid 从 10001 顺序分配，gid 同号；首个 admin 保留既有原生目录的绝对位置。进程回收不删除映射与历史，下次可以重新启动。Skill 安装、核验与会话工作目录也随用户分开。

按需启动，同一个用户只启动一次

按需启动让进程数取决于活跃用户，而不是注册用户总数。同一用户同时发来几个首次请求时，不能各启动一个进程：先占位，后来的请求等待同一份启动结果，这就是single-flight。

身份与上下文：owner 为空直接拒绝。同 owner 的 ready 嵌套调用复用当前 value；池关闭或账号禁用时不能沿用这个快捷路径。

串行 admission：先调用 assertEnabled 核对账号，再读取 entries。closing 项不能借用，等待清理时仍应返回繁忙。

占位与 Promise：entries.set 发生在请求等待之前。entry.ready 只在新项创建时赋值，同用户的请求自然汇合到一个 Promise。

请求租约：refs 在等待前增加，覆盖启动等待和业务执行。try / finally 确保成功、异常都减少租约并更新 lastUsed。

连接路由：await entry.ready 之后还检查 state；通过 context.run 才把 operation 放入当前用户运行环境。取得旧引用不等于可以使用已关闭连接。

启动上限为 30 秒。超时后即使进程迟到，也不能发布为可用连接；必须等待清理完成才释放名额，避免旧进程没退出又开一份。

请求按认证身份路由，后台按任务记录路由。工具回调要同时核对连接 owner、任务用户和会话 owner，一致后再检查轮次与工具权限；参数里自称的身份不参与授权。

服务的 /ready 不表示所有用户进程已启动。首次请求才触发该用户的 Codex、Skill、工具与记忆核验，就绪探测不能提前保证这次启动成功。

进程有限：空闲回收，全忙就拒绝

每人一个进程也不能无限增长。池最多保留 4 个进程；满了先回收最久未用且确实空闲的一个，全都忙就返回 503 RUNTIME_BUSY，提示 10 秒后再试。这延续了 s12 的背压。

“空闲”要同时满足 ready、没有请求租约、没有执行中轮次和排队任务。定时回收还要求闲置 10 分钟，容量满时则不必等满 10 分钟；查不清忙闲时保守地不回收。

租约优先：不是 ready 或 refs 非零直接返回 false。哪怕没有正在执行的 Turn，一个读取请求仍可能在使用连接。

源码 · runtimes/pool.mjs · 第 129–144 行
  async remove(entry, error) {
    if (entry.removing) return entry.removing;
    entry.state = 'closing';
    clearTimeout(entry.idleTimer);
    entry.controller.abort(error || new Error('运行环境已回收。'));
    entry.removing = (async () => {
      // 先停止进程与工具；确认任务状态后才释放名额，防止迟到通知与新进程交叉。
      if (entry.value) await this.closeValue(entry.value);
      else await entry.creating?.then(value => this.closeValue(value), () => {});
      if (error) await this.onLost(entry.owner, error);
      await this.onRemoved(entry.owner);
      if (this.entries.get(entry.owner) === entry) this.entries.delete(entry.owner);
    })();
    return entry.removing;
  }

逐段解读

共用清理：entry.removing 存在时直接返回，避免同一对象并发清理。设置 closing 并中止启动后，其他请求不能继续取得它。

先停止：已有 value 就 await closeValue；启动尚未返回则等待 creating 收尾并关闭结果。关闭前不能释放名额。

再收尾：带 error 时调用 onLost 核对该 owner 的任务状态，然后 onRemoved 清理缓存。最后确认 Map 中仍是当前 entry 才删除。

回收先等待进程退出，再释放名额；关闭异常或超过 10 秒时执行强制终止兜底。回收只影响活动进程和缓存，下次仍从同一用户的历史恢复。

4 个进程不等于 4 轮并发。全局同时执行仍最多 2 轮；一个进程即使没有输出，也可能有排队任务，不能直接当成空闲。

操作系统兜底：每人一个系统身份

只分目录还依赖代码把路径写对。再给每个用户进程独立 uid，并让目录归这个 uid，操作系统就能拒绝跨用户读取：即使知道别人的路径，也没有权限打开。

这里使用独立数值 uid/gid，不需要系统账号文件中的条目。服务进程能切换身份和调整归属，但没有无视权限位的能力；用户进程只继承白名单环境，不拿数据库或服务商密钥。最终 spawn 才是这些约束真正生效的位置。

正向白名单：只选择 CODEX_BASE_URL、CODEX_API_KEY、PATH、LANG，再设置属于用户自己的 HOME、CODEX_HOME、CODEX_SQLITE_HOME。数据库、Redis、服务商凭据和 Node 注入变量不会被整体继承。

系统身份：isolated 时传 uid/gid。Node/libuv 清空继承的补充组；本机非隔离模式不传这些选项，不能将此模式当作权限验收结果。

服务代读文件也要按用户权限进行，否则会成为绕过隔离的通道。隔离模式用同 uid 辅助进程读取，检查属主、文件类型、链接和大小；不能只校验一次路径字符串就放行。

必填上限：maxBytes 必须是 0 到 16 MiB 的安全整数。调用方不能以省略上限的方式执行无界读取。

打开标志：O_NOFOLLOW 拒绝最终路径的符号链接；O_NONBLOCK 避免特殊文件造成阻塞，随后还要核对类型。父目录也逐级检查是真实目录。

一个人的进程崩溃，不连累别人

用户进程崩溃只能说明结果不确定，不能说明工具没有执行。服务按连接 owner 关闭该进程，把他的执行中任务标为 unconfirmed、暂停相关会话待核对；其他用户继续工作，下次请求可重新拉起他的进程。

禁用账号同样会关闭对应进程，并在取得运行环境和工具调用时复查账号状态。若接收禁用通知的控制通道丢失，执行器会停止；这与单用户进程崩溃的影响范围不同。

原生记忆已按用户物理分开，但开启不代表摘要生成成功：固定版本禁用原生写工具时，后台合并仍不能写出最终摘要，知识库挂载策略的限制也继续生效。

离线路由、容量和崩溃实验分别验证身份、回收与故障范围；真实 uid 文件隔离、数据库通知和模型运行需另外验证。部署与实验入口见本章 README，权限及已知限制见设计说明。

判断隔离时，分别寻找三类证据

业务层看认证与任务 owner；进程层看连接归属、租约和生命周期；系统层看真实 uid/gid、目录权限和有界读取。三层互相补充。只看到 HTTP 返回 404，不能证明底层文件不可跨读；只看到用户进程分开，也不能省略工具与资源归属检查。
