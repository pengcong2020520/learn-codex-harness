四层架构：谁存什么、谁唤醒谁

Demo 3 用单文件 JSON 管理业务状态，Codex 原生历史独立维护；已具备 FIFO 排队与重启时暂停不确定执行的能力。Demo 4 在此基础上新增关系事务与内容版本追踪。 Demo 4 把存储拆成四块各自负责，就像一家公司把财务账本、门卫铃、文件柜、原始档案交给四个专职部门。

🗄️
PostgreSQL 账本
所有业务状态（任务、会话、资源版本）的权威来源。写操作在 PG 事务内完成，保证原子性。
🔔
Redis 提醒铃
只存 Thread ID Set，用于低延迟唤醒调度器。它不存任务数据，失联时 outbox 兜底，不丢任务。
📦
Blob 文件柜
以 sha256 命名的不可变文件，存在 .data/files/objects/。内容写入后不覆盖，版本变了就是新文件。
🧠
Codex 原生历史
完整模型回复与工具调用历史，由 Codex 自身管理（SQLite/JSONL），主进程不读写，PG 不重复存储。

PG 账本：任务与调度出口同事务写入

想象银行转账：从 A 账户扣钱和向 B 账户加钱必须同时成功或同时失败，不能只做一半。 Demo 4 把「写任务」和「写调度出口」绑进同一个 PG 事务——服务崩溃时，账本要么两条都有，要么两条都没有，不会出现任务存在但调度出口丢失的情况。

源码：project-evolution/demo4/server/modules/data/jobs.mjs:75–81

真实源码 · 7 行
      await this.wake(job.threadId, client);
      await this.query(
        `UPDATE agent_data.conversations SET name=CASE WHEN name='' THEN $4 ELSE name END,updated_at=now()
        WHERE instance_id=$1 AND owner_id=$2 AND id=$3`,
        [job.threadId, job.text.slice(0, 100)],
        client,
      );
中文对照

第 1 行：wake 用同一事务 client 写 outbox；前面的任务写入也共享这个事务。

第 2–4 行：更新当前 owner 的指定会话；已有名称保留，空名称才采用任务原文。

第 5–7 行：只取原文前 100 字符作为候选会话名，并把同一事务连接传给 query。

⚡ 关键约束：tasks.text 只存用户任务原文（最多前 100 字符同步到会话名）。完整模型回复与工具历史不在 PG，由 Codex 原生存储管理。向 AI 程序员描述问题时，说"任务原文在 PG tasks 表，模型历史在 Codex 原生存储"是准确的表达。
表 存什么 不存什么
tasks 任务原文、状态、模式、Thread 归属 完整模型回复、工具调用历史
outbox 以 Thread 为键的调度出口、generation 号 任务 ID 列表（不是队列）
resource_versions sha256、文件路径、版本元数据 文件正文（正文在 blob）
conversations 会话、绑定的 agent 版本 Codex 原生对话消息

Redis 提醒铃：Set 唤醒，不是任务队列

Redis 在这里扮演的是"门铃"，而不是"信箱"。有人按铃（sAdd），调度器就去 PG 账本里按顺序领取；铃声本身不携带任务详情，也不保证顺序。 任务的权威顺序和状态，永远在 PG。

源码：project-evolution/demo4/server/modules/data/queue.mjs:58–66

真实源码 · 9 行
    const rows = await this.jobs.deliveries(); // Database failure stops execution, Redis failure only delays dispatch.
    for (const row of rows) {
      try {
        await this.commands.sAdd(this.key, row.thread_id);
      } catch {
        this.healthy = false;
        return;
      }
      await this.jobs.delivered(row);
中文对照

第 1–2 行：从 PG 取待投递记录，并逐条处理；数据库失败会中断，Redis 失败只延迟派发。

第 3–4 行：sAdd 只放入 Thread ID；Set 去重仍留在集合中的 ID，不代表任务只执行一次。

第 5–8 行：Redis 失败就标记不健康并退出；尚未确认的 outbox 记录可在后续补投。

第 9 行：Redis 写入成功后，才确认本条调度出口已投递。

✅
Redis 负责
存 Thread ID Set；低延迟唤醒（200 ms 轮询）；sAdd / sPop 操作。
🚫
Redis 不负责
不存任务 ID 队列；不存任务详情；不保证顺序；不替代 PG 做业务状态存储；不存向量数据。
🛡️
Redis 失联时
outbox 记录留存在 PG，调度器健康标记置 false，下次恢复后可补投。任务不丢，只是延迟。
🔑 常见误区：Redis Set 不是任务队列（任务队列存的是任务详情、有顺序保证）。这里 Set 只是"有哪些 Thread 需要被调度器看一眼"的信号，PG 才是决定"领哪条任务"的权威。

02 层 · Redis 提醒铃

Codex 执行完毕，任务状态更新为 completed。若执行中服务重启，状态变为 unconfirmed——暂停，等待人工决策，不自动重发。

不可变 Blob：内容寻址与来源追踪

单机单 owner、单 Agent 配置，支持多 Thread；并非多 Agent 编排。Demo 4 使用数据库 agent_demo4（schema v1），Demo 5 使用 agent_demo5（schema v2），PG 与 Redis 均必需。两套 Compose 绑定相同的 5432/6379 端口，不可同时启动；可共享一组依赖并使用不同数据库。

sha256 是内容指纹，正文按指纹命名保存。内容改动会生成新 blob，已登记版本不被覆盖；这不等于承诺永久保留。 这让系统能追踪“摘要声明引用的是 report.md 哪个版本”；读取或校验发现原文变化后，依赖链会传播失效。

🔒
create-only，不覆盖
write_file 只创建新路径，已有路径会被拒绝，即使内容相同。底层 blob 可按内容指纹复用；这是不同层次的规则。
📂
路径格式
.data/files/objects/<sha256>.txt——无子目录，所有版本平铺在同一目录。.data/codex/ 是 Codex 原生存储，由 Codex 管理，主进程不读写。
🔗
来源声明 vs 语义证明
dependencies 表记录版本依赖，source_versions 声明来源。这是声明，不证明模型语义引用完全——AI 可能引用了未声明的内容。
⚠️
跨存储非原子
blob 文件写入与 PG 写 resource_versions 之间没有跨存储事务保证。PG 内部操作是原子的；跨文件系统与数据库则不是。

场景二：一位 AI 程序员告诉你某条任务的 status 是 unconfirmed，问你该怎么处理。你会如何解释这个状态，以及下一步该做什么？
