# 写作助手角色提示词精简评估报告

**报告日期**：2026-11-02
**评估对象**：`app/agents/writing/role.md`（当前版本 2,274 字）与三版精简候选（见 `candidates/`）
**评估方式**：`app/eval/role/` 的四个固定场景，在服务器上用真实模型（deepseek-flash，推理档 high）运行，每个场景每个版本 5 次、两版交替；`npm run eval:role:score` 做硬性检查、token 统计和盲评（deepseek-v4-pro，交换先后各评一次）。
**判定标准**：质量是红线——每个场景的硬性检查通过率不低于基线、盲评负场不多于胜场；token 必须下降。

---

## 1. 结论

**保持当前角色不变，精简版作为候选保留。** 精简版每次请求的固定指令少一半，四个场景合计 token 下降 15%–21%，但三轮里每一轮都有质量问题没有完全排除，按"质量下降是红线"的标准不能上线。之后模型从 DeepSeek 换成 Kimi，用户决定不再重跑：token 消耗主要取决于提示词长短与任务形态，在各模型之间是通用的结论。

| 轮次 | 候选 | 角色字数 | 四场景平均总 token 合计（基线 → 候选） | 质量 |
|---|---|---|---|---|
| 1 | slim | 659 | 189,355 → 157,970（**−16.6%**） | 公众号 1 次没有保存；盲评公众号 1 胜 2 负（虚构用户经历） |
| 2 | slim2 | 785 | 195,820 → 167,184（**−14.6%**） | 硬性检查全部持平（未盲评） |
| 3 | slim3 | 824 | 187,745 → 148,180（**−21.1%**） | 公众号 1 次篇幅不足且谎报字数；本地写文档盲评前 2.5 对偏向基线 |

第 3 轮盲评做到第 3 对时 DeepSeek 余额耗尽（HTTP 402），没有完成。

## 2. Token

每次请求都会带上的固定部分（第一次请求，字符数）：

| 部分 | 当前 | slim3 |
|---|---|---|
| 基础指令（角色 + 资源规则） | 3,066 | 1,616（−47%） |
| 工具定义 | 5,462 | 5,462 |
| Skill 清单与权限说明 | 992 | 992 |
| 环境信息与用户需求 | 699 | 699 |

第 3 轮各场景平均总 token：

| 场景 | 当前 | slim3 | 变化 |
|---|---|---|---|
| 本地写文档 | 62,612 | 38,615 | −38% |
| 写公众号文章 | 28,407 | 25,284 | −11% |
| 信息调研并整理成文档 | 60,843 | 51,784 | −15% |
| 写汇报材料 | 35,883 | 32,497 | −9% |

- 约 90% 的输入 token 命中缓存；推理 token 每次波动很大（同一场景两次可差 50% 以上），5 次的平均值仍有明显噪声。第 1 轮"写汇报材料"候选比基线多 28%，逐次拆开看是 2/5 次先写超长再另存精简版、1 次推理特别长，与报告详略无关（两版最终字数 1,308 与 1,321）。
- 节省来自两处：角色变短直接减少每次请求的输入（每次约少 1,500 字）；本地写文档的输出 token 也少了约一半（第 1 轮 16,419 → 7,616），这部分的原因没有逐次拆解，不下结论。
- 工具定义（5,462 字）才是最大的固定部分，其中 Codex 内置的 `request_user_input` 就有 1,425 字，在 0.154 版本里关不掉。

## 3. 质量问题与原因

| 问题 | 出现在 | 原因 | 候选里的修正 |
|---|---|---|---|
| 以为 outputs/ 只读，没有保存 | slim，公众号 1/5 | 资源规则里 `articles`（outputs/）标的是 `read`，新建权限写在另一段 `outputs`；当前角色明说"outputs 用于分类保存"，精简版删掉了这句 | slim2 起写明各目录能否新建 |
| 虚构用户没说过的经历（"去年冬天""第一次写复盘卡住"） | slim 3 次 / 当前 1 次（盲评） | "不虚构"写得太笼统 | slim3 写明不替用户编造经历、场景、时间或感受 |
| 篇幅不足（1,287 字，要求 1500–2000）却回复"约 1700 字" | slim3，公众号 1/5 | 模型凭感觉估字数 | 未修正（可加"写完核对篇幅"） |
| 把资料没定的事项写成已定（计数口径、附件去重） | slim3，本地写文档（盲评前 2.5 对） | 精简版对"补充内容标明是建议"的要求不够具体 | 未修正（可加"补充的假设标待定/建议"） |

两处"未修正"如果以后要继续，建议在 slim3 上补这两句后，只重跑公众号和本地写文档两个场景确认。

## 4. 评估过程中发现并修好的问题

- **交付物选错**：原来取 outputs/ 下最长的文件，模型先写长稿再另存精简的 `_v2` 时，评的是被放弃的长稿。改为取最后写入的那份。
- **检查规则认不出千分位**：只认"1000 次"，模型几乎都写"1,000 次"或把冲突写成小标题，导致两版大部分运行被误判。修正后补了回归测试。
- **盲评连接被断开**：评审模型要推理好几分钟，非流式响应在这期间没有数据，被客户端（默认 5 分钟）或代理当作超时断开。改为流式请求，断线和服务端错误自动重试，评审结果按"场景-序号-先后"存盘，重新打分不再重复花费。

## 5. 其他发现

- **联网搜索全部失败**：三轮调研场景共 93 次搜索，0 次拿到结果——Google 自 2025 年 1 月起只给能执行 JavaScript 的客户端返回结果，`search_web` 抓取结果页 HTML 的做法已失效。调研场景实际只能依据用户给的资料。
- **资源规则的写法容易误导模型**：见第 3 节第一行。把"可新建"直接写进对应目录的规则，所有角色都会受益。

## 6. 成本

三轮共 120 次运行：deepseek-flash 输入约 406 万 token（其中缓存命中 349 万）、输出约 117 万 token；第 1 轮盲评 deepseek-v4-pro 输入约 32 万、输出约 15 万 token。
